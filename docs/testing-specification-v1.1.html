Testing
Specification

Abstract. This document specifies the acceptance conditions under which each part of the No Crumbs system is considered correct, and the test level at which each condition is verified. It covers five test levels — unit and domain, component render, end-to-end browser, database policy, and documented manual procedure — and is organised by requirement area: the core business process, input validation, access control, database integrity, and the user interface. Each section states what is measured, the method of measurement, and the classes of defect the level cannot detect. Quantitative claims about model output quality are outside the scope of the automated suite and are addressed in section 1.6.

5 test levels 4,087 unit tests 58 browser tests 277 policy assertions

The suite comprises five levels. Each level exists to detect a class of failure that the other levels cannot detect by construction.

The placement rule is that a test belongs at the cheapest level that can still fail for the reason the test exists to detect. A test that passes for an unintended reason is treated as worse than no test, because it removes the signal without removing the risk.

Section 01

Core Feature and Business Process Verification

The system implements a single business process. The acceptance condition is that the process completes every stage without fabricating data at any stage.

1.1  The business process under test

The system implements one business process, and every test in this section constrains one stage of it. A user submits a TikTok link. The link is converted to a canonical video identity, then to a caption, then to a structured extraction, then to resolved real-world places, and finally to rows owned by that user on a private map.

1.2  Definition of a successful import

Successful completion is not defined as the traversal of the fully-resolving path, because that path is not the modal outcome. The most frequent outcome of an import is that the caption names no place.

The outcome “no places found” is therefore specified as a success state with a dedicated screen and dedicated tests. An implementation that classified it as an error would fail this specification irrespective of the HTTP status codes returned.

1.3  Pipeline coverage

One end-to-end test drives the pipeline through real code. It asserts the emitted event sequence in order, and asserts that an extraction yielding zero candidates terminates on the no-places screen defined in section 1.2.

The same test establishes partial resolution as a terminal success state: an import in which some candidates resolve and others do not is a completed import, on the ground that an unresolved place name carries more information for the user than a failure screen.

1.4  Error code taxonomy

The error taxonomy is closed and is asserted to be closed. Thirteen error codes are defined. The pipeline test reaches each of the thirteen through real code paths and then asserts that all thirteen were reached.

A fourteenth code therefore fails the suite until a reachable path to it is demonstrated. The refusal codes within this taxonomy are further constrained by the distinguishability requirement in section 2.3.

1.5  Verification of the assembled application

Six of the thirteen browser specifications drive the import flow, including a double submission and a stale response arriving after the user has changed the submitted link. In the cited run, 56 browser tests passed and 2 were skipped.

1.6  Exclusions at this level

This level establishes that the process completes and terminates in a defined state. It does not establish the quality of the extracted result. Pinning a specific caption to a specific venue would pin the non-deterministic output of a third-party model, and would fail on a model upgrade that constituted an improvement.

Extraction quality is consequently assessed by the documented manual procedures listed in the level table above, with the resulting measurements recorded.

Section 02

Input Validation and Edge Case Handling

The acceptance condition is that the system refuses malformed and unsupported input with a specific, distinguishable code, and does not convert an anomalous input into a confident incorrect result.

2.1  The two untrusted inputs

Two inputs are treated as untrusted, and the threat each presents differs.

InputThreat modelControl
The pasted linkAdversarial. The submitted value determines an outbound request issued by the server.Default-deny host allow-list (section 2.2)
Language model outputNon-adversarial but unreliable. The model produces well-formed responses containing invented values.Schema validation (section 2.4)

2.2  URL parsing and the host allow-list

The paste field is a security boundary rather than a usability affordance, because the submitted value becomes an outbound request from the server. Its parser is default-deny against a closed allow-list of six hosts, matched by full-host equality and never by suffix.

The corresponding tests submit hosts constructed to defeat a naive matcher.

Attack shapeExpected result
A host that merely ends in tiktok.comRejected
A host containing tiktok.com as a substringRejected
Credentials embedded in the authority componentRejected
An explicit portRejected
An IP literalRejected
Any non-HTTP schemeRejected

A further test asserts that the allow-list is exactly that closed set, and that the same set is shared with the short-link resolver, so that a second adapter cannot widen the boundary independently.

2.3  Distinguishability of refusal codes

Refusal codes are required to remain distinguishable from one another. An Instagram or YouTube link is a recognised unsupported platform rather than a malformed input: it receives its own code and a route to manual entry. Text containing no link at all receives a different code and different copy.

A test asserts that the two cases never collapse into a single code, because a collapsed code directs the user to correct an input that is not incorrect.

2.4  Model output validation

The schema tests reject the classes of value a model produces when it extrapolates beyond its input.

Invalid outputExpected result
A category outside the defined vocabularyRejected
A candidate list exceeding the candidate capRejected
A latitude outside the valid rangeRejected
A string within the length limit as submitted, but over it once accents are normalisedRejected
Null coordinates, present as an explicit fieldAccepted, and the field is required to be present

The final row is a deliberate asymmetry. An explicit null records the claim that no basis for a coordinate exists; an absent field records nothing, and the two are not interchangeable.

2.5  Truncated model output

A response truncated mid-list is salvaged rather than discarded: the candidates that parsed successfully are retained. The alternative — discarding a complete set of valid candidates because the response was cut short — produces the worse outcome for the user, and the behaviour is fixed by test.

2.6  Exclusions at this level

This level establishes that the boundary rejects invalid input. It does not establish that the boundary is the only path into the system. That property is the subject of the layer guard described in section 4.4.

Section 03

Access Control and Privacy Enforcement

The acceptance condition is that a second signed-in user holding a valid session can neither read nor forge a row belonging to the first. It is established by executing the attack, not by inspecting the policy definition.

3.1  Placement of the authorisation tests

Every map is private, so a failure in this area is a disclosure rather than a degradation. Authorisation is enforced in the database, and the tests are therefore executed in the database.

Eight SQL policy files carry 277 assertions. The database job in continuous integration rebuilds the schema from the first migration and executes all eight files on every push. Seven of the eight create at least two real users and issue the adversary’s queries under the adversary’s own role.

3.2  Assertion ordering

Each file asserts the positive case before the negative case. The assertion “user B sees zero of user A’s rows” is satisfied identically by a correct policy and by a database in which no role can read anything, and is therefore the standard mechanism by which a policy suite becomes vacuously green.

Each file consequently demonstrates first that user A reads exactly one of their own rows through each gated table, and only then that user B reads zero. The ordering is a required property of every file in this section.

3.3  Forgery attempts

Read isolation is the weaker half of the requirement. The suite additionally establishes that user B cannot perform the following writes.

Attempted writeExpected result
A provenance row carrying user A’s user idRefused
Provenance attached to a place user B does not ownRefused
A save borrowing user A’s source rowRefused
An invite token chosen by the clientRefused
Presentation of an unknown, a revoked and an expired tokenAll three fail identically, so a token cannot be probed for existence

3.4  Scope of collaborator access

Sharing grants access to a place, not to a library. A collaborator reads the shared place identity and reads none of the owner’s private note, provenance or aliases. The boundary is asserted field by field.

3.5  Failure-first validation of each control

Every assertion in this section was validated in both directions against a disposable database: the control was removed, the assertion was observed to fail with the message it emits, and the control was then restored. A control that has never been observed to fail is not treated as evidence.

Section 04

Database Integrity and Data Safeguards

Database correctness is decomposed into three properties and verified by three methods: authorisation, invariants verified by execution, and a static gate on the security posture of every newly created table.

4.1  Invariants verified by execution

The retention bound on captions is established by executing a deletion and asserting that the dependent rows are absent afterwards, rather than by confirming that a foreign key is declared to cascade. Authorisation, the first of the three properties, is covered separately in section 03.

The same file asserts a set of absences — no coordinate column, no import reference — because a table capable of acquiring a location column represents a privacy guarantee that degrades silently over subsequent migrations.

4.2  Static gate on new table posture

One gate executes on every build, addressing a hazard that a local database does not exhibit: hosted Postgres grants broad privileges on newly created tables to browser-reachable roles.

A script therefore rejects any migration that creates a table without enabling and forcing row-level security and revoking those grants within the same file. The check that protects production is itself executed in the pipeline, so it cannot diverge from the migrations without detection.

4.3  Deferred constraint triggers under privileged functions

One failing test established that a privileged function does not extend its privilege to a deferred constraint trigger. The queued check executes at commit time under whichever role is then in effect, not under the role that queued it.

The condition was classified as harmless only after demonstrating by execution that the signed-in role cannot invoke the one function that inserts into the affected table.

4.4  Self-verification of the layer guard

The architectural layer guard is itself a test. It writes deliberate layer violations, asserts that the linter rejects each one, and then removes them. The guard establishes that the rule is capable of failing before the rule is relied upon to pass. It is the control referred to in section 2.6.

Section 05

User Interface and Interactive Map Tests

This is the least complete level of the suite. The section states its three methods, and states explicitly which properties of the interface remain unverified by automation.

5.1  Methods and their scope

The interface is verified by three methods, each with a stated limit.

MethodProperty establishedLimit
Component renderMarkup and accessible name, from a static HTML stringNo styling is applied, so no conclusion about layout, size or contrast follows
Pinned copyThe exact wording of a screen, and the words prohibited from itEstablishes the string, not the condition under which it is displayed
Browser interactionInteraction in a real browser at both specified viewport sizesNo comparison against a visual baseline (section 5.6)

5.2  Component render tests

These tests target the defect class that is easiest to introduce and hardest to observe. An approximate pin is required to remain visually distinguishable from a matched pin, and is simultaneously required to retain its screen-reader name.

The specific mechanism guarded is that a label replaces the content of a button, after which a glyph placed inside that button is announced nowhere.

5.3  Pinned copy

The no-places screen defined in section 1.2 is asserted word for word against its copy specification, together with a prohibition on the vocabulary that would present it as an error state.

5.4  Source-text assertions and their limits

105 of the 250 unit files read source text and assert against it. This is recorded here as a known weakness of the suite rather than omitted.

The technique is valid for establishing an absence: that a screen contains no prohibited word, or that a module imports nothing from a layer it may not reference. It establishes that the code states something, not that the running application does it. A change that preserves the string while altering the behaviour passes.

5.5  Browser interaction and viewport gates

The shipped device presets are 412×839 and 1280×720. The design is specified at 390×844 and 1440×900, and the 22-pixel difference falls at the width at which the layout selects its column count.

Two additional browser projects therefore exist solely to assert the measurement conditions before any measurement is taken under them.

5.6  Visual regression comparison, excluded

Screenshot comparison is excluded by decision. A pixel baseline maintained against a product undergoing redesign requires re-approval on nearly every commit, which yields the evidential value of no baseline at the maintenance cost of one.

5.7  Limits of automated verification

No automated test in this suite establishes that the map opened at a useful location. An import that persisted eight correct rows while the camera remained on a different continent satisfies every assertion in the suite while being plainly defective.

For that reason the project’s working agreement requires that the application be run, the feature exercised and the persisted rows inspected before any change is accepted as complete. Automation covers the failure modes that can be described in advance; the remainder are covered by the documented manual procedures counted in the level table above.
