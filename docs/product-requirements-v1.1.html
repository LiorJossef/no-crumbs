Product Requirements
Document

Abstract. This document specifies No Crumbs, a private geographic library assembled from social video links. It states the retrieval problem the product addresses, the single user profile it serves, the five business goals it was built against, the twenty-two capabilities that meet them, and the six core processes a person carries out. The scope boundary is fixed in section 1.2 and its consequences are traced through every later section: one supported source platform, caption text as the only input read, and a permanently retainable field set. Sections 01 to 04 establish the product definition and its rationale; sections 05 and 06 specify behaviour, with a capability-to-goal traceability table in section 5.3 and the exclusions listed in sections 3.3, 4.5 and 5.5.

Section 01

Product Overview

No Crumbs is a private map of places selected by the user, assembled from social video links the user already saves.

1.1  System description

The user submits one link. The application retrieves the post, extracts the places its caption names, assigns each one real coordinates and a directory identity, and presents the result for review. Confirmed places are written to the user’s map, each retaining a link to the post it came from.

The map is the retrieval mechanism rather than one feature among several. Saved places are reached by location rather than by search over a chronological list, and the decisions about what is stored, what is displayed and what is refused all follow from that.

One paste

The complete user contribution per import

TikTok

The sole supported source platform, stated before use

Private

No feed, no followers, nothing public to configure

Permanent

Only fields that can be retained indefinitely are stored

1.2  Scope boundary

The system reads what a post states in words. A large proportion of TikTok videos name the place only on screen or in audio, and those are outside what the system reads.

A link that yields no place is therefore an ordinary result rather than a fault. It has a dedicated screen, specified in section 6.3, offering three routes forward.

The product does not request that the user type the caption in. A product that asks a person for text they could have entered into a notes application has forfeited its reason to exist; this constraint is goal 5 in section 4.1.

1.3  Distinguishing characteristics

Converting a social link into a map pin is not itself novel. Three properties distinguish this product from the general case.

  • Certainty is reported rather than concealed. What the post stated, what the system inferred, and what the user wrote are held separately. A place the system cannot confirm is presented as uncertain rather than asserted as fact.
  • An empty result is a specified outcome, not an error. Most posts do not name a place in words, so that outcome has a dedicated screen with real options.
  • The stored library is durable and private. Only fields that can be retained indefinitely are stored, so no entry expires; ownership is enforced at the data layer rather than by each screen.

Section 02

Problem Statement & Business Value

Collection is already solved by the platforms. Retrieval is not, and retrieval is the only moment at which a saved recommendation has any effect.

2.1  Origin of the problem

Recommendations for physical places — restaurants, cafés, bars, viewpoints, shops — increasingly arrive as social video, and the available response is to save the post.

TikTok stores that save as a video, ordered by save date. It stores neither the location of the place, nor its category, nor its name.

Collection therefore succeeds and retrieval fails. Every question a person puts to a saved collection is a question about location:

  1. I'm in this neighbourhood right now — what did I save near me?
  2. I land in Tokyo on Thursday — what do I already have there?
  3. I want dinner tonight and I don't want to scroll.

A thumbnail in a saved folder rarely carries the name or the city, so answering any of these requires opening videos individually and reading them. That work is performed while standing, with a decision pending on its outcome.

2.2  Limitations of the source platform

Converting a post into a place is work the platform has no commercial reason to perform, so at present the user performs it mentally, from a grid of thumbnails, at the least suitable moment.

2.3  Rationale

The selection work is already complete. Users have scrolled, judged and decided that a place is worth remembering. The product introduces no new habit; it takes an existing collection and makes it reachable.

The output carries more information than the input: a real name, real coordinates, a category, the user’s note, and a link back to the post, held in the user’s own account.

The quantity improved is the decision rather than the search. A collection unreachable at the moment of choosing has no value irrespective of its size.

2.4  Persistence boundary

What survives independently of the platform

The name, the category, the coordinates, the user’s note and the Been marks all survive independently of the source platform. The link back to the original post is the exception: it resolves for as long as TikTok continues to serve that post.

Section 03

Target Audience

A single user profile, asking two questions about places already saved. That person is also the customer, because no second party is served.

3.1  User profile

Everyday

Neighbourhood retrieval

Triggered by standing in a neighbourhood and deciding where to eat. Served by nearby places, nearest first, offered on permission and never required.

Trips

Destination retrieval

Triggered by planning a trip, or by arriving somewhere. Served by the whole library on a single map, anywhere in the world, with no location permission needed.

These are one profile, not two segments. The same person saves places in their city of residence and banks places for a trip not yet taken; designing for two audiences would produce two half-products.

Two properties of that profile constrain every subsequent decision in this document.

3.4  Customer identity and monetisation

The customer is the user and nobody else. There is no advertiser, no business account and no party purchasing access to any user’s data or attention, so the product’s only obligation is to the person whose map it is.

The privacy model follows from that: a private map, ownership enforced at the data layer, and the user’s live location never retained server-side.

No price is proposed, and nothing in this version was built to generate revenue. Were that to change, the indicated direction would be a paid tier for the heaviest savers. That is a direction, not a plan.

4.2  Dependency between the goals

Goal 5 is a precondition of the other four. A notes application already satisfies goals 1 to 4 for a user willing to type the entries in. Every scope decision in this document exists to hold the user’s share of the work to one paste, including the boundary stated in section 1.2.

4.3  Success conditions

The measure of success is not a faster search. It is that the saved recommendation was actually used — that the place kept months ago is the place entered tonight. Three design consequences follow.

Scroll the table sideways →

Success conditionDesign consequence
A saved recommendation is acted upon at the moment of choosingRetrieval is optimised for a standing user with a pending decision; see section 6.4
Adding occurs in batches; finding occurs in the momentEach is given its own surface rather than a compromise between the two
The first session ends with places on the mapOnboarding delivers the first places rather than explaining the product; see section 6.1

The third condition is the strongest of the three. An empty map has no value, so a first session that produces comprehension but no saved places has failed.

4.4  Constraint on stored data

Stored data is restricted to fields that can be retained indefinitely: name, category, coordinates, the link to the video, and the user’s own note. Opening hours, photographs, ratings and reviews are excluded, because each carries an expiry condition, and a library assembled from them is rented rather than owned. That restriction is what makes goal 4 a property of the system rather than an aspiration.

Section 05

Product Capabilities

Twenty-two capabilities, all implemented, organised as six capability groups corresponding to six things a user can do.

5.1  Capability groups

01 · Unmodified link input

Any form of TikTok link is accepted — a short link, a link carrying tracking parameters, a regional variant, or the entire text block produced by the share button. No preparation by the user is required.

An unsupported link, such as Instagram or YouTube, is identified by platform before any work begins and handed directly to addition by name, so an incorrect link costs nothing. Submitting the same link twice returns the same result rather than a fresh non-deterministic one.

02 · Automated reading of the post

No typing, pasted text or screenshots are required: the application retrieves the post and reads the caption for the places it names. An empty result is a specified outcome with a screen built for it and, given the character of captions, a frequent one.

03 · Resolution to real places

A name is not a location, so every name found in a caption is looked up in a places directory until it holds real coordinates and a directory identity of its own.

Where a name cannot be matched, the place is retained. It is positioned approximately, where the caption indicates, but is marked as approximate, drawn differently, and never displayed as confirmed. One unmatched name does not cost the remaining places extracted from the same video.

04 · Review before anything is persisted

Nothing is written until the user confirms it, and the review screen states so. Every place on the map was placed there by a person.

Confident matches arrive pre-selected; uncertain ones arrive as a short choice with nothing selected. No score or percentage is displayed — each card links instead to that place on a public map, because an inspectable reference is more useful than a number requiring interpretation. Where some places could not be saved, the count is reported.

05 · Retrieval by looking

The map is the home surface, and opens framed around the user’s own places. At the widest zoom it renders countries; closer in, areas with a name and a count; closer still, individual pins coloured by category.

A list sits beside the map and cannot disagree with it, because both are derived from the same set of places. Search by name, filtering by category, filtering by tag and filtering to visited places are all supported. Nearby places are offered once, shortly after the map opens, and not offered again after a refusal.

A request may also be expressed as a sentence. The interpreter sets the filters and moves the map; it never adds places of its own, and a single action restores the previous state.

06 · Ownership, sharing and deletion

However many videos reference the same place, it is one pin. Each save retains its own link to the video it originated from, so the question of why a place was saved always has an answer.

A place may be marked Been or not yet. Places may be grouped into collections, and a collection shared by link, as an editor or as a viewer. The library is summarised by place, city and country count. All data may be deleted in one action.

5.4  Product-wide guarantees

  • Privacy is enforced at the data layer, not by each screen performing its own check. A map is private because the data itself refuses to be read by another account.
  • A caption is text to be read, never instructions to be followed. The text read belongs to a third party and is handled as untrusted input throughout.
  • Private fields remain private under sharing. Recipients see the places, their categories and the attribution of who added what — not the owner's note, tags, Been marks, or the video a place was saved from. The disclosure is specified in section 6.5.

Section 06

Core User Flows

Six core processes, in the order a user encounters them. Two are drawn, because their structure carries the argument.

01 · First session and initial library

The product has no value at zero saved places, so the first session has one objective: to end with places on the map.

  1. A visitor arrives at a page stating the product in three steps — paste a TikTok link, check what was found, it lands on the map — and stating the boundary of section 1.2 in the same place.
  2. The visitor creates an account. It is private from the first moment; there is nothing public to configure.
  3. An empty map is presented in a designed rather than blank state: one line of text, one button, and a camera already positioned over a sensible part of the world.

No checklist, progress meter, illustration or permission prompt is shown.

The single button adds a TikTok link, and the screen it opens carries real example videos for a user with none of their own to hand. The create menu, present on every tab, also offers addition by name for a user who does not require a video.

The acceptance condition for this flow is not comprehension. It is places on the map before the session ends, as stated in section 4.3.

02 · Import from a TikTok link

The primary flow, and the one the remainder of the product is built around.

The diagram states the structure. It does not state the timing, which constitutes most of the experience. The submitted post appears almost immediately — thumbnail, author handle and caption — and remains on screen while the slower work proceeds beneath it, so the interface presents content rather than a spinner.

Some links never leave the browser: a link that is not a TikTok video is identified locally and handed to addition by name before any request is issued.

Both terminal states drawn here are ordinary outcomes. The only genuine failure in this flow is a video the application cannot read at all, which is sufficiently rare to state in a sentence rather than draw.

The review step is where the design of section 5.1 group 04 takes effect. One card per place; confident matches pre-selected; uncertain ones offered as a short choice with nothing selected. Any of it may be edited, annotated or deselected, and nothing has been persisted at this point. Submitting the same link again returns the same result, so a retry is inexpensive.

The final node is the purpose of all the others: one pin per place, each retaining its link back to the post, held until a day that is usually weeks away.

03 · No places named, and addition by name

Not an error, and the screen this product displays most frequently. It distinguishes which of four conditions occurred, because they are not the same problem.

The caption named a city, not a venueThe same message, and the city narrows the search offered below it
Places found, none saveableA separate screen, stating what to do about it

Three routes forward, strongest first.

  • Addition by name. The user has watched the video, so entering the name and selecting it from the results completes in fewer steps than the flow just left.
  • A recollection in one sentence. Revealed on request and never presented as a standing form.
  • Opening the original video. Always available.

No route requests manual entry of the caption text, per the boundary in section 1.2.

Addition by name is also available independently, from the create menu on any tab. One field accepts either a link or a name, and the input determines the behaviour:

  • a TikTok link is handed to the flow in section 6.2;
  • an unsupported link falls through to addition by name;
  • a name already saved reveals that place on the map instead of saving it a second time;
  • a name not previously saved is looked up and saved in one step — and if the directory returns nothing, nothing is saved and the result is reported.

Reached from the no-places screen, where the user is recovering rather than certain, the behaviour differs: candidates are displayed for selection, and the resulting save is linked to the video that led there.

04 · Retrieval on the map

The return on everything above. It is listed fourth because it occurs on the second day, not because it ranks lowest.

This is the one flow that is not a sequence. The three tiers in the diagram are the same library rendered at three distances, and the transition between them is a pinch rather than a step. The map opens framed around the user's own places, so the first view is a region the user has been considering rather than a default point on the globe.

Two behaviours the diagram cannot express. Area pills are thinned during zoom so their names remain readable, and pin labels are permitted to overlap rather than disappear, because a crowded label is preferable to a pin that vanishes without notice.

Near me is genuinely optional: it is offered once, a refusal is remembered, distances are displayed only when the location fix is accurate enough to be meaningful, and the live location is never retained server-side.

Selecting a pin presents the whole record, including the video that prompted the save. The list beside the map is the other half of this surface, showing the same places under the same filters.

05 · Sharing a collection

A collection is the same map carrying a smaller set of pins, which is why sharing one did not convert this into a different product.

  1. The owner creates a collection, names it, and adds places from the library.
  2. The owner generates a link and selects whether the recipient joins as an editor or as a viewer. One live invite exists per collection; generating a new one explicitly retires the previous one.
  3. Before sharing, the owner is told plainly what the action entails — anyone holding the link who signs in can open this collection. One action opens the detail, behind a control that states what it opens, and it always presents both halves together: what the recipient will see, and what remains private.
  4. The recipient opens the link. Signed out, they receive an explanation before being asked to create an account; signed in, they are shown who invited them and what they will be able to do.
  5. Joining requests a display name first, because every other member of the collection will see it beside the places that person adds.
  6. Both parties then see the collection on their own map, and a viewer can copy a shared place into their own library.

06 · Deletion

A set of rules rather than a sequence.

Delete my data removes the account and its entire contents in one action. Deletion of a single place is separately available at any time.

Deletion is refused, with an explanation, where it would remove something belonging to other people. Where the account owns a collection containing other members, deletion halts and names those collections, with a route to resolve the situation. A refusal that states the next action is not a dead end.

One class of data survives, and the product states so: a note written inside another person's shared collection remains with that collection, with the author's name removed. No screen claims that everything the user wrote has been deleted.
