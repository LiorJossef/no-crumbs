Section 01 · where the code lives

System Layout and Component Hierarchy

The product is one Next.js application split into four source layers, and the rule that holds them apart is that domain may import nothing but itself.

Each layer has one job, and imports only ever point downward.

  • src/app/ is the only place Next.js appears. Pages, route handlers, server actions, and the server-only helpers under _lib/.
  • src/domain/ is plain TypeScript. URL classification, name scoring, plausibility, and deriving a place from a stored extraction — with no network, no database, no React and no vendor SDK.
  • src/integrations/ holds one adapter per external service. A vendor’s types die there.
  • src/components/ holds React, src/ui/ the framework-free logic behind it. So a rule like “which recovery does this error offer” is testable without a browser.

The rule is checked, not trusted

npm run check:layers writes deliberate violations into the tree and asserts the lint zones reject each one. It then searches src/domain/ for input and output independently, so silencing the lint rule does not open the door.

It also proves that every module in src/app/_lib/ imports server-only. That turns a leaked service key into a failed build rather than a review comment.

The payoff is concrete. The scoring benchmark runs in milliseconds because domain/places/score.ts cannot reach a network, and replacing the places provider was one new file in integrations/ and no change in domain/.

Pages, and the shell they live in

There are eleven pages: /, /sign-in, /import, /profile, /auth/reset, /auth/new-password, /collections, /collections/[id], /collections/join/[token], and /map, which is the shell.

/map is one route segment carrying three views — places, the collections index, and one open collection — addressed by ?view=collections and ?collection=<id>.

A segment change unmounts the outgoing subtree, and that used to take the drawer with it. Section 3 explains what stays mounted instead.

Three levels under /map

  • app/layout.tsx renders components/shell/persistent-map.tsx, which owns the map for the session.
  • app/map/page.tsx is a Server Component that authenticates and reads the library.
  • map-page-client.tsx owns selection and filters, and feeds three surfaces: the mobile sheet, the desktop panel and the pin layer.

Section 02 · link to place

The Extraction and Geo-Resolution Pipeline

A pasted link becomes places on a map in four steps: canonicalise the link, fetch the video, ask a language model to read the caption under a fixed schema, then match each name it found against a places provider.

The first step is identity, not content. The canonicaliser re-runs on the server: host allow-list, short links followed with that allow-list re-applied to every redirect, numeric video id extracted.

That id is the key everything hangs off, so the same video pasted twice is one source rather than a second import. The server then fetches the post through TikTok’s public oEmbed endpoint, which returns the caption, the author and a thumbnail.

We read captions only — never the audio, never text burned into the video. Many recommendation videos say the venue out loud and write nothing, so those posts yield nothing here.

We build around that rather than hide it: “no places found” is a designed screen, not an error.

Reading the caption

The caption goes to a language model under a versioned prompt that must answer in a shape we defined in code. We never parse prose, and never run a regular expression over a model reply.

  • The prompt is a plain constant in src/integrations/llm/prompt.ts, because a prompt that can change without a deploy is a prompt nobody can explain.
  • The shape is a schema in src/domain/extraction/schema.ts, which we turn into the JSON Schema that constrains the model at the API level.
  • Production runs Gemini. An Anthropic adapter ships beside it, selected by one environment variable.

What we ask for, and what we trust

What we ask for splits into four classes of claim, and that split is the most important idea in this section. Some fields must be copyable out of the caption. Some are the model’s reading of it. Some are its memory of the real world. One is its opinion of itself.

ClassFieldsWhat it means
Caption‑verbatimrawName, evidence, cityHint, countryHint, areaHint, addressHint, dishesCopied from the caption. A fabrication is a substring test, not a judgement call
Caption‑inferencecategoryHint, tags, whyGoThe model’s reading of the caption, which may not go beyond it
World knowledgeidentifiedName, coordinates, nameVariantsUnverified recall about the real world, checked only by a person
Model self‑reportmodelConfidenceKept so it can be measured; never trusted, never shown

The classification is enforced in code rather than described in a comment, because a convention erodes one field at a time. A constant names the class of every field, and a unit test fails if a new field arrives without one.

Two gates then make the verbatim classes real, and both turn trusting the model into a string search:

  • One drops any candidate whose supporting quote is not in the caption.
  • The other erases the model’s one-line reason when the fragment it cites cannot be found.

That same gate is where obvious non-places die before they cost anything: links, bare usernames, names that are only a city or a country, generic phrases like “this hidden gem”, and duplicates.

Weak-but-real cases are kept deliberately — a venue named only in a hashtag, for instance — with confidence capped and the review screen saying so.

Two caps bound the work. The schema refuses more than twelve candidates, so a model that turns thirty hashtags into places fails validation instead of flooding the pipeline. Eight is the most that are looked up, and anything past that is kept and marked as one we did not check.

Turning a name into a place

Resolution asks a places provider what each surviving name really is. The query is composed from the caption’s name, its city, country and address hints, plus the model’s alternative spellings — which is how a Hebrew caption reaches a venue indexed under its English name.

Results are scored on name similarity, category agreement and dataset confidence, then banded:

  • A clear winner is pre-selected on the review screen.
  • A plausible but unseparated set becomes a shortlist the user picks from.
  • Everything else is no match.

The gate doing most of the work is the margin between the top result and the runner-up. Matching many rows equally well is what a caption naming no venue looks like.

When nothing matches

We neither invent a coordinate nor discard the place. The candidate is saved with the model’s own coordinate, carrying no resolution score, and the card says the pin is approximate and links out to a public map for a person to verify.

Its identity is derived from the caption’s verbatim name, so re-pasting converges on one row rather than growing the library. Only when the resolver found nothing and the model gave no coordinate is the candidate skipped, rather than pinned to a city centre.

Two caches, and why they exist

An extraction is stored under the source, the model and the prompt version together, so re-pasting a link costs no model call. Provider replies are cached below the ranking step.

Cost is the lesser reason. The model is not deterministic, so without the cache the same link produced different places on a second run, under different names and coordinates. That key is what makes an import repeatable.

Why the vendors sit behind a port

Neither the model nor the places provider is called directly from the pipeline. Both sit behind a port — a small interface the domain owns, listing only what it needs — with an adapter per vendor behind it, chosen in one factory.

No vendor type crosses that line. That bought us three things:

  • Fakes instead of a network in tests.
  • A second model as a second file, rather than a rewrite.
  • One place to change provider when licence terms require it.

Section 03 · what lives where

Interactive Map Architecture and Application State

There is no client state library. Every kind of state has one home, chosen by whether it must survive a refresh, a navigation, or neither.

Every kind of state has one home

Kind of stateWhere it livesWhy there
Persisted dataRead on the server, in app/map/page.tsxMust survive a refresh, and the database already knows who may see it
What you are looking atURL search parametersMust survive a navigation and be shareable
Everything transientLocal state in the component that owns itNeeds to survive neither

Persisted data is read on the server. app/map/page.tsx calls _lib/get-spots.ts, which queries saved_places joined to places and sources through the caller’s own client, then passes plain objects into the client tree. No component fetches its own data on mount.

That query carries no user filter on purpose. Row-level security already scopes all three tables, and a second filter in TypeScript would be one rule with two definitions.

State that addresses what you are looking at lives in the URL. Search parameters are not part of the router’s segment cache key, while a dynamic segment’s value is — which is why /collections/[id] remounted the drawer and ?collection= does not. Both old routes survive as redirects, so no shared link stops working.

Everything transient stays in the component that owns it. Selection, search text, active tag and the not-been-yet filter are local state in map-page-client.tsx, and the import run is a union of screens driven only by real server responses.

A mutation ends by revalidating /map. The server stays authoritative, and there is no client cache to keep in sync.

One map, for the whole session

One MapLibre instance exists for the session, and it survives navigation because React never unmounts it. MapLibre has no way to hand a live map to a freshly mounted component, and the only ancestor common to every map-bearing route is the root layout.

So components/shell/persistent-map.tsx renders the surface once, through a React portal, into a detached container it owns. Each route’s shell borrows that container by appending it into its own anchor.

React never reads a portal container’s position, so moving the node moves the canvas and its live graphics context undisturbed. Before this, every tab-to-tab hop built a new map.

The list and the pins cannot disagree

Filtering happens once. Tag, visit state and search text are applied in one place, and the single filtered array goes to the sheet, the desktop panel and the marker layer. There is no second code path that could narrow one and not the others.

Section 04 · what we remember

Database Design and Core CRUD Operations

Everything the product remembers lives in one Postgres database, and its shape follows from one distinction: a place in the world is not the same thing as one person’s decision to keep it.

TableWho it belongs toWhat one row is
profilesone useran account, paired one-to-one with the auth user
sourceseveryoneone TikTok video — its numeric id, canonical URL, author and caption
importsone userone paste: its status, its timings, and the candidates awaiting review
placeseveryoneone physical venue — name, category, latitude and longitude
place_provider_refseveryoneone provider’s id for a venue; many may point at one place
saved_placesone userthat person’s entry for a place: their name for it, note, tags, visited state
saved_place_sourcesone userwhich video recommended which save
collections and friendsseveral usersa shared list, with an owner, editors and viewers

Why a place and a save are different rows

This is the most important decision in the model. places is the shared, de-duplicated record of somewhere real. saved_places is one person’s private entry pointing at it.

One physical venue is therefore one row, no matter how many videos point at it. Three TikToks recommending the same bakery produce one place, one save for me, and three links back to the videos.

The separation also decides where an edit lands. Renaming a place writes to your row and never the shared one, so nobody can edit the map out from under anyone else. A unique constraint on the pair of user and place makes saving the same place twice impossible rather than merely unlikely.

The core operations

  • Saving places from a TikTok — POST /api/imports/confirm, which calls resolve_place() to find or create the shared place, then save_place() once per confirmed candidate.
  • Adding a place by hand — the addPlaceManually server action, down the same two functions, with no source attached.
  • Reading the map or the list — one query joining saved_places to places.
  • Editing a name, category, note or visited state — a server action performing a plain update on the user’s own row.
  • Deleting a save — removes that row and its provenance links, while the shared place survives for everyone else. Deleting an account cascades from profiles.

Integrity, enforced where it cannot be bypassed

  • Nothing is written to places before the user taps confirm. Until then candidates sit as JSON on the import row.
  • De-duplication is a unique constraint on the provider’s own identifier, plus a 75-metre same-name guard inside resolve_place().
  • A deferred trigger refuses to leave a place without at least one provider reference.

Section 05 · how data moves

API Routes and Data Flow

Eight route handlers and seven server-action modules. A request becomes a route handler only when it needs elevated access or a slow external call; everything else is a server action or a plain read on the server.

RouteMethodWhat it does
/api/imports/source-previewPOSTFetches the video through oEmbed, so the thumbnail, handle and caption are on screen in about a second
/api/imports/probePOSTThe rest of the pipeline in one request: caption, extraction, resolution, and the writes that record them
/api/imports/confirmPOSTTurns the reviewed selections into shared places and the user’s own saves
/api/imports/place-searchPOSTSearch-and-add a place by name, from the no-places screen
/api/search/interpretPOSTTurns a typed sentence into filter values. Returns no places and writes nothing
/api/sources/thumbnailPOSTRe-fetches a thumbnail whose signed URL expired
/auth/callbackGETExchanges an auth code for a session
/healthzGETLiveness, revealing no configuration

Everything else is a server action

Server actions cover every ordinary mutation of the user’s own rows: saved places (delete, rename, re-categorise, note, visited), manual add, collections, profile, account and sign-out.

Each one does the same four things:

  • Validates its input before anything else runs.
  • Identifies the user.
  • Writes through that user’s own client, so the database makes the authorisation decision.
  • Revalidates the narrowest correct path.

There is no REST layer over our own database. Row-level security is already the authorisation layer, and a hand-written CRUD API would be a second place for the same rules to drift.

One request, followed all the way down

Confirm is the request to follow, because it is where the trust boundary sits. The browser sends an extraction id and, per item, two integers and an optional note — and no place facts at all.

The route then parses that body against a schema, and authorises the extraction through the user’s client by requiring them to own an import row for its source. The database makes the check, rather than an if.

It re-parses the stored candidates out of the database and hands the named index to the domain, which derives name, coordinates, category and country from the row the server itself wrote.

Two Postgres functions then run:

  • resolve_place(), under the service role. The only path that can create a shared place.
  • save_place(), under the user’s own session. It can only write their own library row.

That shape closes a confirmed exploit. When the browser sent the place itself, the resolve step refreshed provider-owned columns on the matched row — so one user could rename and relocate a venue other people had saved.

Section 06 · when things go wrong

Input Validation and Error Handling

Everything from outside is parsed at the boundary it arrives at, and everything that can go wrong is one of thirteen error codes carrying no provider text.

The URL is checked twice, and only the second check counts

The canonicaliser runs in the browser as the user types, so an unsupported link becomes a recognised redirect to manual add before any request is made.

The same pure function runs again inside the routes that fetch, and that call is the gate against server-side request forgery. The host must be exactly one of a closed list of TikTok hosts, by full-string equality rather than suffix match, so tiktok.com.evil.io and nottiktok.com both fail. It is re-applied to every redirect when a short link is followed.

The browser check is a courtesy; the check on the server about to make the network call is the control.

Four kinds of untrusted input, parsed at their boundary

  • The oEmbed payload. Deliberately tolerant of new fields, so TikTok adding one cannot break us — while removing the title still does.
  • The model’s output. A failure becomes a named error rather than a thrown exception.
  • The confirm request body.
  • JSON read back out of our own database, because the code that wrote it may be an older deploy.

Server actions validate through pure functions that return the message the form should show.

Thirteen ways to fail, and no more

The error code is a closed union of thirteen members, and the wire format carries a code and two booleans — no message, no status, no stack, no vendor string.

Each code has exactly one constructor, with its retryable value baked in, so no call site can claim a code is retryable when the taxonomy says otherwise. Adapters catch every vendor exception and construct one of these instead.

Each code also maps to a status that says whose fault it was.

FailureStatusWhy that status
The video has no caption422We read the video perfectly, and it has none
Model quota exhausted503Not a 429: we are the one who ran out
Internal500The only code that may be a 500, which is what keeps a 500 in the logs meaningful

User-facing copy lives on the client as a total record over that union, so a fourteenth code is a compile error rather than a silent regression to one apologetic screen.

Each entry names its recovery actions, and a test asserts none is ever empty. No failure screen is a dead end.

“No places found” is deliberately not an error

It is a successful outcome with its own screen, because it is the usual result — creators name venues on screen and in speech, not in captions.

Modelling the commonest outcome as a failure would poison every log built on the taxonomy.
