# RECOG-METRICS-1 — the recognition scoreboard, the failure classes, and the picker ruling

**2026-08-28.** Measured entirely by **replay from disk**: zero Google Text Search requests, zero
network, zero database. The owner's ~100-TikTok production dataset keeps the whole 100/day quota.

Two commands regenerate every number in this file, in any order:

```bash
npx vitest run tests/manual/recognition-scoreboard.manual.ts \
  --config tests/manual/vitest.manual.config.ts --reporter=verbose --disable-console-intercept

npx vitest run tests/manual/recognition-failure-classes.manual.ts \
  --config tests/manual/vitest.manual.config.ts --reporter=verbose --disable-console-intercept
```

Machine records: `recognition-scoreboard-run.json`, `recognition-failure-classes-run.json`.
Query variants used by the replay: `recognition-query-variants.json`, regenerated by
`node tests/manual/recognition-variants-from-cache.mjs`.

**On what those three files carry.** The variants file is extractor output only — no provider
content. The two run records carry Google display names and street lines but **no coordinates**,
which is strictly less Places content than `tiktok-recognition-run.google.json` already holds in the
repository. Google's Service Specific Terms §5.4 caps caching of Places content at 30 consecutive
days; that clock is on the source record, and these are derived from it.

## 1. Part 1 — the scoreboard

Denominator throughout is the **adjudicated candidate**: an extracted candidate paired to a corpus
expectation, plus every expectation that no candidate matched. An extraction miss is a recognition
failure the user experiences as one, so it is counted, never dropped. 13 URLs, 16 adjudicated
candidates per provider.

| | **Google** (canonical) | Overture (legacy) |
|---|---|---|
| **correct top-1** — the right venue is rank 1 | **15/16 · 94%** | 12/16 · 75% |
| **auto-resolution** — `preselect` **and** correct | **11/16 · 69%** | 9/16 · 56% |
| **genuine ambiguity** — we asked and could not have known | **0/16 · 0%** | **0/16 · 0%** |
| **wrong auto-match** — `preselect` and wrong | **0/16 · 0%** | **0/16 · 0%** |
| needless questions — we asked and the answer was already ours | 4/16 · 25% | 3/16 · 19% |
| not found / ranking failures | 0 / 0 | 3 / 0 |
| extraction misses | 1 | 1 |

**The 7/16 (44%) figure in the brief is corrected to 11/16 (69%) on Google and 9/16 (56%) on
Overture.** Zero false auto-accepts is confirmed on both, under the shipped policy and under every
variant measured in §4 and §5.

### 1.1 The definitions, stated so they can be argued with

- **correct top-1** — the adjudicated-correct venue is rank 1 of the ranking, by the corpus's own
  `namePattern` / `addressPattern` rules (`acceptsRow`, the same predicate the real harness uses).
- **auto-resolution rate** — band is `preselect` **and** the top-1 is correct. Reported beside the
  raw `preselect` count so the two can never be conflated; on this corpus they are equal, because
  there are no wrong auto-accepts.
- **genuine ambiguity rate** — we asked, and no evidence we already held answered the question.
  Mechanically: not `preselect`, and there exists a contender within `branchGuard.rivalScoreBand`
  such that **(a)** the name does not separate it from the top-1 — either it is branch-shaped
  (`nameDifference !== null`, where the gap measures suffix length rather than which branch) or its
  name score is within 0.02 of the top's — **and (b)** the caption's own address does not separate
  them either. Deliberately conservative in the direction that makes the product look worse:
  anything not provably answerable is counted as genuine.
- **needless question** — we asked and it was not genuine. Includes, and is dominated by, *"the
  user's pick was rank 1 anyway"*.
- **wrong-auto-match rate** — `preselect` and not correct. Both harnesses assert it is zero and
  fail if it is not.

### 1.1b Zero genuine ambiguity is a claim about this corpus, not about the product

**Every question the resolver asks on these 13 captions is one it could have answered.** That is the
owner's thesis, measured. It is not a claim that genuine ambiguity does not exist: on the 44-case
golden benchmark the branch guard fires on **eleven** cases (TYO-02, TYO-04, TYO-07, TYO-09, TYO-10,
TYO-14, LDN-02, LDN-03, LDN-07, LDN-12, LDN-13) and those *are* genuine branch questions — bare
chain names with siblings kilometres away and a caption that names none of them. This corpus simply
contains one branch question (`רוסטיקו` on Overture) and the caption answered it in writing.

### 1.2 Two honesty notes on the numerator

- **`רוסטיקו` on Google counts as correct top-1 and arguably should not.** The caption says
  `בזל 42`; Google returned `רוסטיקו רוטשילד @ Rothschild 15`, 3.1 km away. The corpus expectation
  is `addressPattern: "בזל|רוטשילד"`, so it accepts either branch. Under a branch-strict reading
  Google's correct top-1 is 14/16 (88%), not 15/16.
- **`מתחת לעץ` is a three-branch caption** (`נתן אלתרמן 13 / לבונטין 13 / בן יהודה 202`). The
  extraction produced one candidate with `addressHint: null`; Google returned one branch. The corpus
  accepts any branch, so it scores as correct. The branch information was in the caption and was
  discarded before the resolver ever saw it — that is class **C6** below.

### 1.3 Fidelity of the replay, and what it cannot see

- **Verified against an independent number.** The 44-case golden re-simulation this file uses lands
  on **24 preselect / 20 not**, which is exactly what `tests/unit/places/benchmark-golden.test.ts`
  asserts today. The replay is not a private arithmetic.
- **Verified per row.** The Overture record stores each row's `nameScore`; recomputing it with
  today's primitives drifts by **0.000 on all 16 candidates**, so no row in this corpus matched
  through an `altNames` entry the record does not keep.
- **Google rivals are reconstructed name-only.** Rank 1 is recorded in full; ranks 2+ exist for only
  two of sixteen candidates (`טרטוריה אונה`, `WOW`) and only as `"name (score)"` strings, so their
  address is treated as absent and their geometry is unknown. The suite asserts the one thing that
  makes that harmless: `nameDifference(top, rival) === null` for every synthesised rival, so the
  branch guard fails on names and never reaches the distance test.
- **Overture rankings are a 10-row window** onto prefilters of up to 402 rows. Flagged per candidate.

**Classes the brief listed that the data does not support, and why:**

- *"the scorer's category term (TLV-14)"* — **gone**. `SCORING.total.category` is 0 since
  RESOLVE-CONF-1; TLV-14's top-1 is `Bar 51`, the venue the case asks for, and it auto-accepts.
- *"`datasetConfidence` 0.5 pinning absolute score below the band gate"* — **gone**, same change.
  Measured directly in §5: dropping it from the *old* blend moves the Google auto-accept count by
  **zero**, because a constant cannot rank anything. Setting the weight to 0 is what moved it.
- *"a lone Google result with null margin"* — **already solved** by `'exhaustive-search'`. It is
  worth 10 of the 11 Google auto-accepts; see §4.
- *"two branches of one chain at one address"* — did not occur in this corpus. The one same-address
  pair (`Kohi Coffee Shop` / `NIKO by Sharon Cohen`, 29 m apart on Overture, both at `בן יהודה 155`)
  is *two different venues* at one address, and the shipped guard correctly declines to ask about
  it: the names do not contain one another, so it is not branch-shaped, and 0.946 against 0.587 is
  not a close call. That pair is the specimen the whole picker ruling was raised about — see §5.
- *"address evidence discarded across writing systems"* — occurs, but not as a scoring failure here:
  `Rustico Rothschild`'s address is Latin (`Rothschild Boulevard 15`) against a Hebrew caption, so
  `addressScore` returns `null` rather than 0. On this corpus it costs nothing, because the top-1's
  address corroborated. It remains a real gap (`06` §7.1) and it is why **F2** tests the *top-1's*
  corroboration rather than the rival's contradiction.

## 3. The three fixes, measured on three corpora

Each is a band policy applied on top of the shipped ranking. **Nothing in `score.ts` or
`scoring-constants.ts` was modified to produce these numbers.**

The bar is the one two previous band proposals died on — one false auto-accept on the 44 golden
cases (`band-policy.md` on TLV-14, `dataset-confidence-weighting-2026-08-28.md` on TYO-10).

| fix | what it says | google | overture | golden-44 | wrong auto-matches |
|---|---|---|---|---|---|
| **F1** | A pure suffix is not a mismatch. When token coverage is 1.000, the query's tokens are wholly contained in the name, the score clears `confirmScore`, the margin gate passes and the branch guard is silent → `preselect` | **+2 of 4** (`מתחת לעץ`, `קוהי`) | +0 of 6 | +0 of 20 | **0** |
| **F2** | The caption's own street address is decisive. When `addressScore(hint, top) === 1` (same street **and** same house number), token coverage is 1.000, and no contender corroborates the same address, → `preselect`, waiving the score gate, the null-margin block **and** the branch guard | **+1 of 4** (`קוהי`) | **+2 of 6** (`רוסטיקו`, `WOW`) | +0 of 20 *(untestable)* | **0** |
| **F3** | An exact name is not a close call. When the top-1's name score is 1.000 with full coverage, the runner-up is not branch-shaped and is more than 0.02 below on name, and the guard is silent → waive the **margin** gate only | +0 of 4 | **+1 of 6** (`Palette Bistro`) | +0 of 20 | **0** |
| **all three** | | **11/16 → 13/16 (81%)** | **9/16 → 12/16 (75%)** | **0 cases move** | **0** |

### 3.1 What the golden file can and cannot say about these

**It says nothing, and that is a finding, not a pass.** Of its 20 non-`preselect` cases:

- **none** has a top-1 whose name properly contains the query — every golden query is the venue's
  own bare name — so **F1 is untestable there**;
- `raw-overture-scored.json` records no `addressLine` at all, so **F2 is arithmetically a no-op
  there**;
- **F3 is exercised and correctly declines** on all three of its candidate shapes: TYO-07
  (`Afuri`/`AFURI`), TYO-09 (`猿田彦珈琲` twice) and LDN-13 (`The Dove` twice) all have margin 0.000
  with an *equal* name score, which is exactly the "two rows, one name" case F3 refuses to touch.

So F1 and F2 are supported by the real corpus and **unrefuted rather than proven** by the synthetic
one. That asymmetry is the reason to fill the Google replay cache (§6) before shipping either.

### 3.2 The risk in F1, named

F1's failure mode is the branch guard's own known gap: two **sibling** branches (`X 銀座店` versus
`X 日本橋店`) satisfy neither name's containment of the other, so `branchRival` returns `null` and F1
would auto-accept whichever ranked first. On this corpus that shape never occurs *with a rival* —
`מתחת לעץ` and `קוהי` both return exactly one result. But `מתחת לעץ` is a caption that names **three**
branches, and F1 would auto-accept one of them silently. If F1 ships, it should ship with the
extraction fix for C6 (carry the caption's branch list) or with F1 restricted to the case where the
suffix is a **descriptor** rather than a place name — which we cannot currently tell apart.

**Ranked recommendation.** F2 first: it is the largest recovery (3 candidates across both
providers), it is the only one that makes the product *use* evidence it already collects, and it
makes the branch guard smarter rather than looser. F3 second: one candidate, smallest blast radius,
declines correctly everywhere it is tested. F1 third and not alone: two candidates, but it is the
one that can auto-accept an arbitrary branch.

## 4. Part 3a — the lone candidate

Google's Text Search returns exactly one result for **14 of 16** corpus candidates, so `margin` is
`null` almost always. `'exhaustive-search'` waives **only** the unmeasurable-margin block; the score
gate is untouched and a margin that exists must still clear it.

| provider | `soleCandidateMeaning` | auto-resolution | **wrong auto-match** | needless questions | genuine ambiguity |
|---|---|---|---|---|---|
| google | `narrow-filter` | 1/16 (6%) | **0** | 14 | 0 |
| google | `exhaustive-search` **(shipped)** | **11/16 (69%)** | **0** | 4 | 0 |
| overture | `narrow-filter` **(shipped)** | 9/16 (56%) | **0** | 3 | 0 |
| overture | `exhaustive-search` | 10/16 (63%) | **0** | 2 | 0 |

**Recommendation — keep `'exhaustive-search'` on Google exactly as shipped.** It is worth **ten of
the eleven** Google auto-accepts and costs zero wrong ones. Without it the Google path's
auto-resolution rate is structurally 6%.

**Recommendation — do NOT extend it to Overture.** It gains one candidate (`WOW`) at zero measured
cost, but the two `1` values mean different things: Google's means *a global index holds one place
under that name near that city*, Overture's means *our cheap trigram prefilter matched one row*, and
the second is a statement about our SQL. That one candidate is recovered by **F2** instead, on
evidence — `WOW`'s caption wrote `בית אשל 15` and the row is at `בית אשל 15` — which is the same win
for a reason that generalises.

## 6. What could not be measured from replay alone

1. **Any change to *retrieval*.** The replay fixes the provider's answer. C3's real fix — a second
   Text Search that includes the caption's address, to find the `בזל 42` branch of `רוסטיקו` — is
   invisible to it, and so is any change to `buildTextQuery`, `languageCodeFor` or
   `MAX_GOOGLE_RESULTS`. That needs live calls.
2. **Google rivals for 14 of 16 candidates.** The record stores one row for them. If any of those
   answers actually had a second result that the 07:52 top-3 rendering dropped, this replay cannot
   see it. (`candidatesPrefiltered` says 1, so it probably did not — but that field is the same
   record.)
3. **`altNames` on Overture rows.** Not recorded. Zero drift on this corpus means no row needed one;
   it does not mean the alias path is unexercised in general.
4. **Whether the 07:52 Google answers still hold.** They are a month-old snapshot of a live index,
   and Google's SST §5.4 caps caching of that content at 30 days regardless.
5. **The corpus is 13 URLs against the owner's brief of 20–30, with `bars_and_wine_bars`
   unrepresented.** Every rate here is a pilot at n=16. Two candidates decide 12 percentage points.
6. **Nothing was verified in the running app.** These are offline numbers about the resolver, not
   about the review screen that renders them.

**The one action that removes limits 1 and 2 cheaply:** run the real harness once against Google
with `RECOGNITION_REFRESH` unset. It spends 16 of the 100 daily requests **once**, fills
`docs/evidence/.local/tiktok-recognition-cache/` with `google-*.json`, and every subsequent
scoring, band or guard experiment is free. That is what commit `7d96489` built the seam for, and the
cache is currently empty. It is a spend decision, so it is the owner's.
