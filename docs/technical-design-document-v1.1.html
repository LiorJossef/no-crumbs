Technical Design

Abstract. This document describes the implemented design of the No Crumbs system: a single Next.js application divided into four source layers. It states the layering rule and the mechanism that enforces it, the stages by which a pasted link becomes a set of candidate places, the placement of application state and the lifetime of the map instance, the relational model and its core operations, the route and server-action inventory, and the validation boundaries and closed error taxonomy. Each section describes the system as deployed rather than as planned.

Section 01

System Layout and Component Hierarchy

The product is a single Next.js application divided into four source layers. The governing constraint is that src/domain/ may import nothing outside itself.

1.1  Source layers

Each layer has one responsibility, and import edges point in one direction only.

LayerContentsConstraint
src/app/Pages, route handlers, server actions, and the server-only helpers under _lib/The only layer in which Next.js appears
src/domain/URL classification, name scoring, plausibility assessment, and derivation of a place from a stored extractionPlain TypeScript: no network, no database, no React, no vendor SDK
src/integrations/One adapter per external serviceA vendor’s types terminate here
src/components/ and src/ui/React components, and the framework-free logic behind themRules such as which recovery a given error offers are testable without a browser

1.2  Enforcement of the layering rule

npm run check:layers writes deliberate violations into the tree and asserts that the lint zones reject each one. It then searches src/domain/ for input and output independently, so suppressing the lint rule does not defeat the check.

The same command asserts that every module in src/app/_lib/ imports server-only. A leaked service key therefore fails the build rather than depending on review.

Two consequences are measurable. The scoring benchmark executes in milliseconds because domain/places/score.ts cannot reach a network, and replacing the places provider required one new file in integrations/ and no change in domain/. The port and adapter arrangement that permits this is described in section 2.8.

1.3  Route inventory

The application exposes eleven pages: /, /sign-in, /import, /profile, /account, /auth/reset, /auth/new-password, /collections, /collections/[id], /collections/join/[token], and /map, which acts as the shell.

/map is a single route segment carrying three views — places, the collections index, and one open collection — addressed by the search parameters ?view=collections and ?collection=<id>.

A segment change unmounts the outgoing subtree, which formerly unmounted the drawer with it. The arrangement that keeps the map mounted across such a change is described in section 3.4.

1.4  Component hierarchy beneath /map

ModuleKindResponsibility
app/layout.tsxRoot layoutRenders components/shell/persistent-map.tsx, which owns the map for the session
app/map/page.tsxServer ComponentAuthenticates the request and reads the library
map-page-client.tsxClient ComponentOwns selection and filters, and feeds the mobile sheet, the desktop panel and the pin layer

Section 02

The Extraction and Geo-Resolution Pipeline

A pasted link becomes places on a map in four stages: canonicalisation of the link, retrieval of the post, extraction of candidate names from the caption by a language model under a fixed schema, and resolution of each name against a places provider.

2.1  Link canonicalisation and source retrieval

The first stage establishes identity rather than content. The canonicaliser re-runs on the server: the host is checked against an allow-list, short links are followed with that allow-list re-applied to every redirect, and the numeric video identifier is extracted. The security properties of this stage are stated in section 6.1.

That identifier is the key on which the remainder depends, so the same video pasted twice yields one source rather than a second import. The server then retrieves the post through TikTok’s public oEmbed endpoint, which returns the caption, the author and a thumbnail.

Captions are the only input read. Neither the audio track nor text burned into the video is processed. Many recommendation videos state the venue in speech and write nothing, and such posts therefore yield no candidates.

This outcome is treated as a designed result rather than an error condition; section 6.5 states the reasoning.

2.2  Caption extraction

The caption is submitted to a language model under a versioned prompt, and the model must answer in a shape defined in code. No prose is parsed and no regular expression is applied to a model reply.

ElementLocationProperty
Promptsrc/integrations/llm/prompt.tsA plain constant, so it cannot change without a deploy
Output shapesrc/domain/extraction/schema.tsConverted into the JSON Schema that constrains the model at the API level
ProviderGemini in production; an Anthropic adapter beside itSelected by one environment variable

2.3  Classification of extracted fields

The requested fields divide into four classes of claim. Some fields must be copyable out of the caption; some are the model’s reading of the caption; some are its recall of the world; one is its assessment of itself. The distinction determines how each field may subsequently be used.

ClassFieldsWhat it means
Caption‑verbatimrawName, evidence, cityHint, countryHint, areaHint, addressHint, dishesCopied from the caption. A fabrication is a substring test, not a judgement call
Caption‑inferencecategoryHint, tags, whyGoThe model’s reading of the caption, which may not go beyond it
World knowledgeidentifiedName, coordinates, nameVariantsUnverified recall about the real world, checked only by a person
Model self‑reportmodelConfidenceKept so it can be measured; never trusted, never shown

The classification is enforced in code rather than stated in a comment, since a convention erodes one field at a time. A constant names the class of every field, and a unit test fails if a new field arrives without one.

2.4  Verbatim gates and candidate rejection

Two gates make the verbatim classes of section 2.3 effective, and both reduce trust in the model to a string search. The first drops any candidate whose supporting quote does not appear in the caption. The second erases the model’s one-line reason when the fragment it cites cannot be found.

The same gate rejects obvious non-places before they incur cost: links, bare usernames, names that denote only a city or a country, generic phrases such as “this hidden gem”, and duplicates.

Weak but genuine cases are retained deliberately — a venue named only in a hashtag, for example — with confidence capped and the review screen stating the limitation.

Two caps bound the work. The schema refuses more than twelve candidates, so a model that converts thirty hashtags into places fails validation instead of flooding the pipeline. Eight is the maximum number looked up; candidates beyond that limit are retained and marked as unchecked.

2.5  Place resolution

Resolution asks a places provider to identify each surviving name. The query is composed from the caption’s name, its city, country and address hints, and the model’s alternative spellings, which is the mechanism by which a Hebrew caption reaches a venue indexed under its English name.

Results are scored on name similarity, category agreement and dataset confidence, and then banded.

BandBehaviour on the review screen
A clear winnerPre-selected
A plausible but unseparated setPresented as a shortlist for the user to choose from
Everything elseRecorded as no match

The decisive quantity is the margin between the top result and the runner-up. A caption that names no venue characteristically matches many rows equally well.

2.6  Unresolved candidates

Where nothing matches, no coordinate is invented and the candidate is not discarded. It is saved with the model’s own coordinate, carries no resolution score, and its card states that the pin is approximate and links out to a public map for verification by a person.

Its identity is derived from the caption’s verbatim name, so re-pasting converges on one row rather than growing the library. A candidate is skipped only when the resolver found nothing and the model supplied no coordinate; it is not pinned to a city centre.

2.7  Extraction and lookup caches

An extraction is stored under the source, the model and the prompt version together, so re-pasting a link incurs no model call. Provider replies are cached below the ranking step.

Cost is the secondary motivation. The model is not deterministic, so in the absence of the cache the same link produced different places on a second run, under different names and coordinates. The cache key is what makes an import repeatable.

2.8  Port and adapter boundary

Neither the model nor the places provider is called directly from the pipeline. Both sit behind a port — a small interface owned by the domain, listing only what the domain requires — with one adapter per vendor behind it, selected in a single factory. No vendor type crosses that boundary, which is the layering rule of section 1.1 applied to external services.

Three consequences follow.

  • Tests substitute fakes for the network.
  • A second model is a second file rather than a rewrite.
  • A provider change required by licence terms is confined to one location.

Section 03

Interactive Map Architecture and Application State

No client state library is used. Each kind of state has one location, selected according to whether it must survive a refresh, a navigation, or neither.

3.1  State placement

Kind of stateWhere it livesWhy there
Persisted dataRead on the server, in app/map/page.tsxMust survive a refresh, and the database already holds the visibility rules
The current viewURL search parametersMust survive a navigation and be shareable
Transient stateLocal state in the component that owns itNeeds to survive neither

3.2  Server-side data access

Persisted data is read on the server. app/map/page.tsx calls _lib/get-spots.ts, which queries saved_places joined to places and sources — the tables described in section 4.1 — through the caller’s own client, and passes plain objects into the client tree. No component fetches its own data on mount.

That query carries no user filter, by design. Row-level security already scopes all three tables, and a second filter expressed in TypeScript would give one rule two definitions.

3.3  URL-addressed view state

State that addresses the current view is held in the URL. Search parameters are not part of the router’s segment cache key, whereas a dynamic segment’s value is; this is why /collections/[id] remounted the drawer and ?collection= does not. Both former routes are retained as redirects, so no previously shared link ceases to work.

Transient state remains in the component that owns it. Selection, search text, the active tag and the not-visited filter are local state in map-page-client.tsx, and the import run is a union of screens driven only by real server responses.

A mutation ends by revalidating /map. The server remains authoritative and no client cache requires synchronisation.

3.4  Persistent map instance

One MapLibre instance exists for the session and survives navigation because React never unmounts it. MapLibre provides no means of handing a live map to a freshly mounted component, and the only ancestor common to every map-bearing route is the root layout.

Accordingly components/shell/persistent-map.tsx renders the surface once, through a React portal, into a detached container that it owns. Each route’s shell borrows that container by appending it to its own anchor.

React never reads a portal container’s position, so moving the node moves the canvas and its live graphics context undisturbed. Before this arrangement, every tab-to-tab navigation constructed a new map.

3.5  Single filter path

Filtering occurs once. Tag, visit state and search text are applied in one location, and the single filtered array is supplied to the sheet, the desktop panel and the marker layer. No second code path exists that could narrow one surface and not the others.

Section 04

Database Design and Core CRUD Operations

All persisted state is held in one Postgres database. Its shape follows from a single distinction: a place in the world is not the same entity as one person’s decision to keep it.

4.1  Table inventory

TableWho it belongs toWhat one row is
profilesone useran account, paired one-to-one with the auth user
sourceseveryoneone TikTok video — its numeric id, canonical URL, author and caption
importsone userone paste: its status, its timings, and the candidates awaiting review
placeseveryoneone physical venue — name, category, latitude and longitude
place_provider_refseveryoneone provider’s id for a venue; many may point at one place
saved_placesone userthat person’s entry for a place: their name for it, note, tags, visited state
saved_place_sourcesone userwhich video recommended which save
collections and friendsseveral usersa shared list, with an owner, editors and viewers

4.2  Separation of place and save

This is the principal decision in the model. places is the shared, de-duplicated record of a real location. saved_places is one person’s private entry pointing at it.

One physical venue is therefore one row, irrespective of how many videos refer to it. Three TikToks recommending the same bakery produce one place, one save for the user, and three links back to the videos.

The separation also determines where an edit lands. Renaming a place writes to the user’s own row and never to the shared one, so no user can alter the map beneath another. A unique constraint on the pair of user and place makes saving the same place twice impossible rather than merely unlikely.

4.3  Core operations

OperationMechanism
Save places from a TikTokPOST /api/imports/confirm, which calls resolve_place() to find or create the shared place, then save_place() once per confirmed candidate. The full request path is traced in section 5.3
Add a place by handThe addPlaceManually server action, through the same two functions, with no source attached
Read the map or the listOne query joining saved_places to places
Edit a name, category, note or visited stateA server action performing a plain update on the user’s own row
Delete a saveRemoves that row and its provenance links; the shared place survives for other users. Deleting an account cascades from profiles

4.4  Integrity constraints

RuleEnforcement
Nothing is written to places before the user confirmsUntil confirmation, candidates are held as JSON on the import row
De-duplication of venuesA unique constraint on the provider’s own identifier, plus a 75-metre same-name guard inside resolve_place()
A place must have at least one provider referenceA deferred trigger refuses any transaction that would leave one without

Section 05

API Routes and Data Flow

The application exposes eight route handlers and seven server-action modules. A request becomes a route handler only where it requires elevated access or a slow external call; all other work is a server action or a plain read on the server.

5.1  Route inventory

RouteMethodWhat it does
/api/imports/source-previewPOSTFetches the video through oEmbed, so the thumbnail, handle and caption are on screen in about a second
/api/imports/probePOSTThe remainder of the pipeline in one request: caption, extraction, resolution, and the writes that record them
/api/imports/confirmPOSTTurns the reviewed selections into shared places and the user’s own saves
/api/imports/place-searchPOSTSearch-and-add a place by name, from the no-places screen
/api/search/interpretPOSTTurns a typed sentence into filter values. Returns no places and writes nothing
/api/sources/thumbnailPOSTRe-fetches a thumbnail whose signed URL expired
/auth/callbackGETExchanges an auth code for a session
/healthzGETLiveness, revealing no configuration

5.2  Server actions

Server actions cover every ordinary mutation of the user’s own rows: saved places (delete, rename, re-categorise, note, visited), manual add, collections, profile, account and sign-out.

Each performs the same four steps in order.

  1. Validates its input before any other work runs.
  2. Identifies the user.
  3. Writes through that user’s own client, so the authorisation decision is made by the database.
  4. Revalidates the narrowest correct path.

No REST layer is placed over the application’s own database. Row-level security is already the authorisation layer, and a hand-written CRUD API would be a second location in which the same rules could drift.

5.3  The confirm request path

Confirm is the request worth tracing, because the trust boundary sits there. The browser sends an extraction id and, per item, two integers and an optional note. It sends no place facts.

The route parses that body against a schema, then authorises the extraction through the user’s client by requiring that the user own an import row for its source. The check is performed by the database rather than by a conditional in application code.

The stored candidates are re-parsed out of the database, and the named index is handed to the domain, which derives name, coordinates, category and country from the row the server itself wrote.

Two Postgres functions then execute.

FunctionPrivilegeCapability
resolve_place()Service roleThe only path that can create a shared place
save_place()The user’s own sessionCan write only that user’s own library row

This arrangement closes a confirmed exploit. While the browser supplied the place itself, the resolve step refreshed provider-owned columns on the matched row, which permitted one user to rename and relocate a venue that other users had saved.

Section 06

Input Validation and Error Handling

Every input from outside the system is parsed at the boundary at which it arrives, and every failure is one of thirteen error codes carrying no provider text.

6.1  URL validation

The canonicaliser described in section 2.1 runs in the browser as the user types, so an unsupported link becomes a recognised redirect to manual add before any request is made.

The same pure function runs again inside the routes that fetch, and that second call is the control against server-side request forgery. The host must be exactly one of a closed list of TikTok hosts, by full-string equality rather than suffix match, so tiktok.com.evil.io and nottiktok.com both fail. The check is re-applied to every redirect when a short link is followed.

The browser-side check is a convenience. The control is the check performed on the server immediately before the network call.

6.2  Boundaries at which untrusted input is parsed

InputParsing behaviour
The oEmbed payloadDeliberately tolerant of new fields, so an added field on TikTok’s side cannot break the pipeline, while a removed title still does
The model’s outputA failure becomes a named error rather than a thrown exception
The confirm request bodyParsed against a schema before use, as described in section 5.3
JSON read back out of the system’s own databaseRe-parsed, because the code that wrote it may be an older deploy

Server actions validate through pure functions that return the message the form is to display.

6.3  The error taxonomy

The error code is a closed union of thirteen members. The wire format carries a code and two booleans: no message, no status, no stack and no vendor string.

Each code has exactly one constructor, with its retryable value fixed within it, so no call site can claim that a code is retryable when the taxonomy states otherwise. Adapters catch every vendor exception and construct one of these instead, which is the boundary described in section 2.8.

6.4  Status mapping and client copy

Each code maps to a status that attributes the failure.

FailureStatusRationale
The video has no caption422The video was read successfully and contains none
Model quota exhausted503Not a 429: the exhausted quota is the system’s own
Internal500The only code that may be a 500, which is what keeps a 500 in the logs meaningful

User-facing copy is held on the client as a total record over that union, so a fourteenth code is a compile error rather than a silent regression to a single apologetic screen.

Each entry names its recovery actions, and a test asserts that none is ever empty. No failure screen is a dead end.

6.5  Absence of results as a success outcome

“No places found” is not modelled as an error. It is a successful outcome with its own screen, because it is the usual result: creators name venues on screen and in speech rather than in captions, as stated in section 2.1.

Modelling the commonest outcome as a failure would corrupt every log built on the taxonomy of section 6.3.
