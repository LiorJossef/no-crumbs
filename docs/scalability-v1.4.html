Scale
and Deployment

Abstract. This is the scale document, and its final section carries the deployment and environment material. How No Crumbs behaves as more people use it: the system grows with what people add rather than with how many accounts exist, and the first thing to run out is a third-party place-lookup quota rather than our database. It covers where the load actually comes from, how work is split between the browser and the server, why the map loads a whole library in one query and when that stops being a good idea, which queries carry the load and where the indexes sit, what we would change first, and how to run the thing. Figures marked measured come from query plans taken against a seeded database of two hundred accounts; where a figure is derived or estimated, it says so.

Section 01

User Load & the Add Path

The system grows with what people add, not with how many accounts exist. At tens or hundreds of users nothing we built is the limit — the first thing to run out is a third-party quota.

1.1  What grows with what

Day-to-day use is cheap. Everything a signed-in person reads — their saved places, their collections — is scoped to their own account, and the database enforces that scope with an index on the user’s id. A new account only adds rows that nobody else’s queries ever touch, so the hundredth user costs about what the second did.

Adding a link is where the load actually comes from. Each one reaches outside the system: it fetches the post from TikTok, sends the caption to the model, and looks up the places the model found with Google.

StageDepends onCalls per added link
Caption retrievalTikTok oEmbed1
Reading places out of the captionThe model — Gemini in production1
Turning those into real placesThe places provider2–8

There is one lookup per candidate the model returned, so the count is a property of the post rather than of our system — but the eight is ours: the pipeline resolves at most eight candidates per added link (MAX_CANDIDATES = 8), and anything past that is kept and shown as unresolved rather than silently dropped. Repeats are free: provider answers are cached by place.

1.2  What binds first

The places provider allows 100 searches a day for the whole project. At two to eight lookups per added link that is roughly twelve to fifty added links a day for every user of the product combined, and the add path has no per-user cap. One enthusiastic person working through an evening’s saved posts can therefore use up the day for everybody else. The product degrades honestly when that happens — places come from the caption rather than from a place database, and the screen says so — but it degrades.

So the real answer to what happens at tens or hundreds of users is that the database is untroubled and the ceiling arrives at about one heavily-active user per day, and it is a billing limit rather than an engineering one. The first step is to raise the quota and add a per-user daily cap in the same change, so one account cannot spend everyone’s allowance.

Twelve to fifty is a stricter reading than a looser count of one to three lookups would give, and it is the one the code supports: the ceiling of eight is a constant in the pipeline, and the daily cap of a hundred is read from the provider configuration. The argument of this section therefore gets stronger, not weaker — the ceiling arrives sooner than a generous estimate would suggest.

1.3  How adding a link runs

Adding a link is two ordinary request/response round trips, with no streaming and no background jobs.

  • Step one fetches the post’s thumbnail, handle and caption, and answers in under a second.
  • Step two runs the model and the place lookups and returns candidates for review. It usually takes a few seconds — but it is the slowest thing in the system, because it waits on TikTok, then on the model, then on up to eight place lookups in turn, and a slow reply from any of them stretches the whole chain.

None of those steps sets a ceiling of its own, and no route configures a maximum duration either, so a bad run rides the platform default. Setting one explicitly is a one-line change, and it is in section 5.

Nothing is queued, because no piece of work outlives the request that started it — and there is no separate cache server, because the caches are Postgres tables. Each attempt is recorded with its stage and outcome, and the fetched post metadata, the model’s answer and the provider’s place replies are each kept. That is what makes a repeat cheap: adding the same link again costs nothing, while an edited caption correctly misses and runs again. Provider answers expire at 28 days, under the 30-day ceiling the licence imposes.

Rate limiting is basic anti-spam rather than a defence against a determined attacker, and it is worth being exact about where it sits, because it is not where a reader would expect.

  • Postgres holds a short per-source cooldown on the thumbnail-refresh path. Ten minutes per post, and a day for a post TikTok has refused, so scrolling an expired library does not turn into a burst of outside calls. Because it is a row in a table rather than a variable in a process, no number of warm instances can bypass it.
  • The add path itself has no limiter — neither of its two routes counts anything. Repeats are cheap because of the caches, not because anything refuses them.
  • The one in-memory counter in the system sits on the sentence-search route. It resets on deploy and is not shared between instances, so the real limit there is the stated one times however many instances are warm.

The gap that matters is the first bullet’s absence from the second: the path that spends the provider quota is the one with no cap on it. Section 5 puts that first.

Section 02

Client vs Server Boundaries

Pages read data on the server. The client filters an array it already holds and issues no queries of its own.

2.1  The ordinary arrangement

Each page builds a cookie-bound database client and reads under the user’s own token, so row-level security applies to every query a page makes. No page can return another user’s rows.

Client components exist for two reasons: the map needs browser APIs, and the sheets, filter chips and search field hold local state. They receive already-fetched arrays as props and filter in memory — search, category, tag and Been there are all array operations over that one array. Because the list and the markers come from the same array they cannot disagree, which two separately issued queries could.

2.2  Calls the browser makes

A few things start in the browser rather than in a page load:

  • The add flow, which is browser-driven because the browser holds the review state between the two steps.
  • Adding a place by name.
  • Refreshing a post’s thumbnail.
  • Turning a typed search sentence into filter values, which the browser then applies itself.

None of them is a database query. Each is a request to a server endpoint that does its own reading, so no credential and no query ever reaches the browser.

2.3  Reads that bypass row-level security

A small number of server modules — five API routes and two server actions — run with a privileged key that bypasses row-level security entirely. They therefore scope by user themselves, in ordinary application code: each resolves the signed-in user through the normal cookie-bound client, then writes the ownership condition into the query or passes it as an argument. The database is never asked to work out who is calling; by the time the privileged key is used, that has already been decided.

The point for this document is that these reads are still scoped to one person, so they cost what one library costs, like every other read. How the key is kept off the browser is the Security document’s subject.

2.4  What is deliberately not fetched

Over-fetching is controlled in four ways:

  • By column. No query selects every column; each names what it needs. A shared collection returns a place’s identity and nothing of the person who added it — not their note, not their tags, and not whether they have been — enforced both by the select and by a policy that would refuse those columns anyway.
  • By query. The list and the map share one fetch rather than issuing two.
  • By call. The caches remove whole classes of outside call.
  • By row, where it matters most. The one query over a table not scoped to a user is the resolver’s own prefilter, and it caps its result at 500 rows so a loose match cannot pull thousands of irrelevant records into memory. It is worth saying plainly that no production path runs it: it belongs to a dormant fallback resolver, and production resolves with Google. It is kept because that fallback is a terms-of-service switch rather than dead code.

What is not capped by row are the two reads the map page runs together: the library query, which is the next section, and beside it the membership read, which pulls one place id per item of every collection you can edit so a place’s sheet knows which collections it is already in.

Section 03

Map Rendering & Viewport Data Fetching

The map loads a user’s whole library in one query. That is the right choice at the size a personal library reaches, and the wrong one well above it.

3.1  The map query

The map reads every saved place belonging to the signed-in user in one query: 31 named columns across four tables — saved_places, the joined places row, the saved_place_sources link row and the sources row behind it — ordered by created_at desc, with no limit, no bounding box and no filter of any kind. Row-level security is its only scoping, and that scoping is the user.

3.2  Why it is unbounded

Three things need the complete set:

  • The camera frames the whole library on first paint.
  • The list and the markers come from one array, and so cannot disagree.
  • Search has to reach places outside the current view.

A viewport-scoped query gives none of the three on its own, and would need a second query for the camera besides.

3.3  The rendering is bounded even though the fetch is not

Drawing is banded by zoom — countries at the widest extent, then areas, then individual pins — and each layer declares its own zoom range, so the map library picks the band. The listeners the surface registers note what the user did and where the camera settled; none of them redraws features while you pinch.

3.4  When this stops being fine

Every saved place becomes a feature at every zoom level, so cost grows with the library and nothing caps it. Three things grow together, and all three are in the browser:

  • The response itself.
  • The feature collection, rebuilt on each filter change.
  • The array, re-filtered on each keystroke.

The database is not under pressure here, which is why this limitation sits in this section rather than in section 4.

The design target is about a hundred places, and that is not a round number: the library this was built against holds 113. At that size there is no difficulty at all.

Where it stops being fine is arithmetic rather than judgement, because the input was measured. A saved place serialised over exactly the columns the map query asks for is 1,306 bytes on average and 2,011 at most (measured against the real rows). So the payload is about 130 KB at a hundred places and about 1 MB at a thousand, on a phone, on every render of the map, alongside a thousand-feature collection rebuilt on each filter change and a thousand-element array re-filtered on each keystroke. That puts the point of difficulty at roughly five hundred to a thousand places in one library — derived from the measurement rather than guessed at.

What has not been measured is the browser half: no browser load test has been run at that size, so the 500–1,000 figure is where to start measuring rather than a proven cliff. The database half was measured and is not the problem — it is still answering in well under a millisecond at thirty thousand saved rows.

3.5  Pagination

No user-facing list is paginated, and that is a decision rather than an oversight. At a hundred pins a page control would cost the camera fit, the list-and-marker agreement and off-view search, and buy nothing anyone would notice. The collections list, a single collection’s places and the profile page are the same: unbounded reads of small things.

Adding it later would not be hard, and it is the one change that would make an index we already carry start earning its keep. saved_places_user_recent_idx is declared on (user_id, created_at desc) — exactly the map query’s scope and its order — and today’s query cannot use it. With no limit the planner has to read the whole library anyway, so it reaches the rows through saved_places_user_place_unique and sorts them in memory, which at this size is genuinely cheaper.

Adding limit 50 changes the plan outright: the ordered index takes over, the sort disappears, and the work falls by a factor of 2.6. That is measured, not assumed — EXPLAIN (ANALYZE, BUFFERS) under a real signed-in role, against 30,008 saved rows across 200 users:

no LIMIT     1,052 buffers   0.570 ms   saved_places_user_place_unique, then a sort
limit 50       402 buffers   0.251 ms   saved_places_user_recent_idx, no sort at all

Elsewhere, single-row reads use limit 1 correctly, and the only row cap in the system is the 500-row one in section 2.4 — which, as that section says, is on a path production does not take.

Section 04

Database Queries & Indexing

Every user-facing read is served from an index keyed on the user, so query cost follows one library’s size rather than a table’s.

4.1  The queries that could be heavy

Three queries account for the database work, and none of them is heavy today.

QueryHow oftenWhat it costs
The map readMost frequentThree steps: an index scan over the user’s saves, a key lookup per place, and a third through the link table to each source. Each step has an index behind it. Measured at 1,052 shared buffers and 0.570 ms with 30,008 saved rows across 200 users, the reader holding 150 of them
The collections listHeaviest per pageIt fetches a collection’s items in order to show a count and a few category chips. Measured at 1,289 buffers and 2.081 ms for 80 items — more work than the whole map read, for two collections. Comfortable at today’s sizes; a count is the right shape as collections grow
The resolver’s prefilterNever, in productionThe only query over a table not scoped to a user, and it is reached solely through the Overture fallback resolver. Production resolves with Google, which has no prefilter step at all, so no production path runs this query. When it does run — locally, or if the fallback is switched on — it caps at 500 rows and happens a few times per added link, never on a page view

4.2  The indexes that matter

Every frequent query is served by an index, and the user-facing ones all lead on the user’s id — the same column row-level security checks — so a read costs what one person’s library costs rather than what the table holds.

IndexWhat it serves
saved_places_user_place_uniqueThe map read’s driving scan today. The planner reaches the user’s rows through it and then sorts them in memory — measured, section 3.5 — and it is also the rule that you cannot save the same place twice
saved_places_user_recent_idxDeclared on (user_id, created_at desc), the map read’s scope and order. It serves no query today: the planner only switches to it once a limit is added, which is exactly the change section 3.5 describes
saved_places_place_user_idxThe shared-place check, which leads on the place rather than the user
sps_source_idx, sps_user_idxThe map read’s third step, and the gate on who may read a source
Five collection indexesThe collections read, item ordering, membership checks and the single-owner rule
Two trigram indexesThe dormant fallback resolver’s fuzzy matching — one on name, one on address. Idle while production resolves with Google
Four indexes on the add tablesBookkeeping for each attempt, the source access gate, expiry sweeping, and the one-open-attempt-per-source rule

All of these exist in production, and every migration on disk is applied there — 0001–0037 with no 0027, checked against the production database on 6 September 2026. No query asks the database to do text search or filtering on user data, so nothing further is needed there.

4.3  Room to tidy up

collection_invites has no index on collection_id, and the query that reads it filters on that column. At today’s handful of invites per collection that is fine; if invites ever reach the thousands, one index in one migration keeps it fast.

A couple of other indexes serve no query yet, and both say so in their own migrations: one supports whole-table maintenance, and the tag index is idle because tag filtering happens in the browser. It earns its place if that ever moves to the database.

Section 05

Current Limits & What We Would Do

A handful of things bind before the database does, and the one that actually binds is a third-party quota.

5.1  Limits, and when each one matters

LimitWhen it bitesWhat we would do
Places provider quota — 100 searches a day for the whole project Under any sustained use. Roughly twelve to fifty added links a day for all users combined, at two to eight lookups each. Raise the quota and add a per-user daily cap in the same change.
The add request’s duration — no maximum is configured Usually a few seconds, but the step waits on three external services in turn and nothing caps it, so a slow provider can stretch it well past that. Set an explicit maximum duration so a stalled request fails predictably instead of hanging; a one-line change.
Map payload — every place is drawn as a feature at every zoom Roughly five hundred to a thousand places in one library — derived from the measured 1,306 bytes per saved place, not from judgement. Add pagination and a viewport-scoped read, keeping a bounds query for the camera.
Collections list — counts a collection’s places by fetching its items Comfortable today; worth changing as collections grow. Replace the embedded read with a count.
collection_invites index — not declared Only once invites reach the thousands. Add the index — a small migration.

None of these is database capacity. Everything we run on is a free tier today, and the only external constraint that bites is the places provider’s 100 searches a day. Raising it is a billing decision, not an engineering one — it belongs to the owner rather than to the architecture.

5.2  What we would do first

  1. Raise the quota and add a per-user daily cap together, so one account cannot spend the shared allowance. The add path has no limiter at all today (section 1.3), and the table it would count against is already indexed for exactly this.
  2. Set a maximum request duration, then build the streaming add route, turning the longest request in the system into visible progress.
  3. Add pagination and a viewport-scoped read once a library passes a few hundred places, keeping the bounds query the camera needs. Measured payoff: 2.6× fewer buffers and no sort, and an index that currently serves nothing starts serving the most frequent query in the product.
  4. Make the collections list a count, add the invites index, and drop the tag index unless tag filtering moves to the database.
  5. Trim the prompt, which is sent to the model in full even when a caption names no places at all — the most common outcome. Last, because it is the only item that needs extraction quality re-checked.

A durable rate limiter — a counter table in Postgres — comes after all of these, once enough instances stay warm for the in-memory counters to be noticeably wrong.

5.3  What we would keep

Neither a job queue nor a separate cache server is planned, for the reason given in section 1.3: no work outlives its request. If that changes, the table that records each attempt already holds the shape one would need.

Section 06

Deployment & Environment

Where it runs, how to run it yourself from a clean clone, and what every environment variable is for.

6.1  Live, and how to run it

Live

https://no-crumbss.vercel.app — on Vercel, rebuilt automatically from main. /healthz reports the stage and the exact commit running. The database, auth and row‑level security are a Supabase Postgres project in the same region as the functions.

Run it locally

Needs Node 22, Docker Desktop and psql.

npm install
cp .env.example .env.local
npx supabase start
npm run db:reset
npm run dev

The repository is github.com/LiorJossef/no-crumbs, and it is public — a clean clone is the starting point those five commands assume. There are no containers of our own and no custom infrastructure: the build is the framework’s own preset with its defaults, which is deliberate, because there is then nothing here for a reader to reverse-engineer.

Anything starting with NEXT_PUBLIC_ is baked into the browser bundle at build time, so it must never hold a secret — and changing one requires a rebuild, not just a restart. No value of any of these appears in this document, in the repository, or in any other submitted file.
