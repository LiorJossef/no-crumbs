Section 01

User Load & the Import Path

The system grows with imports, not with accounts. At tens or hundreds of users nothing we built is the limit — the first thing to run out is a third-party quota.

1.1  What grows with what

Every user-facing read is scoped to the signed-in account, and the database applies that scope itself: row-level security compares user_id to auth.uid(), and every such policy sits on an indexed column. A new account adds rows no existing query traverses, so the hundredth user costs roughly what the second did. What the system pays for is imports.

One import makes three kinds of outside call.

StageDepends onCalls per import
Caption retrievalTikTok oEmbed1
Reading places out of the captionA language model (Gemini in production)1
Turning those into real placesThe places provider1–3 typical, 8 ceiling

Lookups are one per place the model found, so that last figure is a property of the post rather than of our system. Repeats are free: lookups are cached by place.

1.2  What binds first

The places provider allows 100 searches a day for the whole project. At one to three lookups per import that is roughly thirty-three to a hundred imports a day for every user combined, and the import path has no per-user cap. One enthusiastic person working through an evening’s saved posts can therefore use up the day for everybody else. The product degrades honestly when that happens — places come from the caption rather than a place database, and the screen says so — but it degrades.

So the real answer to what happens at tens or hundreds of users is that the database is untroubled and the ceiling arrives at about one active user. Raising it is a commercial decision, not an engineering one. The first step is to raise the quota and add a per-user daily cap in the same change, so one account cannot spend everyone’s allowance.

1.3  How an import runs

An import is two ordinary request/response round trips, with no streaming and no background jobs. The first fetches the post’s thumbnail, handle and caption and answers in under a second. The second runs the model and the place lookups and returns candidates for review; it takes seconds rather than milliseconds, at its slowest around thirty-four. No route in the codebase exports a maxDuration, so that chain runs against the platform default. Setting one is a one-line change, and it is in section 5.

Nothing is queued, because no piece of work outlives the request that started it, and there is no separate cache server, because the caches are tables.

TableWhat it holds
importsOne row per attempt, with its stage, timings and error code
extractionsThe model’s answer, unique on (source_id, model, prompt_version) and checked against a hash of the caption it was computed from
sourcesPost metadata already fetched
place_lookupsProvider answers, expiring at 28 days under the 30-day ceiling the licence imposes

The extraction cache is the one that pays: re-importing the same link costs nothing, while an edited caption correctly misses and runs again. An import costs a fraction of a cent, so money is not the constraint — the quota is, and it arrives long first.

Rate limiting is deliberately modest. A per-source cooldown lives in Postgres, so it is durable and identical on every instance. Two other counters live in process memory: they reset on deploy and are not shared between instances, so the real limit is the stated one times however many instances are warm. They restrain a misbehaving client rather than an attacker, and section 5 sequences a durable replacement.

Section 02

Client vs Server Boundaries

Pages read data on the server. The client filters an array it already holds and issues no queries of its own.

2.1  The ordinary arrangement

Each page builds a cookie-bound database client and reads under the user’s own token, so row-level security applies to every query a page makes. No page can return another user’s rows.

Client components exist for two reasons: the map needs browser APIs, and the sheets, filter chips and search field hold local state. They receive already-fetched arrays as props and filter in memory — search, category, tag and visited are all array operations over that one array. Because the list and the markers come from the same array they cannot disagree, which two separately issued queries could.

2.2  Calls the browser makes

Six calls start in the browser rather than in a page load. Three are the import flow — source-preview, probe and the confirm that saves the result — which is browser-driven because the browser holds the review state in between. place-search backs adding a place by name. thumbnail refreshes a post’s image and writes to the sources table. Only search/interpret reads nothing: it turns a typed sentence into filter values the browser applies itself.

None of the six is a database query. Each is a request to a server route that does its own reading, so no credential and no query ever reaches the browser.

2.3  The privileged key

The service key is never exposed to the browser, and three separate things ensure it. The module that reads it imports server-only, so a client-side import fails at build time. The variable has no public prefix, so its value cannot be inlined into a bundle. And only seven server-side modules use it — five API routes and two server actions.

Those seven run as service_role and so bypass row-level security entirely. They therefore check identity themselves, first and in ordinary application code: each resolves the signed-in user through the normal cookie-bound client, then writes the ownership condition into the query or passes it as an argument. The database is never asked to work out who is calling — by the time the privileged key is used, that has already been decided.

2.4  What is deliberately not fetched

No query selects every column; each names what it needs. A shared collection returns a place’s identity and nothing of the person who added it — not their note, not their tags, and not whether they have been — enforced both by the select and by a policy that would refuse those columns anyway. The list and the map share one fetch rather than issuing two. The caches remove whole classes of outside call. And the one query over a table not scoped to a user — the resolver’s prefilter over poi_index — returns at most 500 rows, ordered; without that cap one fuzzy match returned 2,904.

So over-fetching is controlled by column, by query and by call, and uncontrolled by row on exactly one read: the map’s, which is the next section.

Section 03

Map Rendering & Viewport Data Fetching

The map loads a user’s whole library in one query. That is the right choice at the size a personal library reaches, and the wrong one well above it.

3.1  The map query

The map reads every saved place belonging to the signed-in user in one query: 31 named columns across four tables — saved_places, the joined places row, the saved_place_sources link row and the sources row behind it — ordered by created_at desc, with no limit, no bounding box and no filter of any kind. Row-level security is its only scoping, and that scoping is the user.

3.2  Why it is unbounded

Three things need the complete set: the camera frames the whole library on first paint, the list and the markers come from one array and so cannot disagree, and search has to reach places outside the current view. A viewport-scoped query gives none of the three on its own, and would need a second query for the camera besides.

3.3  The rendering is bounded even though the fetch is not

Drawing is banded by zoom — countries at the widest extent, then areas, then individual pins — and each layer declares its own zoom range, so the map library picks the band. No zoom listener runs and nothing re-renders during a pinch.

3.4  When this stops being fine

Every saved place becomes a feature at every zoom level, so cost grows with the library and nothing caps it. Three things grow together: the response, the feature collection rebuilt on each filter change, and the array re-filtered on each keystroke. All three are in the browser. The database is not under pressure here, which is why this limitation sits in this section rather than in section 4.

The design target is about a hundred places, and that is not a round number: the library this was built against holds 113. At that size there is no difficulty at all. The point where it stops being fine — a library in the high hundreds — is engineering judgement rather than a measurement. No load test has been run at that size, and it is written as an estimate so that whoever first exceeds it measures instead of trusting this sentence.

3.5  Pagination

No user-facing list is paginated, and that is a decision rather than an oversight. At a hundred pins a page control would cost the camera fit, the list-and-marker agreement and off-view search, and buy nothing anyone would notice. The collections list, a single collection’s places and the profile page are the same: unbounded reads of small things.

Adding it later would not be hard. saved_places_user_recent_idx is already declared on (user_id, created_at desc) — exactly the map query’s scope and its order — so adding a limit and a cursor needs no schema work. Today the planner prefers to read a few hundred rows and sort them in memory, which is genuinely cheaper at this size; that was checked with EXPLAIN rather than assumed. Elsewhere, single-row reads use limit 1 correctly, and the only real cap in the system is the 500-row one in section 2.4.

Section 04

Database Queries & Indexing

Every user-facing read is served from an index keyed on the user, so query cost follows one library’s size rather than a table’s.

4.1  The queries that could be heavy

Three queries account for the database work, and none of them is heavy today.

QueryHow oftenWhat it costs
The map readMost frequentThree steps: an index scan over the user’s saves, a key lookup per place, and a third through the link table to each source. Each step has an index behind it
The collections listHeaviest per pageOne embedded select pulls every collection_items row of every collection you are a member of, with each item’s places row joined, only to render a count and a few category chips. A count() plus a small distinct set is the right shape
The places prefilterA few times per importThe only query over a table not scoped to a user. That table holds 10,462 rows and the query caps its result at 500, ordered — and it is a resolver fallback, never on a page view

4.2  The indexes that matter

IndexWhat it serves
saved_places_user_recent_idxThe map read’s ordering, and the only index a paginated version would need
saved_places_user_place_uniqueThe map read’s driving scan, and the rule that you cannot save a place twice
saved_places_place_user_idxThe shared-place check, which leads on the place rather than the user
sps_source_idx, sps_user_idxThe map read’s third step, and the gate on who may read a source
Five collection indexesThe collections read, item ordering, membership checks and the single-owner rule
Two trigram indexesThe prefilter’s fuzzy matching, one on name and one on address
Four import indexesImport bookkeeping, the source access gate, expiry sweeping, and one-open-import-per-source

All of these exist in production; every migration is applied there. No query asks the database to do text search or filtering, so no full-text index is needed, and a leading-wildcard match could not use one anyway.

4.3  The one that is missing

collection_invites has no index on collection_id. The query that reads it filters on collection_id, drops revoked rows and takes the newest, and it runs whenever an owner opens a collection. The table grows across the whole product while that query is per-user, so the scan grows with every invite anyone has ever created rather than with the owner’s own data. It is fine today, at a handful of invites per collection; the point where it stops being fine — a few thousand rows — is an estimate, not a measurement. The fix is one index in one migration, cheap enough that the estimate need not be precise.

Two other indexes serve no query today, and both say so in their own migrations: one supports whole-table maintenance, and the tag index is idle because tag filtering happens in the browser. It earns its place only if that moves to the database.

Section 05

Current Limits & What We Would Do

Six things bind before the database does. The ceiling is a quota, which is a decision about money rather than about architecture.

5.1  Limits, and when each one matters

LimitWhen it bitesWhat we would do
Places provider quota — 100 searches a day for the whole project Under any sustained use. Roughly thirty-three to a hundred imports a day for all users combined. Raise the quota and add a per-user daily import cap in the same change.
Import duration — no maximum is configured An oEmbed call, a model call and a few lookups chained together, reaching about 34 s at worst against the platform default. Configure a maximum duration; a one-line change.
Map payload — every place is drawn as a feature at every zoom A library several times the design target of about a hundred places. The multiplier is judgement. Add pagination and a viewport-scoped read, keeping a bounds query for the camera.
Collections list — fetches items in order to count them Grows with the total membership of every collection you are in. Replace the embedded read with an aggregate.
Missing collection_invites index A few thousand invites across the product — an estimate, not a measurement. Add the index.
Model cost — a fraction of a cent per import Capped today by the quota, to well under a dollar a day. Raising the quota removes that cap. Cut the prompt, which is sent in full even on imports that find nothing.

Not one of these is database capacity. What separates a working product from one serving a hundred users is a quota decision and the spending decision behind it — which belongs to the owner rather than to the architecture.

5.2  What we would do first

  1. Raise the quota and add a per-user daily import cap together, so one account cannot spend the shared allowance.
  2. Set a maximum request duration, then build the streaming import route, turning the longest request in the system into visible progress.
  3. Add pagination and a viewport-scoped read once a library passes a few hundred places, keeping the bounds query the camera needs.
  4. Make the collections list an aggregate, add the missing invites index, and drop the tag index unless tag filtering moves to the database.
  5. Cut the prompt, which dominates what an import costs. Last, because it is the only item that needs extraction quality re-checked.

A durable rate limiter — a counter table in Postgres — comes after all of these, once enough instances stay warm for the in-memory counters to be noticeably wrong.

5.3  What we would keep

Neither a job queue nor a separate cache server is planned, for the reason given in section 1.3: no work outlives its request. If that changes, the imports table already holds the shape one would need.
