Section 01 · who you are

Authentication & Session State

Signing in is handled by the auth provider, so this application never sees, hashes or stores a password.

The whole of authentication is one screen, which calls sign-up or sign-in. Nothing else in the codebase authenticates anybody. Accounts live in the auth provider’s own tables, in a schema no browser role can read at all, so a user’s email address is not reachable from the product’s data API.

The session is a cookie with a one-hour token and refresh rotation. “Remember me” is a custom cookie adapter that drops the expiry, so with the box unticked the cookie dies with the browser instead of living for the library’s default 400 days.

Every server-side check asks the auth server rather than the cookie. One call decodes what the browser sent and trusts it; the other validates the token upstream. The validating call appears at 31 sites across 21 files — the middleware, every page that renders user data, every API route and every server action. The single trusting call is on the sign-in screen, deciding whether to say “check your email”.

The checks are layered on purpose: middleware redirects anonymous visitors away from the map, and each page still guards itself, because a route matcher is a list somebody forgets to update. If all of it were deleted the database would still refuse — the page would render an empty list rather than somebody else’s.

Section 02 · whose rows you get

Row-Level Security & User Map Isolation

Who may read a row is decided by Postgres itself, not by if statements in application code.

Row-level security means the database attaches a rule to a table and adds it to every query touching it. Our rule is one sentence: the row’s owner must be the person asking. Postgres adds that rule with AND, so a caller’s own filter can only narrow the result — asking for someone else’s id returns nothing rather than their map.

All 17 tables have row-level security enabled and forced; forcing matters, because without it a table’s owner is exempt from its own rules. There are 38 live policies, every one written for the signed-in role and reducing to the caller’s own identity.

The anonymous role holds nothing. Across the 36 migrations there is not one grant to it, only revokes — which is why the key shipped in the browser is not a contradiction. It identifies the project and grants no access; authorisation is the database’s rules, not the secrecy of that key.

Users hold no insert, update or delete privilege on the tables shared between people. Those writes go through privileged functions that run with the owner’s rights. There are 20, of which 13 may be run by a signed-in user and seven actually write — deliberately, because for a user’s tags and for model-written prose the function is the write path. Each takes the caller’s identity from the session inside its own filter and refuses a stranger’s row.

Privileges are also granted column by column, which makes some attacks impossible to express rather than merely refused. A user may update exactly five columns of their own saved place; the owner, the venue and the origin are not among them, so “give my save to another account” fails at the privilege layer before any rule is consulted.

Eight SQL suites prove it rather than assert it: each is one transaction that creates its own users, attempts the cross-user read, write and delete, and rolls back. Their assertions are counted in the testing specification.

Section 03 · what we refuse

Input Sanitization & External Link Defense

Every value crossing a boundary is parsed against a schema before it is used — and the most important boundary is the one where we stopped trusting the browser at all.

The strongest thing here is a bug we found and closed. The import-confirm endpoint used to accept the place itself — name, latitude, longitude, provider id — and passed it to a function that refreshes a venue’s details. Venue rows are shared between everyone who saved that venue, and nothing checked who was asking, so one ordinary signed-in request could rename and relocate a venue other people had saved. Confirmed on a local database: a single request renamed a Tel Aviv café and moved it to the Eiffel Tower.

The fix was not a stricter validation rule, because no schema can tell a truthful latitude from a malicious one. It was a change of authority: the request now carries an extraction id, indices into the candidate list the server itself wrote, and the user’s own note — place facts do not travel from the browser at all. A hostile body can do exactly two things, name an extraction it does not own or an index that does not exist, and both are refused.

Other boundaries are guarded the same way, including data read back out of our own database, and beneath all of them sit 103 database check constraints — the layer an application bug cannot skip.

The pasted link, which is the one value that makes our server open a connection

A server given a URL can be tricked into fetching something private. The canonicaliser rejects anything that is not http or https, anything carrying credentials or a port, and any bare IP address, then matches the hostname for exact equality against a closed list of six TikTok hosts — never an “ends with” test, so tiktok.com.evil.io fails like any random host.

Redirects are followed by hand: every new location re-checked against the same list, five hops maximum, a timeout on each request, and no HTML parsed. Both import routes re-run the whole check on the server whatever the client did, because only the server’s check counts. The language model is untrusted in the same way: its output is schema-validated, and every claim it makes must quote the caption before a user is offered it.

Section 04 · routes and keys

API Protection & Secrets Management

There are six routes under /api; all are POST, and all establish who is calling before doing anything else.

Being POST-only matters more than it looks: a GET handler is reachable from a cross-site image tag or a link, whereas a JSON POST is not. Most of the product needs no route protection at all, because most of it is not a route — everything the user reads is fetched on the server under that user’s own token.

Errors are treated as a leak channel, not a formatting problem. A route returns a code from a closed set of thirteen and nothing else: no provider message, no upstream status, no stack, no environment-variable name. Detail goes to the server log, which carries codes and counts, never a caption and never a coordinate.

Security headers are set on every response: no content-type sniffing; a referrer policy that becomes no-referrer on the invite-join route, because the token is in the path; a ban on being framed by anyone; and a permissions policy granting location to our own page while denying camera, microphone and payment.

The rule for secrets is one line — anything without the public prefix must never reach the browser — and two mechanisms enforce it. The framework inlines only prefixed variables into client code, and every module holding a secret imports server-only, which turns “a client component imported this” into a build failure rather than a shipped key. Twelve modules carry that import.

Nothing sensitive is in the repository: every environment file is excluded while the example is kept, and keys live in the hosting platform’s encrypted store. The privileged database key bypasses every rule, so its protection is placement and secrecy — never in the browser, never in the repository, never in an error message.

Section 05 · what remains open

Known Risks & Security Hardening

No exploitable cross-user vulnerability was found — and the honest version of that sentence names what was actually attempted.

The attacks were executed, not reasoned about. A freshly created attacker account, running as a real signed-in user, tried to read another user’s saved places directly, through joined requests and through row counts; to update and delete their rows; to reassign a save, take over a shared collection and choose its own invite token; and called every stored procedure with someone else’s identifiers. The same set was repeated with no account at all, and again over HTTP with genuine tokens. Every read returned zero rows and every write returned a permission error.

One property does behave as an attacker would like, and it is documented rather than fixed: saving a venue id you already possess grants read access to that shared venue row. The ids are random 128-bit values, the data is open and non-personal, and the column grants mean it reaches nothing else.

The rest are real and remain open. Each is graded for a coursework project with no public sign-up, and each names what would change the grade.
