Section 01 · who you are

Authentication & Session State

Signing in is handled by the auth provider, so this application never sees, hashes or stores a password.

Authentication is one screen, and nothing else

The whole of authentication is one screen, which calls sign-up or sign-in. Nothing else in the codebase authenticates anybody.

Accounts live in the auth provider’s own tables, in a schema no browser role can read at all. A user’s email address is therefore not reachable from the product’s data API.

The session is a cookie that expires when we say it does

The session is a cookie with a one-hour token and refresh rotation.

“Remember me” is a custom cookie adapter that drops the expiry. With the box unticked the cookie dies with the browser, instead of living for the library’s default 400 days.

Every server-side check asks the auth server, not the cookie

One call decodes what the browser sent and trusts it; the other validates the token upstream. Only the second one is used to decide anything.

  • The validating call appears at 31 sites across 21 files — the middleware, every page that renders user data, every API route and every server action.
  • The single trusting call is on the sign-in screen, deciding whether to say “check your email”.

The checks are layered on purpose. Middleware redirects anonymous visitors away from the map, and each page still guards itself, because a route matcher is a list somebody forgets to update.

If all of it were deleted the database would still refuse. The page would render an empty list rather than somebody else’s.

Section 02 · whose rows you get

Row-Level Security & User Map Isolation

Who may read a row is decided by Postgres itself, not by if statements in application code.

The rule is one sentence, and Postgres adds it to every query

Row-level security means the database attaches a rule to a table and applies it to every query touching that table. Our rule is one sentence: the row’s owner must be the person asking.

Postgres adds that rule with AND, so a caller’s own filter can only narrow the result. Asking for someone else’s id returns nothing rather than their map.

All 17 tables have row-level security enabled and forced. Forcing matters, because without it a table’s owner is exempt from its own rules.

The isolation surface, counted from the migrations

The anonymous role holds nothing

Across the 36 migrations there is not one grant to it, only revokes. That is why the key shipped in the browser is not a contradiction.

The key identifies the project and grants no access. Authorisation is the database’s rules, not the secrecy of that key.

Shared tables are written only through privileged functions

Users hold no insert, update or delete privilege on the tables shared between people. Those writes go through functions that run with the owner’s rights.

There are 20, of which 13 may be run by a signed-in user and seven actually write. That is deliberate: for a user’s tags and for model-written prose, the function is the write path.

Each one takes the caller’s identity from the session inside its own filter, and refuses a stranger’s row.

Column grants make some attacks impossible to express

Privileges are granted column by column, which makes some attacks impossible to express rather than merely refused.

A user may update exactly five columns of their own saved place. The owner, the venue and the origin are not among them, so “give my save to another account” fails at the privilege layer before any rule is consulted.

Proved, not asserted

Eight SQL suites prove the isolation rather than assert it. Each is one transaction that creates its own users, attempts the cross-user read, write and delete, and rolls back.

Their assertions are counted in the testing specification.

Section 03 · what we refuse

Input Sanitization & External Link Defense

Every value crossing a boundary is parsed against a schema before it is used — and the most important boundary is the one where we stopped trusting the browser at all.

The strongest thing here is a bug we found and closed

The import-confirm endpoint used to accept the place itself — name, latitude, longitude, provider id — and passed it to a function that refreshes a venue’s details.

Venue rows are shared between everyone who saved that venue, and nothing checked who was asking. One ordinary signed-in request could rename and relocate a venue other people had saved.

Confirmed on a local database: a single request renamed a Tel Aviv café and moved it to the Eiffel Tower.

The fix changed the authority, not the validation rule

A stricter schema would not have helped, because no schema can tell a truthful latitude from a malicious one.

The request now carries an extraction id, indices into the candidate list the server itself wrote, and the user’s own note. Place facts do not travel from the browser at all.

A hostile body can now do exactly two things — name an extraction it does not own, or an index that does not exist — and both are refused.

Every other boundary, and the layer underneath them all

Other boundaries are guarded the same way, including data read back out of our own database. Beneath all of them sit 103 database check constraints, the layer an application bug cannot skip.

The pasted link is the one value that makes our server open a connection

A server given a URL can be tricked into fetching something private. The canonicaliser rejects, before any request is made:

  • Any scheme that is not http or https — so file, ftp and data never reach the fetcher.
  • Any URL carrying credentials, which is the classic way to disguise the real host.
  • Any URL carrying a port, which is how an internal service is usually addressed.
  • Any bare IP address, including the loopback and metadata addresses.
  • Any hostname not exactly equal to one of six TikTok hosts — matched for equality, never an “ends with” test, so tiktok.com.evil.io fails like any random host.

Redirects are followed by hand, and the model is untrusted too

Every new location is re-checked against the same list, with five hops maximum, a timeout on each request, and no HTML parsed.

Both import routes re-run the whole check on the server whatever the client did, because only the server’s check counts.

The language model is untrusted in the same way. Its output is schema-validated, and every claim it makes must quote the caption before a user is offered it.

Section 04 · routes and keys

API Protection & Secrets Management

There are six routes under /api; all are POST, and all establish who is calling before doing anything else.

Six routes, all POST, all identifying the caller first

Being POST-only matters more than it looks. A GET handler is reachable from a cross-site image tag or a link; a JSON POST is not.

Most of the product needs no route protection at all, because most of it is not a route. Everything the user reads is fetched on the server under that user’s own token.

Errors are treated as a leak channel, not a formatting problem

A route returns a code from a closed set of thirteen and nothing else: no provider message, no upstream status, no stack, no environment-variable name.

Detail goes to the server log, which carries codes and counts — never a caption, and never a coordinate.

Security headers, set on every response

  • No content-type sniffing, so a response is only ever read as what we said it is.
  • A referrer policy that becomes no-referrer on the invite-join route, because the invite token is in the path.
  • A ban on being framed by anyone, which closes the clickjacking route into the map.
  • A permissions policy granting location to our own page while denying camera, microphone and payment.

Secrets: one rule, two mechanisms that enforce it

The rule is one line — anything without the public prefix must never reach the browser. It is not left to discipline.

  • The framework inlines only prefixed variables into client code, so an unprefixed name is simply absent from the bundle.
  • Every module holding a secret imports server-only, which turns “a client component imported this” into a build failure rather than a shipped key. Twelve modules carry that import.

Nothing sensitive is in the repository. Every environment file is excluded while the example is kept, and keys live in the hosting platform’s encrypted store.

The privileged database key bypasses every rule, so its protection is placement and secrecy: never in the browser, never in the repository, never in an error message.

Section 05 · what remains open

Known Risks & Security Hardening

No exploitable cross-user vulnerability was found — and the honest version of that sentence names what was actually attempted.

What was actually attempted

The attacks were executed, not reasoned about. A freshly created attacker account, running as a real signed-in user, tried to:

  • Read another user’s saved places directly, by selecting their rows.
  • Read them through joined requests, arriving at the same rows from a related table.
  • Read them through row counts, to see whether an aggregate would leak what a select would not.
  • Update their rows.
  • Delete their rows.
  • Reassign a save to a different owner.
  • Take over a shared collection belonging to the other user.
  • Choose its own invite token, rather than accept a generated one.
  • Call every stored procedure with someone else’s identifiers.

The same set was repeated with no account at all, and again over HTTP with genuine tokens.

Every read returned zero rows, and every write returned a permission error.

The one property that behaves as an attacker would like

It is documented rather than fixed: saving a venue id you already possess grants read access to that shared venue row.

The ids are random 128-bit values, the data is open and non-personal, and the column grants mean it reaches nothing else.

The risks we accepted, and what would change each grade

The rest are real and remain open. Each is graded for a coursework project with no public sign-up, and each names what would change the grade.

The hardening that matters most

The most valuable hardening is the least glamorous: keep the policy suites running on every push, rather than on the day somebody remembers.

Evidence that is not continuous is a snapshot, and a snapshot ages.
