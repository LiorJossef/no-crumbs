Scalability
Analysis

Abstract. This document analyses the behaviour of the No Crumbs system under increasing load. It establishes the axis along which cost grows, the division of work between client and server, the cost characteristics of the map and database read paths, and the five constraints that bind before the database does. Each constraint is stated together with the threshold condition that makes the corresponding remediation worth performing.

Binding constraint: provider quota No job queue Index-scoped reads 36 migrations

Section 01

User Load & Extraction Queue

System load scales with import volume rather than with the number of accounts. Within the range of tens to hundreds of users, the binding constraint is a third-party API quota rather than any component of this system.

1.1  Scaling axis

All user-facing reads are scoped to the signed-in account. Row-level security applies that scope at the index, so an additional account introduces rows that no existing query traverses. Read cost is therefore a function of a single user’s library size, not of table size.

The import path is the cost driver. A single import issues three classes of external call in sequence.

StageExternal dependencyCalls per import
Caption retrievalTikTok oEmbed endpoint1
Candidate extractionLanguage model (Gemini in production)1
Place resolutionPlaces providerup to 8

The model provider is selected by a single environment variable. Two adapters implement one interface, and the branch occurs in exactly one file.

1.2  Execution model

An import executes as two synchronous request/response round trips. Neither streaming nor background processing is used.

Round tripWork performedResponse
1Source metadata retrievalThumbnail, author handle and caption, returned in under one second
2Extraction and place resolutionCandidate places for review

A streaming variant of the import route was specified but not implemented. In its absence the interface reports the actual state rather than displaying synthetic progress.

1.3  Absence of a job queue

No job queue and no dedicated cache server are deployed. Two conditions justify this. First, no unit of work outlives the request that initiated it. Second, the persistence a queue would require is already provided by four tables in the primary schema.

TableFunction
importsPer-attempt record, carrying stage, timings and error code
extractionsUnique on source, model and prompt version, so a repeated link against the same model incurs no model cost
sourcesCached post metadata
place_lookupsCached provider responses under a 28-day expiry enforced by the database

Cache state is held within the system of record. No secondary store requires consistency management.

1.4  Rate limiting

Three rate-limiting controls are in place. Their scope and durability differ, and the difference is material.

ControlLimitHeld inDurability
Search interpretation20 submissions per user per 10 minutesProcess memoryResets on deploy; not shared across instances
Thumbnail retrievalThree windows over a shared daily allowanceProcess memoryResets on deploy; not shared across instances
Per-source import cooldown10 minutes; 24 hours after a platform refusalPostgresDurable and instance-independent

The two in-memory counters constrain a malfunctioning client. They are not a security control, and are not represented as one.

The import path carries no per-user cap. The threshold condition for introducing one is the raising of the provider quota described in section 5.1: while that daily ceiling is the effective limit, an uncapped import path remains bounded. The index a per-user counter would read is already present in the schema, so the change is confined to application code.

Section 02

Client vs Server Boundaries

All data fetching occurs on the server. Client components hold interaction state and issue no database queries.

2.1  Server-side data access

Each route’s page constructs a cookie-bound database client and reads under the public key carrying the user’s token. Every query issued by a page is consequently subject to row-level security; no page-level read can return rows outside the requesting user’s scope.

2.2  Client components

83 files are marked as client components, for two reasons: map rendering requires browser APIs, and the sheets, filter chips and search field hold local state.

These components receive already-fetched arrays as props. Search, category, tag and visited filtering are array operations performed over that single array. The list and the map markers are therefore derived from one source, which eliminates the possibility of divergence between two independently issued queries.

2.3  Client-initiated server call

One call originates in the browser and is not a page load. The search interpreter transmits the sentence the user typed and returns a set of filter values, which the browser then applies locally. It reads no rows.

It is rate-limited because it consumes model budget, not because it accesses data.

2.4  Privileged credential containment

The privileged database key is not exposed to the browser. Three independent controls enforce this.

ControlEffect
The module that reads the key imports server-onlyA client-side import of that module fails at build time
The variable carries no public prefixThe value cannot be inlined into a client bundle
Callers are limited to eight server-side modules — five API routes, two server actions and one server-side helperEvery one of the eight identifies the user before the key is used

A further constraint applies within that module: a privileged query never filters by user. It accesses only the global cache tables, which carry no user column.

Section 03

Map Rendering & Viewport Data Fetching

The map issues a single unbounded query for the user’s complete library and bounds the rendering rather than the fetch. The section states the rationale, the resulting cost model and the threshold at which the decision should be revisited.

3.1  The map query

The map read selects 31 columns across the user’s saved places, the joined place record and the linked source, ordered by recency. It applies no limit, no filter and no viewport predicate.

3.2  Rationale for an unbounded read

Three product requirements depend on the complete result set.

RequirementDependency on the full set
Initial camera positionThe camera frames the entire library on first paint
List and marker agreementBoth views derive from one array, so they cannot disagree
SearchResults must include places outside the current viewport

A viewport-scoped query would require an additional query returning the bounds of the user’s complete library, and would still leave off-screen search results unreachable.

3.3  Render-time bounding

Bounding is applied at draw time across three zoom bands: country markers at the widest extent, then area markers, then individual pins. Band selection is delegated to the map library through each layer’s own zoom range. No zoom listener executes and no re-render is triggered during a pinch gesture.

3.4  Cost model and known limitation

Every saved place is emitted as an individual feature at every zoom level. Cost is linear in library size, and no mechanism caps it.

Three quantities grow together: the response payload, the feature collection rebuilt on each filter change, and the array re-filtered on each keystroke. The constraint is client-side rather than database-side; the database is not the component under pressure.

The design target is a library of approximately one hundred places, at which client performance is unproblematic. The threshold for revisiting the decision is a library in the high hundreds.

3.5  Pagination readiness

An existing index matches the map query’s ordering exactly, so introducing a limit would permit the planner to walk that index and eliminate the sort. The query cannot use the index in its present form, because an unbounded read retrieves every row regardless of ordering. Pagination is therefore a measured and prepared change rather than an absent one.

Section 04

Database Query Performance & Indexing

Every user-facing read is served from an index keyed on the user. Query cost is a function of one library’s size rather than of table size.

4.1  Query inventory

Three queries account for the system’s database cost.

QueryFrequencyAccess path and cost driver
Map readHighestIndex scan over the reader’s saves, followed by a key lookup per place
Collections index readHeaviest per pageEmbeds every item of every collection the user belongs to in order to render a count and a small number of category chips
Places prefilterA few times per importThe only query over a six-figure table; a resolver fallback, not on the page-view path

4.2  Index inventory

IndexQuery served
saved_places_user_recent_idxThe map read’s ordering; the only index a paginated form could use
saved_places_user_place_uniqueThe map read’s driving scan, and the duplicate-save constraint
saved_places_place_user_idxThe shared-place policy’s existence check, which leads on the place
Three collection indexesThe collections read, and collection membership checks for a place
Two trigram indexesThe resolver prefilter’s fuzzy-match arms
Three import indexesImport bookkeeping and the source access gate

No query delegates text search or filtering to the database, so no full-text index is required. A leading-wildcard match could not use one in any case.

4.3  Identified gaps

One index is absent. collection_invites carries no index on its collection column; the absence was verified across all 36 migrations. The table grows globally while the query that reads it is per-user, executed whenever an owner opens a collection. The resulting scan is linear in the total number of invites created across the product rather than in the owner’s own data. The threshold is a few thousand rows; the remediation is a single index.

Two indexes serve no current query, and both are documented as such in their own migrations. One exists to support whole-table maintenance and is consulted by no per-user query. The tag index is unused because tag filtering executes in the browser; it becomes justified only if server-side tag filtering is introduced.

Section 05

Current Scale Limits & Future Architecture

Five constraints bind before the database does. The system’s ceiling is a provider quota, which is a commercial decision rather than an engineering one.

5.1  Constraints and thresholds

Each constraint below is stated with the condition under which the corresponding remediation becomes warranted.

ConstraintThreshold conditionRemediation
Places provider quota — a hard cap of 100 searches per day across the whole project Reached under any sustained usage. At two to eight lookups per import, the cap corresponds to roughly twelve to fifty imports per day for all users combined. Raise the cap, and introduce a per-user daily import cap in the same change.
Import wall-clock duration — no maximum duration is configured A route chaining an oEmbed call, a model call and up to eight sequential lookups against the platform default. Manifests as an individual failure rather than a scale limit. Configure a maximum duration; a one-line change.
Map payload — every saved place is emitted as a feature at every zoom level A library several times larger than the design target of approximately one hundred places. Introduce pagination and a viewport-scoped read, retaining a bounds query for the camera.
Collections index read — retrieves items in order to count them Cost grows with the total membership of every collection the user belongs to. Replace the embedded read with an aggregate.
Missing collection_invites index A few thousand invite rows across the whole product. Add the index.

None of these constraints is database capacity at the stated user range. The distinction between a functioning product and a product serving one hundred users is, in this system, a quota decision.

5.2  Remediation sequence

The work above is ordered as follows.

  1. Raise the provider quota and introduce a per-user daily import cap in the same change, so that a single account cannot consume the shared allowance.
  2. Configure a maximum request duration, then implement the streaming import route specified in section 1.2, converting the longest request in the system into observable progress.
  3. Introduce pagination and a viewport-scoped read once a library exceeds a few hundred places, retaining the bounds query the camera requires.
  4. Convert the collections read to an aggregate, add the missing invites index, and drop the tag index unless server-side tag filtering is introduced.

A durable rate limiter — a counter table in Postgres — is sequenced after the above. It becomes necessary once enough instances remain warm for the in-memory counters to be measurably incorrect.

5.3  Decisions retained under growth

Neither a job queue nor a separate cache server is planned, on the same ground stated in section 1.3: no unit of work outlives its request. Should that condition change, the imports table already provides the required schema.
