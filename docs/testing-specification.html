What we decided
working means.

A test suite is only as good as its definition of success. This document states what working means for each part of No Crumbs, how each claim is checked, and — just as plainly — what the tests cannot tell us.

Section 01 · the business process

Core Feature and Business Process Verification

The product has one business process, and working means it survives all of its hops without inventing anything.

The product has one business process, and every test in this section exists to hold one of its hops honest.

A user pastes a TikTok link. The link becomes a canonical video identity, then a caption, then a structured extraction, then real-world places, then rows that user owns on a private map.

“No places found” is a success, not an error

Working could not mean “the happy path completes”, because that is not the common case. The most frequent outcome of an import is that the caption names no place at all.

So “no places found” is defined as a success, with its own screen and its own tests. A version of the product that treated it as an error would fail this specification even if every request returned 200.

The process is specified as a test, not as prose

One test drives the real pipeline. It asserts the event sequence in order, and that zero candidates ends on the no-places screen.

The same test makes partial success first-class. Some places resolved and some not is still a finished import, because unresolved names help a person more than a failure screen does.

Thirteen error codes, and no fourteenth

The error taxonomy is closed, and proved closed. There are thirteen error codes; the pipeline test reaches each one through real code, then asserts all thirteen were reached.

Adding a fourteenth fails the suite until someone shows how a user could get there.

Then checked assembled, in a real browser

Six of the thirteen browser specs drive import, including a double submit and a stale response arriving after the user changed the link. In the run cited above, 56 browser tests passed and 2 were skipped.

What this layer cannot tell us

None of this tells us whether the answer was any good. Pinning “this caption yields this venue” would pin a third party’s non-deterministic output, and would fail on a model upgrade that was an improvement.

Quality is therefore measured by hand, and the numbers written down.

Section 02 · refusing precisely

Input Validation and Edge Case Handling

Working here means the product refuses precisely, and never turns an odd input into a confident wrong answer.

There are two untrusted inputs, and they are untrusted in different ways.

The paste field is a security boundary

It is a security boundary rather than a usability one, because what a user pastes becomes an outbound request from our server.

Its parser is default-deny against a closed allow-list of six hosts, matched by full-host equality and never by suffix.

The tests attack it the way an attacker would, with a host that:

  • merely ends in tiktok.com;
  • contains it as a substring;
  • carries credentials in the authority;
  • carries an explicit port;
  • is an IP literal;
  • arrives under any non-HTTP scheme.

A further test asserts the allow-list is exactly that closed set, and that it is shared with the short-link resolver, so a second adapter cannot quietly widen it.

Refusals must be distinguishable

That is a product decision written as a test. An Instagram link is not broken — it is a platform we do not support, and it earns its own code and a route to manual add.

Text that is not a link at all earns a different code and a different sentence. The two are asserted never to collapse into one, because collapsing them sends a person to fix something that is not broken.

The model is the second untrusted input

The language model is well-intentioned and wrong rather than hostile, so the schema tests reject what a helpful model invents:

  • an invented category;
  • a list past the candidate cap;
  • an out-of-range latitude;
  • a length that fits raw but not once accents are normalised.

Null coordinates are accepted and required to be present, because “no basis for a guess” is a claim and a missing field is not.

One edge case changed the design

Truncated model output is salvaged, not discarded. A reply cut mid-list yields the candidates that did parse, because losing eight good places to one bad byte is the worse outcome.

The limit of this layer

It proves the boundary rejects bad input. It does not prove the boundary is the only way in — that is what the layer guard in section 4 is for.

Section 03 · the one real breach

Access Control and Privacy Enforcement

Working means a second signed-in user, holding a valid session, can neither read nor forge a row belonging to the first — proved by executing the attack, not by reading the policy.

Every map is private, so this is the one failure that is a breach rather than a disappointment.

The tests live where the authorisation does

Authorisation lives in the database, so the tests do too. Eight SQL policy files carry 277 assertions, and the database job rebuilds the schema from the first migration and runs all eight on every push.

Seven of the eight create at least two real users, then issue the adversary’s queries under the adversary’s own role.

The positive half is asserted first

That ordering is the most important decision in this section. “User B sees zero of user A’s rows” is satisfied identically by a correct policy and by a database where nobody can read anything.

That is the standard way a policy suite goes vacuously green. So each file first shows A reading exactly one of their own rows through each gated table, and only then shows B reading zero.

Forgery is tested, not only reading

Reading is the easy half. These are the writes the suite proves user B cannot make:

  • A provenance row carrying A’s user id.
  • Provenance attached to a place B does not own.
  • A save that borrows A’s source.
  • An invite token chosen by the client — and unknown, revoked and expired tokens fail identically, so a token cannot be probed for existence.

Sharing shares a place, not a library: a collaborator reads the shared place identity and none of the owner’s private note, provenance or aliases.

Every file was written failure-first

Each assertion was checked in both directions against a throwaway database: the control removed, the test seen to fail with the message it prints, the control restored.

A guard never seen to fail is not a guard.

Section 04 · invariants, executed

Database Integrity and Data Safeguards

“The database” means three things here, so it is tested three ways: authorisation, invariants executed rather than read, and a static gate on the posture of every new table.

Invariants are asserted by doing

The retention bound on captions is proved by executing a delete and asserting the rows are gone, not by confirming that a foreign key says it cascades.

The same file asserts absences — no coordinate column, no import reference — because a table that can quietly grow a location column is a privacy promise that decays.

A gate on the posture of every new table

One gate runs on every build because of a hazard a local database cannot show: hosted Postgres grants broad privileges on new tables to browser-reachable roles.

So a script refuses any migration that creates a table without enabling and forcing row-level security and revoking those grants in the same file.

The check that guards production is itself run in the pipeline, so it cannot drift from the migrations unnoticed.

What one failing test taught us

A privileged function does not protect a deferred constraint trigger. The queued check runs at commit under whatever role is in effect then, not the role that queued it.

It was ruled harmless only by proving, by execution, that the signed-in role cannot call the one function that inserts into the table concerned.

The layer guard is a test in its own right

It writes deliberate architecture violations, asserts the linter rejects each one, then removes them. It proves the rule can fail before trusting it to pass.

Section 05 · the thinnest layer

User Interface and Interactive Map Tests

This is the thinnest layer in the suite, and saying so is more useful than overstating it.

The interface is checked three ways, and each has a limit we can name:

  • Component render — markup and accessible name, from a static HTML string.
  • Pinned copy — the exact words of a screen, and the words banned from it.
  • A real browser — interaction, at both of our specified sizes.

Components rendered to a string

This catches the failure easiest to introduce and hardest to see. An approximate pin must stay visually distinguishable from a matched one, and must keep its screen-reader name.

A label replaces a button’s content, so a glyph inside it is then announced nowhere.

No component test here is evidence about layout, size or contrast, because a static string has no styling attached.

Copy is pinned where honesty depends on it

The no-places screen is asserted word for word against its specification, together with a ban on the words that would make it sound like an error.

The source-text weakness, stated rather than hidden

105 of the 250 unit files read source text and assert against it. That is a real weakness, and we would rather state it than hide it.

It is a legitimate way to prove an absence — that a screen contains no forbidden word, or that a module imports nothing from a layer it may not touch.

But it proves the code says something, not that the application does it. A change that keeps the string and breaks the behaviour passes.

Real interaction, at the real sizes

The shipped device presets are 412×839 and 1280×720; our design is specified at 390×844 and 1440×900, and 22 pixels is exactly the width at which a layout decides its column count.

So two extra browser projects exist only to assert the measurement conditions before anything is measured under them.

There is no screenshot comparison, deliberately. A pixel baseline on a product mid-redesign is re-approved on nearly every commit, which is the same as having no baseline while paying for one.

What no automated test here can tell you

No automated test here can tell you the map opened somewhere useful. An import that saved eight correct rows while the camera sat on another continent passes every assertion in the suite and is plainly broken.

That is why our working agreement requires running the application, using the feature and reading the saved rows before anything is called done.

Automation covers the failures we can describe; the rest we look at.
