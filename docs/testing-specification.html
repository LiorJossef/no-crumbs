Every figure here was counted on a clean run of the full suite on 6 September 2026, on the pull request CI passed immediately before the merge. Section 06 gives the command that reproduces each one.

The tooling is ordinary. There are four levels, and each one catches what the others cannot.

  • Unit and domain tests — 251 files, 4,137 tests, in Vitest. They reach every failure reason and every URL shape. Component tests render to a static HTML string in the same runner.
  • Browser tests — 13 specification files, 58 tests, in Playwright against the built application. They catch assembly: routing, focus, a double submission, a stale response.
  • Database policy tests — 8 files, 282 named checks, in plain SQL. The only place authorisation is executed as a second real user.
  • Manual drivers — 25 of them. A driver is a small script that works the real product from the outside — it drives a real browser, or calls a real third party, and then reports what it found — and it is run by hand because it spends a live quota or asks for a judgement no assertion can make.

Continuous integration runs all three automated levels on every pull request. Nothing runs again on the merge itself: the merge commit is the branch plus main, and the merge script refuses a branch that does not already contain current main, so only a combination CI has already passed can land.

Section 01

The Core Loop, and What Counts as Working

The product does one thing. A user pastes a TikTok link; it becomes a video identity, then a caption, then a structured extraction, then resolved real places, and finally rows on that user’s private map. The condition is that the import finishes every stage without inventing anything on the way.

1.1  What a successful import is

Success is not “every place resolved”. That is not the common outcome — most often the caption names no place at all, so “no places found” is a success state, with its own screen and its own tests. Treating it as an error would fail this specification whatever HTTP status came back.

Partial resolution counts too. If three candidates resolve and one does not, the import is complete: an unresolved name still tells the user something, a failure screen tells them nothing.

1.2  The pipeline test

One test drives the whole process. It runs the real import and the real link handling, and stands in for everything outside our control — TikTok, the caption reader, the model, the place lookup, the database — with a substitute we can steer. So it is fast, it is deterministic, and it can force situations a live run would give us only by luck.

It asserts the stages emit in order, that zero candidates ends on the no-places screen, and that partial resolution ends in success rather than failure.

1.3  When an import stops

An import that cannot finish stops for one of thirteen named reasons: the link was not a TikTok link, the platform is one we do not support, there was no link in the pasted text at all, the caption could not be read, the model did not answer, the user was not signed in, and so on. Each reason has its own message written for it. Nothing falls through to a generic failure.

Two tests keep that list honest, from opposite ends. The first runs the process until it has triggered every reason on the list, then checks that the set it managed to reach is exactly the set we declared — add a fourteenth reason and the suite fails until someone shows a real path to it. The second checks the reverse: every reason on the list must be raised somewhere in shipped code, so a reason nothing can cause is a failure rather than dead weight.

One reason is exempt today, by name: RATE_LIMITED_UPSTREAM has a screen and an HTTP status but nothing under src/ that raises it. The exemption is a list of exactly one entry, and two further tests hold it there — one asserts the list has a single member, so a second exemption cannot be added quietly, and one asserts the exempt code still has no producer, so the exemption expires by itself the moment somebody builds one.

1.4  The browser tests

Thirteen browser specifications drive the built application the way a person does — loading pages, pasting, clicking, waiting — rather than calling functions directly. Seven of them cover the import:

  • the happy path, all the way to a saved place;
  • the paste field refusing to submit until it holds a link;
  • the same link submitted twice, before the first attempt has returned;
  • a slow response arriving after the user has already changed the link;
  • the failure screens;
  • their wording;
  • and the status shown on screen against the status actually on the wire.

This is the level that catches assembly. Every part can pass on its own and the product still be broken by the way the parts are wired together: a route that does not exist, focus landing nowhere, a second click doing the work twice.

The signed-in tests need a password for the seeded demo account, and ten of the thirteen specifications skip themselves without one. In CI the run fails outright rather than skipping; on a developer machine it degrades to the signed-out tier, which is the right behaviour there — nobody needs a database up to check that the landing page renders. A setup step decides which of the two it is, so a run can never report green on the strength of tests that did not execute.

1.5  What this level does not show

It shows that an import finishes in a defined state, not that the answer is any good. Locking one caption to one expected place would lock in the output of a third-party model, and the test would then fail on a model upgrade that was an improvement. Extraction quality is measured separately, by hand, against a corpus of real saved videos.

1.6  Editing and deleting what you saved

Adding a place you cannot then undo is not something anybody would trust, so the writes that come after an import are tested too.

  • Every write a saved place accepts. Deleting one, deleting a selection, editing the note, changing the category, marking a place Been there. Each is checked against the exact statement sent to the database — which table, which columns, and nothing else.
  • Someone else’s row reads as gone, not as an error. The database answers a write you are not allowed to make with zero rows rather than a refusal, so the code has to ask for an exact count to tell the two apart.
  • No database error text reaches the user. What they see is a sentence we wrote.
  • Collections, the same way. Creating one, renaming it, deleting it, adding and removing a place. The checks that carry the most weight here are absences: no action works out for itself whether the user is allowed — that belongs to the database — and adding or removing a place never touches the saved places or the places themselves, so nothing here can cost somebody their library.
  • And once for real. A manual driver runs the delete and the note edit against the real application and the real database, reloading the page each time, so what it proves is that the change was written rather than that the screen redrew. It takes one viewport per invocation, so it is run twice: once at a phone width, once at a desktop width.

Section 02

Bad Input, and Edge Cases

The condition is that bad input is refused with a specific code the user can act on, and that a strange input is never turned into a confident wrong answer.

2.1  Two untrusted inputs

The pasted link is hostile: what the user submits decides an outbound request the server makes. The model’s reply is unreliable rather than hostile — well formed, and full of invented values. An allow-list for the first, a schema for the second.

2.2  The link

Only six hosts are allowed, and membership is decided by comparing the whole host. Never a suffix, never a substring. A parser matching anything ending in tiktok.com would pass every functional test and still be wrong: tiktok.com.evil.io ends in it, nottiktok.com contains it. Both are in the tests, with embedded credentials, an explicit port, an IP literal and any non-HTTP scheme.

Another test asserts the allow-list is that set of six and that the short-link resolver shares it, so a second adapter cannot quietly widen the boundary.

2.3  Refusals have to stay apart

An Instagram or YouTube link is a platform we do not support, not a broken link: it gets its own code and a route to adding the place by hand. Text with no link in it gets a different code and different copy. Collapse the two into one code and we tell the user to fix an input that was not broken, so the tests hold the two apart.

2.4  The model’s reply

Every reply is checked against a schema before anything is stored. Three things are refused outright:

  • A category outside our vocabulary. We can only draw the ones we have.
  • A latitude out of range. A number that cannot be a place on Earth.
  • A name that grows past its limit. It fits as typed, then exceeds the limit once its characters are written out in the standard form we store them in — accented letters and ligatures expand. The check in front of the write and the column behind it have to agree on the length, or a perfectly good name is refused at the last moment.

And two are accepted, carefully:

  • No coordinate, as long as the field is there. An explicit null says “no basis for a coordinate”; a missing field says nothing at all. They are not the same claim.
  • A reply cut off mid-list. We keep the candidates that parsed and record how many we dropped, so a partial answer is never shown as a complete one.

2.5  Edge cases

Each has a defined outcome, and that is the condition: a case that ends nowhere, or ends looking like an error when it is not one, fails.

Six sit in the import: no candidates at all, only some of them resolving, more candidates than the cap of eight, every location lookup failing, a model reply cut off mid-list, and a name that fits its length limit until it is normalised. Two are in the browser: the same link submitted twice before the first request returns, and a stale response arriving after the user changed the link.

2.6  When the place lookup is slow

Looking up a real place is the one step that waits on somebody else’s service, so it is held to five seconds. Past that the lookup is abandoned and reported as a timeout.

  • The deadline is tested by making it fire. Not a check that the number is written down somewhere — the lookup runs against a service that never answers, and the test waits for the timeout to happen.
  • A user pressing Back is not a slow provider. The two look identical to the code doing the fetching, so we ask the timeout directly rather than inferring it from the error.
  • A failed lookup does not fail the import. A place the model found in the caption is still saveable. The pin is labelled as coming from the caption rather than from a provider, and it is stored with no provider identity and no score attached to it.
  • Nothing is invented. When the model found nothing to place, no coordinate is produced at all.

A slow lookup costs the user some precision. It never costs them the import, and it never produces a confident location that nobody actually established.

Section 03

One User Cannot Reach Another User’s Map

Every map is private, so a failure here leaks data rather than degrading a feature. Signed in as a second real user, we attempt to read, update and delete the first user’s saved places, and assert every attempt returns nothing or is refused. We establish it by running the attack, not by reading the policy.

3.1  The tests run in the database

Authorisation is enforced by row-level security in Postgres, so that is where it is tested: eight SQL files carrying 282 named checks, raised by 588 assertion statements between them — a check is one labelled condition, such as P1, and several statements can defend it. Continuous integration rebuilds the schema from migration 0001 and runs all eight on every pull request.

All eight create at least two real users in auth.users and run the attacker’s queries under the attacker’s own role: set request.jwt.claims to their user id, then set local role authenticated. Those are the two steps PostgREST performs for a signed-in browser, so the attack is the real one. Each file runs in one transaction ending in ROLLBACK.

3.2  Prove the read works before proving it is blocked

“User B sees zero of user A’s rows” is also true of a database where nobody can read anything, so every file proves the positive case first.

The founding file does it in that order. First, user A has to see exactly one row through each of the six protected tables — the reads work. Only then is user B required to see none of A’s saved places, and B’s attempts to update and delete across A’s whole library required to change no rows at all. A failure prints what it actually saw, not just that it failed: FAIL P1: B sees 1 saved_places rows of A.

We checked these the other way round too. On a throwaway database we removed the rule that keeps a user’s saved places private, re-ran the file, and watched it fail with exactly that line. A control nobody has watched fail is not evidence.

3.3  Writes, not just reads

Read isolation is the easier half. The suite also inserts, as B, a provenance row carrying A’s user id; a provenance row attached to a place B does not own; and a save borrowing A’s source row. All three are refused, and the last is checked twice — once that it failed, once that it left no row behind in B’s library. Invite tokens cannot be chosen by the client, and an unknown, a revoked and an expired token all fail identically so nobody can probe for which tokens exist.

3.4  What a collaborator sees

Sharing gives access to a place, not to a library. A collaborator reads the shared place and none of the owner’s private note, provenance or aliases. That boundary is asserted field by field.

Section 04

The Database Keeps Its Promises

A database can be told to promise things — that deleting an account takes its data with it, that a table is not readable by a stranger. The condition here is that a promise counts only once we have watched it kept. We delete the account and then go looking for the rows, rather than reading the rule in the schema and concluding that they would have gone.

4.1  Promises proved by running them

We promise that caption text does not outlive the account it belongs to. So the test creates an account, saves data under it, deletes the account, and then goes looking for the rows that hung off it. They have to be gone. What it deliberately does not do is read the schema, see that a cascading delete is declared there, and call that evidence.

The same test also asserts a set of absences: this table has no coordinate column, and no reference back to an import. Asserting that something does not exist reads oddly at first, but a table that quietly acquires a location column two migrations later is a privacy promise decaying with nobody noticing.

4.2  New tables arrive open

Hosted Postgres is generous by default. A table created by a migration is readable by the public web role until that migration explicitly takes the privilege away. Worse, a local database will not show you the mistake — the row-level rules pass either way — so no amount of policy testing catches it.

So it is caught before it ships instead. A script reads every migration and rejects any that creates a table or view without locking it down first. It runs alongside the ordinary checks, on every change.

Section 05

The Screens

The condition is that anything the eye can tell apart, a screen reader can tell apart too, and that pinned copy matches its specification word for word. This is the least complete level of the suite, and the last subsection says what it misses.

5.1  Component render

Components are rendered to HTML and checked for their markup and for the name a screen reader would announce. The case worth naming: when we are unsure of a place’s exact location, the row’s accessible name ends in “approximate location”, and when the location is a confirmed match it does not — so the uncertainty reaches someone who cannot see the row at all.

That is easy to lose by accident, because an aria-label replaces everything inside the element it sits on: anything shown inside is then announced nowhere. No styling is applied at this level, so these tests say nothing about layout or size. Colour separation between categories is asserted separately, as a unit test over the palette values themselves:

  • The pair that was actually broken. Café and restaurant once sat close enough to read as two shades of the same red on a 26 pixel pin. The test now requires a colour difference above 18 and at least 8 points of lightness between them — lightness because that is the axis that survives both a small disc and a red-green deficiency.
  • And every other pair. The same floor is asserted across every pair in the palette, including the uncategorised colour, so the next category added cannot land on top of an existing one.

5.2  Copy and viewport

Two smaller checks sit alongside, both about things that drift silently.

The first pins wording. The “no places found” screen is compared word for word against its copy specification in all three of its cases — no caption at all, a caption that named nothing, an area but not the place itself — together with a ban on the vocabulary that would make it read as an error.

The second pins the window. Two browser runs assert nothing but that the viewport is the size the design is specified at, before anything is measured inside it — a layout checked at the wrong width is checked against the wrong set of columns.

5.3  What automation does not cover

No test here shows the map opened somewhere useful. An import that saved eight correct places while the camera sat on another continent passes everything in this suite and is obviously broken to anyone looking at it.

Screenshot comparison is deliberately excluded: a pixel baseline against a product still being redesigned needs re-approving on nearly every change, which costs real maintenance and buys almost no evidence. Instead the rule is that the app is run, the feature used and the saved rows read before a change is accepted.

Section 06

Running the Suite

Everything below is run from the repository root.

6.1  The commands

CommandWhat it runs
npm run testThe unit and component tests
npm run test:e2eThe browser tests
npm run db:testThe eight SQL policy files, each in a transaction that rolls back
npm run verifyLint, the TypeScript check, the repository gates and the unit tests
npm run db:inventoryThe deployed database grants against the designed ones. Read-only, so it is safe against production

Set E2E_PASSWORD for the seeded demo user before running the browser tests. Without it the signed-in tier skips locally and fails the job in CI (§1.4).

6.2  Where everything lives

Unit and component tests are in tests/unit/, browser specifications in tests/e2e/, and the eight database policy files in supabase/tests/, numbered after the migration each one guards. What those eight cover is set out in sections 03 and 04 and is not repeated here.

Manual drivers are in tests/manual/, kept out of the automated run for the reasons given above. Two of them drive the running app and read back the rows they saved — import-e2e.manual.mjs and crud-e2e.manual.mjs, the second run once per viewport — and owner-corpus.manual.ts is where extraction quality is measured against a corpus of real videos.
