01 · The problem

A folder sorted by when, when the question is always where.

People save videos of places constantly. The save is instant and the retrieval is impossible: the folder is ordered by the moment you tapped it, and a bakery you saved in March is five hundred videos down from the day you are standing outside it.

Ordered byTime. Never by where you are.
Searchable byThe caption's words — not the place's name, and not its location.
SurvivesOnly as long as the account and the post do.

The realistic outcome is not a slow search. It is no search at all — and dinner somewhere you never saved.

That is the loss this product addresses. Not storage, and not elapsed seconds, but a decision made without the thing you deliberately kept.

02 · The solution

One paste, one confirmation. Everything else is ours.

The exchange

You giveOne link, and a tap to confirm.
You getA permanent, private, location-indexed library of places you chose — retrievable in seconds, each keeping the post that recommended it.
Get it inThe app reads the post. Any link shape, nothing tidied up first, and a caption that names no place is a screen rather than a failure.
Decide & keepNothing is saved until you confirm it. One venue is one pin however many videos name it, and the link back can never be lost.
Get it backThe map is home. Three zoom tiers, a list that always agrees with the pins, and a sentence that filters what is there without inventing anything.

03 · Architecture

Four layers, one direction, no way back up.

A single Next.js application. Every import is the same five stages, run on the server, and the domain layer has no outgoing edge — it cannot reach the network or the database, so the rules stay testable in isolation.

04 · Security

Your map is private because the data refuses to be read.

Not because each screen remembers to check. Isolation is enforced in Postgres, on every table, under a policy that is forced even for the table's owner — so a route that forgets its filter returns nothing rather than everything.

The keyThe privileged database key never reaches the browser. The module that reads it is server-only, its name carries no public prefix so it cannot be inlined into a bundle, and every caller identifies the user first.
SharingPeople you share with see the places. Not your note, your tags, your Been marks, or the video you saved it from.

The stance on untrusted text

A caption is words to read, never instructions to follow.

The words belong to somebody else. They are treated that way at every boundary they cross — including the one into the language model.

05 · Scalability

The ceiling is a quota, not the database.

Load scales with imports, not with accounts. Every read is scoped to one person at the index, so a hundredth user adds rows no query ever walks. What runs out first is a third-party allowance — and that is a billing decision.

Cost axisOne import is three external calls. User count is not the axis.
No queueBy decision, not omission. No job outlives its request, and the four tables a queue would have needed already exist as caches inside the source of truth.
The map readFetches the whole library once and bounds the drawing, not the fetching — so the list, the pins and search can never disagree.

Every limit ships with the condition that makes the work worth doing

NowProvider quota — 100 lookups a day. Raise it, and add a per-user cap in the same change.
LaterMap payload, once a library passes a few hundred places. The index a paginated read needs is already in the schema.
WatchOne missing index on a globally growing table. A few thousand rows, and one line to fix.

None of that is “the database at hundreds of users”. That is the headline worth taking away: the architecture is not what limits this product today.

06 · Testing

Every control is proved by making it fail first.

A policy test that only ever passes proves nothing — it might be asserting against a table that is empty. Each one here denies before it allows, so a green result means the rule fired, not that nothing happened.

07 · What comes next

In order, and for a stated reason.

Not a wish list. Each item is the remediation for a limit that has already been measured, sequenced by the condition that triggers it.

FirstRaise the provider quota and add a per-user daily cap together — so one person cannot spend everyone's allowance.
ThenSet a maximum duration, and build the streaming import route that was specified and cut — turning the longest request in the product into visible progress.
At scalePagination and a viewport read, once a library passes a few hundred places, keeping the bounds query the camera needs.
CleanupMake the collections read an aggregate, add the missing index, and drop the one that earns nothing.

We would still not add a queue, or a cache server. No job outlives its request — and the day one does, the schema for it is already there.
