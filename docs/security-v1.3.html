Section 01

Authentication & Session State

Signing in is handled by Supabase. We never see a password, never hash one, and never store one.

1.1  How signing in works

There is one sign-in screen. It calls Supabase Auth to sign a user up or in with an email and password, and nothing else in the codebase authenticates anybody. The password goes from the browser to Supabase directly; our server never handles it.

Account records live in Supabase’s own auth schema, which no browser-facing database role may read, so a user’s email cannot be reached through the data API. This is the ordinary, correct arrangement: we did not build our own authentication, because password hashing, reset emails and token rotation are bad things to hand-roll.

1.2  How a session works

After sign-in the browser holds a cookie containing an access token. The token is valid for one hour, and a refresh token renews it.

We write that cookie through our own small adapter for one reason: the Supabase library sets a 400-day cookie by default. If the user does not tick “remember me”, our adapter leaves the expiry off, so the cookie dies when the browser closes. A delete instruction from the library is honoured either way.

1.3  Where identity is checked

The Supabase client offers two calls that look similar and are not. getSession() decodes the token the browser is holding without asking the auth server whether it is real. getUser() sends it to the auth server and gets a verified answer back.

Only getUser() may decide access. It runs in the request proxy, on every page that renders a user’s data, in every API route and in every server action. getSession() appears in exactly one place — the sign-in screen, deciding whether to show an email-confirmation prompt, which is not an access decision. Identity is always checked on the server; the browser is never believed about who it is.

1.4  What you must be signed in to do

The product has one kind of user — no administrator, no moderator, no support login — so authorisation is mostly one question: does this row belong to you? Shared collections add a second, are you a member, and that is the only exception.

Open to anyoneRequires being signed in
Landing, sign-in and sign-up, password resetThe map, importing a link, collections, profile, account
An invite link — a generic screen naming neither the collection nor its ownerAccepting that invite
Nothing else: no public profile, no public collection, no guest view of a mapEvery read and every write of real data

Each signed-in page checks identity itself and redirects if there is none. Every write goes through a server action — saving a place, editing its note or category, marking it visited, deleting it, everything in collections, manual add, account rename and deletion — and each calls getUser() before touching data. The one exception is sign-out, which ends a session rather than reading one.

Section 02

Row-Level Security & User Map Isolation

Your map is private, and the database is what makes it private. Not our application code.

2.1  How authorisation works

Postgres row-level security lets you attach a rule to a table. Postgres applies that rule to every query touching the table and combines it with whatever the caller asked for. A caller can narrow a result set; a caller cannot widen one.

Nearly every rule here says the same thing: the row’s owner column must equal the signed-in user. Ask for someone else’s rows and you get zero back, because your condition is joined to one you cannot remove.

Shared collections are the exception. There the caller is not the owner, so the rule asks whether they hold a live role in the collection, or have already saved the place being referenced. We say that openly rather than claiming every rule is a simple ownership test, because sharing is the point of that feature. All 38 policies are written for the signed-in role; none for the anonymous role.

2.2  Why the database, and not our code

Row-level security is enabled on all 17 tables, and forced on all 17. The difference matters: merely enabled, the role that owns a table is exempt from that table’s own rules. Forcing removes the exemption, so the rules bind everybody. Three tables carry row-level security with no policy at all — the strongest setting there is, since there is nothing to satisfy.

The anonymous role, which a browser holds before signing in, has no privileges on any table, column or function — across all 36 migrations it is only ever revoked from. That is why the publishable Supabase key sitting in the browser bundle is not a leak: it names the project and grants nothing. Access is decided by policy, not by keeping a key secret.

Two mechanisms sit underneath. Grants are made column by column: on your own saved place you may update the display name, category, note, visit state and visit date, and nothing else. There is no grant on the owner column, so moving a saved place into another account is not a request that can even be expressed. And on tables shared between accounts users hold no write privilege at all — writes go through SECURITY DEFINER functions, which run with the table owner’s rights but re-check the caller’s identity inside themselves first.

The point is simple: if we forgot a check or wrote the wrong filter in application code, the database would still refuse. The page renders an empty list, not somebody else’s places.

2.3  What happened when we attacked it

We did not take that on trust. We built a database with every migration applied, created two users, gave one saved places and a collection, then signed in as the other and attacked. We tried reading the victim’s saved places directly, and sideways through the tables they join to. We tried counting them, in case an aggregate revealed what a select would not. We tried updating them, deleting them, and reassigning one into the attacker’s account. We tried taking over the victim’s collection, by writing ourselves in as owner and by choosing our own invite token. We called every stored function a signed-in user may call, aimed at the victim’s rows. Then we repeated all of it with no account at all.

Every read returned zero rows. Every write was refused. The reassignment and the collection takeover failed before any policy was consulted, because those columns carry no grant. The functions refused with no such saved place for this user. Signed out, everything failed a step earlier still, at permission denied for table — the anonymous role has nothing for a policy to be evaluated against.

Eight SQL suites keep this honest as the schema changes: each creates its own users, tries the cross-user read, write and delete, and rolls back.

One property does favour an attacker and we document it rather than hide it. If you already know a venue’s id, saving it lets you read that shared venue row. We accept that: the ids are random 128-bit values nobody can guess, the row holds open, non-personal place data, and the column grants mean it leads to nothing belonging to a user.

Section 03

Input Sanitization & External Link Defense

Three things arrive that we did not write: the request body, the TikTok link, and whatever the language model says. All three are treated as hostile.

3.1  How input is validated

Validation is not uniform, and we would rather say so than round it up. Five places parse input against an explicit Zod schema: the import-confirm request body, TikTok’s oEmbed response, the language model’s output, and two that re-parse rows read back from our own database. Those are the boundaries where a value arrives with real structure.

The other five API routes take two or three flat fields and are checked field by field instead: every value type-tested, empty values rejected, free text length-capped, all before any external call. Same protection, simpler mechanism — but a different one, and a reader should not have to open the file to learn which is which.

Underneath, every table constrains its own columns with check constraints, so value ranges, allowed states and a row’s internal consistency are enforced by Postgres whatever code path produced the row.

3.2  Validation is not always enough

One defect shows what schema validation cannot do. The import-confirm route used to accept the place itself from the browser — name, latitude, longitude, provider id — and pass it to a function that refreshes a venue. Venue rows are shared by everyone who saved that venue and nothing checked who was asking, so one ordinary signed-in request could rename and move another user’s venue. We confirmed it by doing it: one request renamed a Tel Aviv café and moved it to the Eiffel Tower.

A stricter schema would not have helped, because no schema can tell a true latitude from a malicious one. We changed who is trusted instead: the request now sends only an extraction id, indexes into the candidate list the server itself produced, and the user’s own note. An extraction belonging to another account is rejected on an ownership check, an index outside the list as out of range.

3.3  The pasted link

The pasted link is the only user input that makes our server open an outbound connection, so it is our whole server-side request forgery surface. We parse it with the WHATWG URL parser and reject the following before any request is sent.

RejectedWhat that prevents
Any scheme other than http or httpsfile, ftp and data URLs reaching the fetcher
A username or password in the URLHiding the real host behind a trusted-looking prefix

Any host not exactly equal to one of six TikTok hostnamesLook-alike domains — we compare for equality, never by suffix, so tiktok.com.evil.io is refused like any other stranger

Short links redirect, so we follow redirects ourselves with redirect: 'manual' rather than letting fetch do it: every Location header goes through the same checks before we follow it, with five hops maximum, and no HTML parsed at any point. Both import routes redo the whole check on the server whatever the client did.

3.4  What the model says

The language model is untrusted on the same terms as the link. Its output is parsed against a Zod schema, every claim must quote the caption it came from before a user sees it, and the difference between what the caption said and what the model inferred survives to the review screen — so the user confirms a place rather than inheriting a guess.

Section 04

API Protection & Secrets Management

Six API routes, all POST-only, each one identifying the caller before it does anything else.

4.1  How API calls are protected

There are six route handlers under /api. Each starts by calling getUser() and returns 401 if there is no verified user. All six export POST and no other method — partly convention, partly a cross-site request forgery control, since a GET handler can be triggered from another site with an image tag and a JSON POST cannot. Most of the product has no API surface at all: pages load their data on the server under the signed-in user’s own token, so those reads meet the policies in section 2 like everything else.

On failure a route returns a short code from a closed set and nothing else — no provider message, no upstream status code, no stack trace, no environment-variable name. Detail goes to the server log, which records codes and counts, never captions and never coordinates. Every response carries these headers.

HeaderWhat it stops
X-Content-Type-Options: nosniffA response being interpreted as a type it did not declare
Content-Security-Policy: frame-ancestors 'none'Clickjacking — no other site may put our map in an iframe
Referrer-Policy, tightened to no-referrer on the invite-join routeThe invite token, which sits in the URL path, leaking to another site
Permissions-PolicyEmbedded content taking capabilities: geolocation is allowed to our own origin, camera, microphone and payment are denied

This policy covers framing and embedding only. It has no script-source directive, which is a real gap and is listed in 5.2.

4.2  Where secrets are kept

All secrets are environment variables. The .env files are gitignored, only an example with empty values is committed, and in production the real values live in Vercel’s encrypted environment store.

The rule is one line: a variable without the NEXT_PUBLIC_ prefix must never reach the browser. Two things enforce it rather than our memory. Next.js inlines only prefixed variables into client code, so an unprefixed one is absent from the bundle; and every importable module that reads a secret imports server-only, so importing it from a client component is a build failure rather than a shipped credential.

The Supabase service-role key bypasses row-level security completely, so nothing in section 2 restrains a query made with it. We use it on the server only, for account deletion and writes to shared tables; it is never in the bundle, the repository or an error response.

One variable is awkward, so we name it. The Google Maps key carries the public prefix but is read only as a server-side fallback for place lookup, inside a server-only module. No client code references it, so it is not in the bundle — but the prefix means it would be inlined the moment some did, and unlike the publishable Supabase key this one costs money. Its protection is a referrer restriction set at Google, not secrecy.

Section 05

Known Risks & Security Hardening

We found no way for one user to reach another user’s data. That statement is only as wide as the attacks in 2.3, and these are the weaknesses we know about.

5.1  Location data, and deleting your account

This is a map, so it is fair to ask what it knows about where you are. Nothing. “Near me” reads your position from the browser, centres and sorts the list on your own device, and sends it nowhere — no API route, no server action, no column. The only coordinates we store are the venue’s own, on a shared row built from open data. A saved place says where you want to go, not where you have been.

Deleting your account is built, not promised. It removes the account and the database does the rest through on delete cascade: saved places, source links, imports, mentions, your profile and name, collections you own and memberships you hold all go with it.

It refuses in one case. If you are the live owner of a collection that still has another live member, deletion is blocked and the screen names the collections in the way — the same cascade would delete that collection for everyone in it, and erasing your data must not erase somebody else’s. One thing survives deliberately: the cached caption of a public TikTok post, which carries no user identifier and is shared by everyone importing the same link. That is the retention gap below.

5.2  What is still weak

These are real and open. Each is graded for what this deployment is — a course project with sign-up closed and no public users — and each names the condition that would end the acceptance.

5.3  What we would do next

Run the eight SQL suites on every push rather than on demand: the attacks in 2.3 prove something about the database we tested, not the one six migrations from now. Then the import rate limit, which is the first acceptance to expire — the thing that ends it is a configuration change, not a piece of work.
