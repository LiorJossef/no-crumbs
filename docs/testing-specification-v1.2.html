Testing
Specification

Abstract. What “working” means for No Crumbs, and how each part of it is checked. Every section says what would count as working, what would count as broken, and what it cannot detect. Section 06 has the commands.

5 test levels 4,087 unit tests 58 browser tests 277 policy assertions

Every figure here was counted at commit 601cebf, or against continuous-integration run 33912752591 of 4 September 2026, which gated it into main. Section 06 gives the command that reproduces each one.

The tooling is ordinary. Unit and domain tests run in Vitest — 250 files, 4,087 tests — and component tests render to a static HTML string in the same runner. Browser tests run in Playwright against the built application: 13 specification files, 58 tests. Database policy tests are plain SQL run by psql: 8 files, 277 assertions. Continuous integration runs all three on every pull request and every push to main. A fourth level, 23 documented manual drivers, covers what needs a live third party or a human judgement.

Each catches what the others cannot. The unit tests reach every error code and every URL shape; the browser tests catch assembly — routing, focus, a double submission, a stale response; the SQL tests are the only place authorisation is executed as a second real user.

Section 01

The Import, and What Counts as Working

The product does one thing. A user pastes a TikTok link; it becomes a video identity, then a caption, then a structured extraction, then resolved real places, and finally rows on that user’s private map. The condition is that the import finishes every stage without inventing anything on the way.

1.1  What a successful import is

Success is not “every place resolved”. That is not the common outcome — most often the caption names no place at all, so “no places found” is a success state, with its own screen and its own tests. Treating it as an error would fail this specification whatever HTTP status came back.

Partial resolution counts too. If three candidates resolve and one does not, the import is complete: an unresolved name still tells the user something, a failure screen tells them nothing.

1.2  The pipeline test

One file drives the whole process: tests/unit/import/pipeline.test.ts. It is a Vitest file at the unit level. It calls the real runImport generator and the real URL canonicaliser, and supplies every adapter — TikTok source, caption reader, model, place resolver, store — as a mocked port. It is not a browser test.

It asserts the stages emit in order, that zero candidates ends on the no-places screen, and that partial resolution ends in success rather than failure.

1.3  The error codes

Thirteen error codes are defined in src/domain/errors.ts, and the list is asserted closed. The pipeline test reaches twelve of them through real code paths and the thirteenth, NOT_AUTHENTICATED, at the route handler that raises it in production. It records each code as it goes, then asserts the set it reached is exactly the set declared — so a fourteenth code fails the suite until a path to it is shown.

tests/unit/errors-have-producers.test.ts closes the other end: every code must be constructed somewhere under src/, so a code nothing can raise is a failure rather than dead weight.

1.4  The browser tests

Thirteen Playwright specifications drive the built application, seven of them the import flow: the happy path, the paste gate, a double submission, a stale response arriving after the user changed the link, the failure screens, the error copy, and the status shown against the status on the wire. In the run cited above, 56 passed and 2 skipped, both on viewport rather than credentials.

That distinction had to be earned: the pipeline once set no E2E_PASSWORD, so most of the suite skipped on every run and the check still went green. tests/e2e/global-setup.ts now fails the job outright when a skip would be dishonest. Locally, without E2E_PASSWORD, the signed-in tests skip by design and only the signed-out ones run.

1.5  What this level does not show

It shows the import finishes in a defined state, not that the result is any good. Pinning one caption to one venue would pin the output of a third-party model and break on an upgrade that was an improvement, so extraction quality is measured by the manual drivers in section 06 instead.

Section 02

Bad Input, and Edge Cases

The condition is that bad input is refused with a specific code the user can act on, and that a strange input is never turned into a confident wrong answer.

2.1  Two untrusted inputs

The pasted link is hostile: what the user submits decides an outbound request the server makes. The model’s reply is unreliable rather than hostile — well formed, and full of invented values. An allow-list for the first, a schema for the second.

2.2  The link

Only six hosts are allowed, and membership is decided by comparing the whole host. Never a suffix, never a substring. A parser matching anything ending in tiktok.com would pass every functional test and still be wrong: tiktok.com.evil.io ends in it, nottiktok.com contains it. Both are in the tests, with embedded credentials, an explicit port, an IP literal and any non-HTTP scheme.

Another test asserts the allow-list is that set of six and that the short-link resolver shares it, so a second adapter cannot quietly widen the boundary. All of it is in tests/unit/source/canonicalise-tiktok-url.test.ts.

2.3  Refusals have to stay apart

An Instagram or YouTube link is a platform we do not support, not a broken link: it gets its own code and a route to adding the place by hand. Text with no link in it gets a different code and different copy. Collapse the two into one code and we tell the user to fix an input that was not broken, so tests/unit/source/extract-pasted-url.test.ts holds them apart.

2.4  The model’s reply

Every reply is checked against a schema before anything is stored. A category outside our vocabulary is rejected, so is a latitude out of range, and so is a string that fits its length limit as written but exceeds it once NFKC-normalised — normalisation expands some characters, and the two sides of a write have to agree.

Null coordinates are accepted, but the field must be present: an explicit null says “no basis for a coordinate”, a missing field says nothing at all, and they are not the same claim. When a reply is cut off mid-list we keep the candidates that parsed and record how many we dropped, so a partial answer is never shown as a complete one. Both are in tests/unit/extraction/schema.test.ts and partial-parse.test.ts.

2.5  Edge cases

Each has a defined outcome, and that is the condition: a case that ends nowhere, or ends looking like an error when it is not one, fails.

Six sit in the import and are covered by tests/unit/import/pipeline.test.ts and tests/unit/extraction/: zero candidates, partial resolution, more candidates than the cap of eight, every resolver lookup failing, a reply truncated mid-list, and a string that fits its length bound until it is normalised. Two are in the browser: the same link submitted twice before the first request returns, and a stale response arriving after the user changed the link. One is in the database: a deferred constraint trigger firing at commit time under a different role from the one that queued it.

Section 03

One User Cannot Reach Another User’s Map

Every map is private, so a failure here leaks data rather than degrading a feature. Signed in as a second real user, we attempt to read, update and delete the first user’s saved places, and assert every attempt returns nothing or is refused. We establish it by running the attack, not by reading the policy.

3.1  The tests run in the database

Authorisation is enforced by row-level security in Postgres, so that is where it is tested: eight SQL files in supabase/tests/ carrying 277 assertions. Continuous integration rebuilds the schema from migration 0001 and runs all eight on every pull request and every push to main.

All eight create at least two real users in auth.users and run the attacker’s queries under the attacker’s own role: set request.jwt.claims to their user id, then set local role authenticated. Those are the two steps PostgREST performs for a signed-in browser, so the attack is the real one. Each file runs in one transaction ending in ROLLBACK.

3.2  Prove the read works before proving it is blocked

“User B sees zero of user A’s rows” is also true of a database where nobody can read anything, so every file proves the positive case first.

In supabase/tests/0008_policy_tests.sql, run by npm run db:test:0008: assertion P0b requires A to see exactly one row through each of the six gated tables. Only then does P1 require B to see zero saved_places, and P4 that B’s unqualified update and delete against A’s library change no rows. A failure prints what it saw: FAIL P1: B sees 1 saved_places rows of A.

We checked these the other way round too: drop the saved_places_select_own policy on a throwaway database and P1 fails with exactly that line. A control nobody has watched fail is not evidence.

3.3  Writes, not just reads

Read isolation is the easier half. The suite also inserts, as B, a provenance row carrying A’s user id; a provenance row attached to a place B does not own; and a save borrowing A’s source row. All three are refused, and the last is checked twice — once that it failed, once that it left no row behind in B’s library. Invite tokens cannot be chosen by the client, and an unknown, a revoked and an expired token all fail identically so nobody can probe for which tokens exist.

3.4  What a collaborator sees

Sharing gives access to a place, not to a library. A collaborator reads the shared place and none of the owner’s private note, provenance or aliases. That boundary is asserted field by field.

Section 04

The Database Keeps Its Promises

The condition is that a guarantee counts only once it has been executed: a deletion actually performed and the dependent rows observed gone, never a foreign key read as evidence of what it would do.

4.1  Promises proved by running them

We promise caption text does not outlive the account it belongs to. The test deletes a profile and asserts the dependent rows are gone, rather than checking that a foreign key is declared to cascade.

The same file asserts a set of absences — no coordinate column, no import reference — because a table that can quietly acquire a location column is a privacy promise decaying over later migrations. Both are in supabase/tests/0031_place_mentions_policy_tests.sql.

4.2  New tables arrive open

Hosted Postgres grants broad privileges on new tables to the roles a browser can reach, so a new table is readable by anon until a migration revokes it. A local database does not show you this, because row-level security passes either way, and no policy test can catch it.

So it is checked statically: scripts/check-migration-grants.sh rejects any migration creating a table or view without forcing row-level security and revoking those grants. It runs as npm run check:migrations, inside npm run verify and inside continuous integration.

4.3  The layer guard checks itself

The rule keeping input and output out of src/domain/ is enforced by ESLint. scripts/check-layer-guard.sh writes four deliberate violations into src/, asserts ESLint rejects each, then removes them — a rule nobody has watched fail is not relied on to pass.

Section 05

The Screens

The condition is that anything the eye can tell apart, a screen reader can tell apart too, and that pinned copy matches its specification word for word. This is the least complete level of the suite, and the last subsection says what it misses.

5.1  Component render

Components are rendered to a static HTML string and the markup and accessible name asserted. The case worth naming: a pin we are unsure about must look different from a matched pin and keep its screen-reader name.

That is easy to break: an aria-label replaces a button’s contents, so a glyph inside it is announced nowhere. tests/unit/sheet/place-row.test.ts asserts the accessible name ends in “approximate location” when the pin is a guess and does not contain it when the pin is matched. No styling is applied here, so nothing follows about layout, size or contrast.

5.2  Pinned copy

The no-places screen is asserted word for word against its copy specification in tests/unit/import/no-places-screen.test.ts, in all three of its cases — no caption, a caption that named nothing, an area but no venue — together with a ban on the vocabulary that would make it read as an error.

5.3  Viewport gates

Playwright’s device presets are 412×839 and 1280×720. Our design is specified at 390×844 and 1440×900, and the 22-pixel difference lands exactly where the layout picks its column count. Two extra browser projects exist only to assert the viewport before anything is measured in it.

5.4  What automation does not cover

No test here shows the map opened somewhere useful. An import that saved eight correct rows while the camera sat on another continent passes everything in this suite and is obviously broken.

Screenshot comparison is deliberately excluded: a pixel baseline against a product mid-redesign needs re-approval on nearly every commit, costing the maintenance of a baseline and buying the evidence of none. Instead the working agreement requires the app to be run, the feature used and the saved rows read before a change is accepted.

6.3  Where everything lives

Unit and component tests are in tests/unit/, browser specifications in tests/e2e/ with the viewport gates in tests/e2e/gates/, and policy tests in supabase/tests/. Manual drivers are in tests/manual/, named *.manual.* and kept out of npm run test by vitest.config.ts, because each spends a real quota, drives a real browser, or asks for a judgement no assertion can make. import-e2e.manual.mjs and crud-e2e.manual.mjs drive the running app and read back the rows they saved; owner-corpus.manual.ts is where extraction quality is measured.
