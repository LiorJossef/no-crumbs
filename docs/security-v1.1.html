Security
Analysis

Abstract. This document examines the security posture of the No Crumbs system. The threat surface comprises four boundaries: identity and session state, cross-user data isolation, untrusted input arriving from the browser and from external services, and the containment of credentials. For each boundary the document states the control that enforces it, the mechanism by which the control is enforced, and the residual risk that remains. Section 1 covers authentication and session validation; section 2 covers row-level security and the privilege model that isolates one user’s data from another’s; section 3 covers schema validation, the place-authority correction and the server-side request forgery gate; section 4 covers route protection, error disclosure and secret classification; section 5 states the attacks executed against the system, their outcomes, and the six residual risks accepted for a coursework deployment together with the condition that would withdraw each acceptance. Every count in this document was measured from the 36 migrations and from the application source.

Section 01

Authentication & Session State

Sign-in is delegated to the authentication provider. The application does not receive, hash or store a password at any point.

1.1  Authentication surface

Authentication is confined to a single screen, which calls either sign-up or sign-in. No other module in the codebase authenticates a user.

Account records reside in the authentication provider’s own schema, which no browser-facing database role may read. A user’s email address is consequently not reachable through the product’s data API. The absence of any grant to the browser-facing anonymous role is stated in section 2.3.

1.2  Session lifetime and cookie persistence

The session is carried in a cookie holding an access token with a one-hour lifetime, under refresh-token rotation.

Persistence is controlled by a custom cookie adapter. When the “remember me” option is not selected, the adapter omits the expiry attribute, so the cookie is discarded when the browser session ends rather than persisting for the client library’s default of 400 days. A deletion instruction from the library, expressed as a zero lifetime, is honoured in both modes.

1.3  Session validation

The client library exposes two calls with different trust properties. One decodes the token presented by the browser without contacting the authentication server; the other validates the token upstream. Only the second is permitted to determine access.

CallTrust propertyOccurrencesWhere it is used
Validating callToken verified against the authentication server31 sites in 21 filesThe request proxy, every page rendering user data, every API route and every server action
Decoding callAccepts the browser’s assertion without verification1 siteThe sign-in screen only, to decide whether to display an email-confirmation prompt

1.4  Layering of controls

Access control is applied at three layers, and each layer is independently sufficient to deny an unauthorised read.

LayerControlEffect on an anonymous request for another user’s map
Request proxySession refresh on every page request; redirect to sign-in for the map routeRedirected before any component renders
PageEach page performs its own validating callRedirected before any query is issued
DatabaseRow-level security, described in section 2Zero rows returned

The proxy’s route matcher is written as a negative lookahead covering every page, with route handlers, the liveness endpoint and static assets excluded by pattern. A new page is therefore covered on the day it is created, without an enumerated route list requiring maintenance. Per-page validation is retained regardless, because the proxy’s purpose is session refresh and redirection rather than final authorisation.

If every application-layer control were removed, the database would still refuse the request. The page would render an empty list rather than another user’s data.

Section 02

Row-Level Security & User Map Isolation

Read and write authorisation is determined by Postgres row-level security rather than by conditional logic in application code.

2.1  The isolation predicate

Row-level security attaches a predicate to a table and applies it to every query touching that table. The predicate used throughout this schema is a single condition: the row’s owner must equal the identity of the caller.

Postgres conjoins that predicate with the caller’s own filter, so a caller-supplied condition can only narrow the result set. A query naming another user’s identifier returns zero rows.

All 17 tables in the public schema have row-level security both enabled and forced. Forcing is material: without it, a table’s owning role is exempt from the table’s own policies.

2.3  Privileges of the anonymous role

The anonymous role holds no privilege on any table in the public schema. Across the 36 migrations it receives no grant, only revokes.

This is why shipping the publishable key in the browser bundle is not a disclosure. That key identifies the project and confers no access; authorisation is determined by the database’s policies rather than by the secrecy of the key. The privileged key, which does bypass policy evaluation, is governed by section 4.5.

2.4  Privileged functions on shared tables

Users hold no insert, update or delete privilege on the tables shared between accounts. Writes to those tables are performed by SECURITY DEFINER functions executing with the owning role’s rights.

There are 20 such functions. 13 are executable by a signed-in user, and 7 of those perform writes. The arrangement is deliberate: for a user’s tags and for model-authored prose, the function is the write path rather than a convenience over one.

Each function derives the caller’s identity from the session inside its own filter and refuses a row belonging to another account. The three functions added most recently — those covering tags and model-authored prose — follow the same pattern; two further definer functions are granted only to the privileged role and are unreachable from a user session.

2.5  Column-level grants

Privileges are granted column by column. Where a column carries no grant, the corresponding attack is not expressible rather than merely refused.

A user may update exactly five columns of their own saved place: the display name, the category override, the note, the visit state and the visit timestamp. The owner column, the venue reference and the origin reference are not among them. An attempt to reassign a saved place to another account therefore fails at the privilege layer, before any policy is evaluated.

2.6  Verification of the isolation properties

Eight SQL suites verify the isolation properties by execution rather than by assertion. Each suite runs as a single transaction that creates its own users, attempts the cross-user read, write and delete, and rolls back. The corresponding assertion counts are recorded in the testing specification.

The attacks executed against a running system, and their outcomes, are stated in section 5.1.

Section 03

Input Sanitization & External Link Defense

Every value crossing a trust boundary is parsed against a schema before use. At the import-confirm boundary the control is stronger than validation: the browser is no longer the authority for the data in question.

3.1  Schema validation at boundaries

Request bodies, external service responses and rows read back from the system’s own database are each parsed against an explicit schema before use. Validation of a value’s shape is a necessary control but not a sufficient one, for the reason set out in section 3.2.

3.2  Authority for place data at the import-confirm boundary

The import-confirm endpoint previously accepted the place record itself — name, latitude, longitude and provider identifier — and passed it to a function that refreshes a venue’s details.

Venue rows are shared between every account that has saved that venue, and no check established which account was making the request. A single ordinary signed-in request was therefore able to rename and relocate a venue saved by other users. The defect was confirmed by execution against a local database: one request renamed a Tel Aviv café and relocated it to the coordinates of the Eiffel Tower.

A stricter schema would not have closed the defect, because no schema can distinguish a truthful latitude from a malicious one. The correction changed the authority rather than the validation rule. The request now carries an extraction identifier, indices into the candidate list that the server itself produced, and the user’s own note. Place facts no longer travel from the browser.

Field accepted from the browserHostile value it permitsOutcome
Extraction identifierAn extraction belonging to another accountrefused Ownership is checked before the candidate list is read
Candidate indexAn index outside the stored candidate listrefused Reported as an out-of-range error for that item
User noteArbitrary textstored Written only to the requesting user’s own row

3.3  Database-level constraints

Beneath every application-layer boundary sit 103 check constraints in the database, which an application defect cannot bypass. They constrain value ranges, enumerated states and the internal consistency of a row independently of the code path that produced it.

3.4  URL canonicalisation and server-side request forgery

The pasted link is the only user-supplied value that causes the server to open an outbound connection, and is therefore the system’s server-side request forgery surface. The canonicaliser applies the following rejections before any request is issued.

RejectedThreat addressed
Any scheme other than http or httpsfile, ftp and data URLs never reach the fetcher
Any URL carrying credentials in the userinfo componentDisguising the effective host behind a trusted-looking prefix; rejected outright rather than left to parser behaviour
Any URL carrying an explicit portAddressing an internal service on a non-standard port
Any bare IP literal, IPv4 or bracketed IPv6Loopback and cloud metadata addresses
Any hostname not exactly equal to one of six TikTok hostsMatched for equality, never by suffix, so tiktok.com.evil.io is rejected as any unrelated host is

3.5  Redirect handling

Redirects are followed manually rather than by the fetch implementation. Every Location header is re-checked against the same allow-list before it is dereferenced, with a maximum of five hops, a timeout on each request, and no HTML parsed at any point.

Both import routes re-execute the complete check on the server irrespective of any check performed by the client, since only the server-side result is authoritative. This is the same principle applied to place data in section 3.2.

3.6  Treatment of language-model output

The language model is treated as an untrusted source on the same terms as the external link. Its output is parsed against a schema, and every claim it produces must quote the source caption before that claim is presented to a user for review. The provenance distinction between an extracted value and an inferred one is preserved through to the review screen.

Section 04

API Protection & Secrets Management

Six route handlers exist under /api. All are POST-only, and each establishes the identity of the caller before performing any other work.

4.1  Route inventory and method restriction

The six routes export a POST handler and no other method. The restriction is a cross-site request forgery control as well as a design convention: a GET handler is reachable from a cross-origin image tag or hyperlink, whereas a JSON POST is not.

Most of the product presents no route surface at all, because most of it is not reached through a route. Every value the user reads is fetched on the server under that user’s own token, and is therefore subject to the policies described in section 2.

4.2  Error responses as a disclosure channel

A route returns a code drawn from a closed set of thirteen and nothing further: no provider message, no upstream status code, no stack trace and no environment-variable name.

Diagnostic detail is written to the server log, which records codes and counts. Captions and coordinates are not written to the log.

The policy governs framing and embedding only. It carries no script-source directive; that gap is stated as a residual risk in section 5.3.

4.4  Secret classification and enforcement

The classification rule is a single line: a variable without the public prefix must never reach the browser. Two independent mechanisms enforce it, so the rule does not depend on developer discipline.

4.5  The privileged database key

The privileged key bypasses row-level security entirely, so none of the controls in section 2 constrains a query made with it. Its protection is placement and secrecy: it is never present in the browser bundle, never committed to the repository, and never included in an error response, as stated in section 4.2.

Section 05

Known Risks & Security Hardening

No exploitable cross-user vulnerability was identified. The scope of that statement is bounded by the attacks that were actually executed, which are enumerated below.

5.1  Attacks executed and their outcomes

The following attacks were executed rather than reasoned about. Each was attempted from a freshly created attacker account operating as a genuine signed-in user, then repeated with no account at all, and again over HTTP with genuine tokens.

AttemptMethodOutcome

Deletion of another user’s rowsDirect deletedenied

Every read returned zero rows and every write returned a permission error, in all three execution contexts.

5.2  Accepted property: readability of a shared venue row

One property of the schema behaves in an attacker’s favour and is documented rather than remediated: saving a venue identifier already in the attacker’s possession grants read access to that shared venue row.

The acceptance rests on three conditions. The identifiers are random 128-bit values, so they are not enumerable. The data in the row is open and non-personal. The column grants described in section 2.5 mean the row reaches no user-scoped data.

5.4  Hardening priority

The highest-value hardening measure is continuous execution of the eight policy suites described in section 2.6 on every push, rather than on demand.

Evidence gathered once is a snapshot of a schema at one commit, and the schema changes. Of the residual risks in section 5.3, the per-user import cap is the first to become necessary, since the condition that withdraws its acceptance — opening sign-up — is a single configuration change.
