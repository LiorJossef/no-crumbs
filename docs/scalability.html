Section 01 · what runs out first

User Load & Extraction Queue

At tens or hundreds of users, nothing in our own system runs out first — a third-party quota does.

Every screen reads only the signed-in person’s own rows, and row-level security scopes each read by user at the index, so a hundredth account adds rows no query walks. Imports, not user count, are the axis this product gets expensive along.

An import is the one expensive path, and it is external calls in a row: TikTok’s oEmbed endpoint for the caption, a language model for candidate place names, then up to eight places lookups. The model is chosen by one environment variable, with two adapters behind one interface; production runs Gemini, and the code branches in exactly one file.

What ships is two request/response round trips, not a stream and not a queue. The first returns the thumbnail, handle and caption in under a second so the screen has something true on it; the second runs extraction and resolution. The streaming route was planned and never built, and the screen says so rather than faking progress.

Why there is no queue

There is deliberately no job queue and no separate cache server, because the tables a queue would have needed already exist. imports is the per-attempt record with its stage, timings and error code. extractions is unique on the source, model and prompt version together, so re-pasting a link against the same model costs nothing. sources caches the post, and place_lookups caches provider responses under a 28-day expiry the database itself enforces. The caches live inside the source of truth, so there is no second system to keep consistent.

Rate limiting exists and is honest about being weak. The search-interpretation route allows twenty submits per user per ten minutes, and the thumbnail route holds three windows over a shared daily allowance — but those counters live in process memory, so they reset on deploy and do not span instances. They are a brake on a stuck client, not a security control. The one instance-independent bound is in Postgres: a per-source cooldown of ten minutes, and a day after TikTok refuses a post.

The import path itself has no per-user cap at all. The trigger for adding one is the day the provider quota is raised — an unmetered import is only safe while that daily ceiling is doing the limiting. The change is small, because the index a counter would read is already in the schema.

Section 02 · who does the work

Client vs Server Boundaries

All data fetching happens on the server; the browser holds interaction and never queries the database.

Each route’s page builds a cookie-bound database client and reads under the public key carrying the user’s token, so every query a page makes is subject to row-level security.

The 83 files marked as client components exist because the map needs the browser, and because sheets, chips and the search field are state. They receive already-fetched arrays as props, and search, category, tag and been filtering are array operations over that array — the list and the pins agree because they filter one array, not two queries that could drift.

One client-to-server call is not a page load, and it reads no rows: the search interpreter sends the sentence a user typed and returns a set of filter values the browser then applies itself. It is rate-limited because it spends model budget, not because it touches data.

The privileged database key never reaches the browser, and three things ensure it: the module that reads it imports server-only, its variable carries no public prefix so it cannot be inlined into a bundle, and its only callers are the two import routes, each of which identifies the user first. The rule in that file is that a privileged query never filters by user — it touches only the global caches, which have no user column.

Section 03 · fetch all, draw some

Map Rendering & Viewport Data Fetching

The map fetches the whole library in one query and bounds the drawing rather than the fetching — a decision with a trigger, not an oversight.

The map read selects 31 columns across the user’s saves, the joined place and the linked source, ordered newest first, with no limit, no filter and no viewport box. Three product requirements need the whole set: the camera frames the entire library on first paint, the list and the pins must agree, and search must find a place that is off screen. A viewport query would need a second “bounds of everything I have” query beside it and would still leave off-screen results unreachable.

Rendering is where the bounding happens, in three zoom bands: country markers furthest out, then areas, then individual pins. The map library owns the swap through each layer’s own zoom range, so there is no zoom listener and no re-render while a user pinches.

The honest limitation is that the map data still carries every saved place as its own feature at every zoom. Cost here is linear in library size and nothing caps it — the payload, the feature collection rebuilt on each filter change, and the array re-filtered on each keystroke grow together. The database is not the part that struggles; the phone is.

The trigger is a real library in the high hundreds; the design target is a hundred or so places, and the browser is comfortable there. Pagination is measured and ready rather than absent: an existing index already matches the query’s ordering exactly, so adding a limit would let the planner walk it and drop the sort. Today the query cannot use it, because a read with no limit has to fetch everything anyway.

Section 04 · what the database does

Database Query Performance & Indexing

Every user-facing read is served from an index keyed on the user, so query cost tracks one person’s library rather than the size of the table.

Three queries are worth naming. The map read is the most frequent: a scan of the reader’s own saves, then a key lookup per place. The collections index read is the heaviest per page, because it embeds every item of every collection the user belongs to just to render a count and a few category chips. The places prefilter is the only query over a six-figure table, and it is off the hot path — it is a fallback that runs a few times per import, never per page view.

IndexWhat it serves

No query asks the database to search or filter, so no text index is needed — and a leading-wildcard match could not use one anyway.

One index is genuinely missing, and it is the shape to watch: collection_invites has no index on its collection, verified absent across all 36 migrations. It is a globally growing table read by a per-user query every time an owner opens a collection, so the scan is linear in every invite ever created across the whole product. The trigger is a few thousand rows, and the fix is one index.

Two indexes earn nothing today, and both say so in their own migrations: one exists for whole-table maintenance and no per-user query consults it, and the tag index serves nothing at all now that tag filtering happens in the browser.

Section 05 · the ceiling, and the plan

Current Scale Limits & Future Architecture

The ceiling on this product is a provider quota, not the database.

The places provider behind the live key carries a hard cap of 100 searches per day, across the whole project. At two to eight lookups per import that is roughly a dozen to fifty imports a day for every user combined — a billing decision rather than an engineering one, and the reason “the product works” and “the product serves a hundred people” are different sentences.

Second is the import request’s wall clock: no maximum duration is configured anywhere, so the route chaining an oEmbed call, a model call and eight sequential lookups runs against the platform default. That arrives as one person’s failure rather than a scale wall, and the fix is one line.

Third is the map payload, at a library several times larger than the design target. Fourth is the collections read, expensive for a reason the screen does not need: it ships items in order to count them. Fifth is the missing invites index. None of those is “the database at hundreds of users”, and that is the headline.

What we would do, in order

Raise the provider quota and add a per-user daily import cap together, so one person cannot spend everyone’s allowance. Set a maximum duration, then build the streaming import route that was planned and cut, turning the longest request in the product into visible progress. Add pagination and a viewport read once a library passes a few hundred places, keeping the bounds query the camera needs. Then make the collections read an aggregate, add the missing invites index, and drop the tag index unless server-side tag filtering arrives.

A durable rate limiter — a counter table in Postgres — belongs after those, once enough instances stay warm for the in-memory version to be visibly wrong. We would still not add a queue or a separate cache server, because no job outlives its request. The day one does, the imports table is already its schema.
