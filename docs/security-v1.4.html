Abstract. Map privacy is enforced at the database level: Postgres row-level security ties every row to its owner, so application code cannot widen access. Section 01

Authentication & Session State

Signing in is handled by Supabase. We never see a password, never hash one, and never store one.

1.1  How signing in works

One sign-in screen calls Supabase Auth with an email and password; nothing else in the codebase authenticates anybody, and the password goes from the browser to Supabase directly without passing through our server.

Credentials and account records live in Supabase’s internal auth schema, which is not exposed through the public Data API and cannot be read by any browser-facing database role. A user’s email address is unreachable from the client. We did not build our own authentication, because password hashing, reset emails and token rotation are bad things to hand-roll.

1.2  How a session works

After sign-in the browser holds a cookie containing an access token, valid for one hour and renewed by a refresh token.

We write that cookie through our own small adapter because the Supabase library sets a 400-day cookie by default. If the user does not tick “remember me”, our adapter leaves the expiry off, so the cookie dies when the browser closes.

1.3  Where identity is checked

getSession() only decodes the token the browser is holding — unverified client-side data. getUser() verifies that token against the auth server, and it is what runs on every protected action: the request proxy, every page that renders a user’s data, every API route and every server action.

1.4  What you must be signed in to do

There is no administrator, no moderator and no support login, so on your own map authorisation is one question: does this row belong to you? Shared collections add a second question and three roles — owner, editor and viewer — which are not a UI convention but a value in collection_members.role, read back by a collection_role() function that answers only about the caller. An owner may rename the collection, invite and remove people; an editor may add and remove places; a viewer may only read. Every policy on the four collection tables is written in terms of that function.

Open to anyoneRequires being signed in
Landing, sign-in and sign-up, password resetThe map, importing a link, collections, profile, account
An invite link — a generic screen naming neither the collection nor its ownerAccepting that invite
Nothing else: no public profile, no public collection, no guest view of a mapEvery read and every write of real data

Each signed-in page checks identity itself and redirects if there is none. Every write goes through a server action that calls getUser() before touching data. The one exception is sign-out, which ends a session rather than reading one.

Section 02

Row-Level Security & User Map Isolation

Your map is private, and the database is what makes it private. Not our application code.

2.1  How authorisation works

Postgres applies a row-level security rule to every query touching a table, combined with whatever the caller asked for — a caller can narrow a result set, never widen one. Nearly every rule here is the same test, owner = current_user, so asking for someone else’s rows returns zero.

Shared collections are the deliberate exception: there the rule asks whether the caller holds a live role in the collection. All 38 policies are written for the signed-in role; none for the anonymous role. Nearly all of them are this short:

create policy saved_places_select_own
  on public.saved_places
  for select to authenticated
  using (user_id = (select auth.uid()));

Three lines, and they are the whole of the privacy model. auth.uid() reads the user id out of the verified token Postgres was handed, so it cannot be spoofed by the caller; to authenticated means the rule is never even considered for an anonymous request, which holds no privilege to be filtered.

2.2  Why the database, and not our code

Four things make the isolation hold even if our application code is wrong.

  • Enabled and forced on all 17 tables. Forcing binds the table owner too. Three tables carry no policy at all — the strictest setting there is.
  • The anonymous role has nothing. No privileges on any table, column or function. The publishable key in the browser names the project and grants nothing.
  • Grants are column by column. You may change a saved place’s name, category, note and visit state — never its owner column, so moving a place into another account cannot be expressed.
  • SECURITY DEFINER functions guard shared tables. They update shared rows on your behalf and re-check your identity internally, so you need no write permission of your own.

The first two are not left to good intentions. New tables in Postgres arrive with privileges already granted to the browser-facing roles, so a table that ships without the revoke is a cross-user read on the day it lands. scripts/check-migration-grants.sh runs in CI and fails the build if any migration creates a table in public without enabling and forcing row-level security and revoking from both roles — so the paragraph above is an enforced invariant rather than an assertion about the schema as it stands today.

The result: a forgotten check in our code renders an empty list, not somebody else’s places.

2.3  What happened when we attacked it

Two users. One — the victim — held a saved place with a private note, its source link, and a collection. We signed in as the other and ran nine attacks against those rows, in one transaction that was rolled back afterwards, with the connection set up exactly the way a browser request arrives: the signed-in database role, carrying the attacker’s verified token.

Every read returned zero rows and every write was refused. Attacks 6 and 7 failed before any policy was consulted, because those columns carry no grant at all. Attack 9 is the interesting one: one of those functions runs with elevated rights and a signed-in user may legitimately call it, so it does not refuse — it runs, matches nothing, and returns. A function that silently does nothing and one that refuses look identical from the caller’s side, so the harness does not trust the absence of an error: it re-reads the victim’s row afterwards with full rights and asserts the owner and the note are unchanged. They were. Repeated with no account at all, every one of the nine failed a step earlier still, at permission denied for table.

Eight SQL suites keep this honest as the schema changes: each creates its own users, tries the cross-user read, write and delete, and rolls back. One caveat we name rather than hide — knowing a place’s id lets you read that place row, but places are shared open-data rows, so an id reveals only a public name and location, never who saved it or their private note.

Section 03

Input Sanitization & External Link Defense

Three things arrive that we did not write: the request body, the TikTok link, and whatever the model says. All three are treated as hostile.

3.1  How input is validated

Complex payloads and the model’s output are validated against explicit Zod schemas: the import-confirm request body, TikTok’s oEmbed response, the model’s output, and two paths that re-parse rows read back from our own database.

The other five API routes carry two or three flat fields, checked field by field instead: every value type-tested, empty values rejected, free text length-capped, all before any external call.

Underneath both, every table constrains its own columns with check constraints, so value ranges, allowed states and a row’s internal consistency are enforced by Postgres whatever code path produced the row.

3.2  Validation is not always enough

The import-confirm route used to accept the place itself from the browser — name, latitude, longitude — and one ordinary signed-in request renamed a shared Tel Aviv café and moved it to the Eiffel Tower. No schema can tell a true latitude from a malicious one, so the request now sends only an extraction id, an index into the candidate list the server itself produced, and the user’s own note.

3.3  The pasted link

The pasted link is the only user input that makes our server open an outbound connection, so we parse it with the WHATWG URL parser and reject anything that is not http or https on one of six exact TikTok hostnames — compared for equality, never by suffix, so tiktok.com.evil.io is refused. Shortened links are followed manually rather than by fetch, and every redirect hop is re-checked against those same rules before we follow it, so a hop that leaves the verified TikTok domains is refused instead of fetched.

3.4  What the model says

The model is untrusted on the same terms as the link. Its output is parsed against a Zod schema — or, on the search path, JSON.parsed into a deliberately unknown value and then clamped to a closed vocabulary: a category, tag or visit state the model invents is dropped rather than rejected, because the caller already told us which values it actually has rows behind, and the clamp keeps only those. The clamp is the stronger of the two defences, because it does not depend on the model having agreed to a shape. Every claim must quote the caption it came from before a user sees it, and the difference between what the caption said and what the model inferred survives to the review screen — so the user confirms a place rather than inheriting a guess.

Section 04

API Protection & Secrets Management

Six API routes, all POST-only, each one identifying the caller before it does anything else.

4.1  How API calls are protected

All six route handlers under /api are built the same way, so there is no odd one out to forget.

  • POST-only endpoints. This alone does not stop cross-site request forgery — a cross-site form with enctype="text/plain" sends a POST with no preflight, and req.json() will parse it whatever the content type claims. What actually stops it is the session cookie’s SameSite=Lax attribute, which means the browser does not attach it to a cross-site POST at all, so the request arrives unauthenticated and is refused at the next line. Server actions are covered separately by Next.js’s own Origin-against-Host check.
  • Server-side authentication on every call: each route begins with getUser() and returns 401 if there is no verified user.
  • Generic error codes. Failures return a short code from a closed set — never a stack trace, a provider message or an environment-variable name. Deliberately, three of the stored functions and one route answer “that is not yours” and “that does not exist” with the same code, so the error itself cannot be used as an oracle to enumerate other people’s ids.
  • Standard security headers on every response: nosniff; frame-ancestors 'none', so nobody may embed us; frame-src allow-listing exactly one host, https://www.tiktok.com, so we may embed nothing else; a tightened Referrer-Policy on the invite route; and a Permissions-Policy denying camera, microphone and payment.

Most of the product has no API surface at all: pages load their data on the server under the signed-in user’s own token, so those reads meet the policies in section 2 like everything else.

4.2  Where secrets are kept

Every secret is an environment variable. The .env files are gitignored, only an empty example is committed, and in production the real values live in Vercel’s encrypted environment store.

  • One rule, held two different ways. Anything without the NEXT_PUBLIC_ prefix must never reach the browser. Next.js inlines only prefixed variables into the bundle, so an unprefixed name is not something a client component can accidentally read. On top of that, every shared module that reads a secret — the Supabase server client, the resolver, the extractor, the service-role client — imports server-only, which turns an import from a client component into a build failure rather than a shipped credential.
  • Two route handlers read a key without that import, and we say so rather than claim an absolute. A route.ts is server-side by construction — it is never bundled for the browser — so they are safe; but “every module that touches a secret imports server-only” would be a stronger sentence than the code supports, and the guard is worth adding for the next person who copies one of those files.
  • The service-role key never leaves the server. It bypasses row-level security entirely, so it is used only for account deletion and shared-table writes — never in the bundle, the repository or an error response.
  • The Google Places key is the awkward one. It carries the public prefix but is read only on the server, so it is not in the bundle today — and unlike the Supabase key, this one costs money. See 5.2.

Section 05

Known Risks & Security Hardening

We found no way for one user to reach another user’s data. That statement is only as wide as the attacks in 2.3, and these are the weaknesses we know about.

5.1  Location data, and deleting your account

This is a map, so it is fair to ask what it knows about where you are. Nothing. “Near me” reads your position from the browser, centres and sorts the list on your own device, and sends it nowhere — no API route, no server action, no column. The only coordinates we store are the place’s own, on a shared row built from open data.

Where the boundary actually is, because “we send your location nowhere” and “we send nothing to anyone” are different sentences. Resolving a place does leave our servers: the caption text goes to the model, and a place name with an optional city hint goes to Google. Your device’s position is never part of either call, and neither provider is ever told which user asked. What travels is what the video said; what never travels is where you are standing.

Deleting your account removes your personal data — saved places, source links, imports, mentions, profile, collections and memberships — and is blocked if you are the sole owner of an active shared collection, so deleting your data never deletes anyone else’s. Two things survive it, and naming them is more useful than a clean sentence:

  • The captions. The sources table has no owner column — it is keyed by the TikTok post, so two people importing the same video share one row. The caption text, the author’s handle and the link therefore outlive the account that first fetched them, with nothing left to tie them to that account.
  • Notes already added to someone else’s shared collection. collection_items.added_by is on delete set null on purpose: deleting your account must not silently empty a collection other people are still using. The note stays; the authorship is unlinked.

Both are defensible for what this is, and both are things a user would want told to them rather than discovered. Neither leaves anything that identifies the deleted user.

5.2  What is still weak

These are real and open. Each is graded for what this deployment is — a course project with no public users, and with sign-up closed. That last one is load-bearing for every severity below, so it is worth saying exactly what it is: a project-level setting in the Supabase dashboard, not a line of code in this repository. Nothing in the codebase would stop a stranger registering; the provider does.

5.3  What we would do next

  • Automate the eight SQL security suites in CI, running on every push — the attacks in 2.3 prove something about the database we tested, not the one six migrations from now.
  • Implement import rate limiting, the first acceptance above due to expire, and move the thumbnail counter into the database while we are there.
  • Set an expiry on invite links and default them to viewer rather than editor.
