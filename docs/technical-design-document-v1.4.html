Abstract. No Crumbs turns a pasted TikTok link into places on a map. This document explains how: what the application is built from, how a caption becomes candidate places and then real coordinates, what is stored and why places are shared while saves are private, what the routes and actions do, who is allowed to do what, and what happens when something fails. The design came before the code; this version reconciles the two, and describes the system as deployed.

Section 01

What the System Is Made Of

One Next.js application, deployed as a single unit, divided into four source layers. The one rule that shapes everything else is that src/domain/ may import no outer layer and no vendor SDK.

1.1  The four layers

app/ holds the pages, the route handlers and the server actions, and is the only layer in which Next.js appears. domain/ is plain TypeScript — no network, no database, no React — and holds the rules: how a link is classified, how a name is scored against a search result, what makes a candidate plausible. integrations/ holds one adapter per outside service, and is where a vendor’s types stop. components/ and ui/ hold React and the framework-free logic behind it.

The domain imports no layer outside itself and no vendor SDK. Zod is its one third-party dependency, and it is there because a validator is a rule, not a vendor. So the domain’s rules can be tested without a browser, a database or a network. npm run check:layers keeps it that way: it writes deliberate violations into the tree and fails if the linter does not reject them. It also checks that every module holding a secret imports server-only, so a leaked key breaks the build instead of reaching a browser.

1.2  Where things live

PathWhat lives there

app/import/The paste flow, one component per screen

1.3  Pages

There are eleven: /, /sign-in, /auth/reset, /auth/new-password, /import, /profile, /account, /collections/join/[token], two collections paths kept as redirects, and /map, which is the shell the product mostly lives in.

/map is one route carrying three views — the places list, the collections index, one open collection — switched by search parameters rather than route segments, because changing a segment unmounts the drawer and rebuilds the map.

And nothing scrapes TikTok or logs into it — captions only, through the public endpoint.

Section 03

How a Pasted Link Becomes Places on a Map

This is the process the product exists for. It has four stages: identify the link, fetch the post, read the caption with a language model, and match each name it finds against a real place.

3.1  Identify the link, then fetch the post

The first stage is about identity, not content. The server checks the host against a short allow-list, follows a short link if there is one — re-checking the host at every redirect — and pulls out TikTok’s numeric video id. That id is the key everything else hangs on, so pasting the same video twice produces one stored post, not two.

The post is then fetched through TikTok’s oEmbed endpoint, which returns the caption, the author and a thumbnail. Captions are the only thing read: nothing listens to the audio or reads text burned into the video. Plenty of videos say the place out loud and write nothing, and those produce no candidates.

3.2  Read the caption

The caption goes to a language model under a fixed prompt, and the reply shape is not left to chance. domain/extraction/schema.ts is converted into a JSON Schema and handed to the API, so the model is constrained at the source. We never parse prose or run a regular expression over an answer.

The fields we ask for are sorted into four kinds of claim, because they cannot be trusted equally.

  • Copied from the caption. rawName, the quote supporting it, and any city or address it mentions. These have to appear in the caption literally, so checking them is a substring test rather than a judgement.
  • The model’s reading of the caption. A category, a one-line reason, tags. Allowed to interpret, not to go beyond what is written.
  • The model’s recollection of the world. A coordinate, an official name, alternative spellings. No caption can confirm these, so only a person can.
  • The model’s opinion of itself. Its confidence score, which we store so it can be measured and never show.

A constant in the code labels every field with its kind, and a test fails if a new field arrives unlabelled.

3.3  Throw away what is not a place

Two checks turn trust in the model into a string search. If the quote it gives as evidence is not in the caption, the candidate is dropped. If the fragment behind its one-line reason cannot be found, the reason is erased. The same pass discards things that are obviously not places — links, bare usernames, names that are only a city, phrases like “this hidden gem” — before any of them cost a lookup.

Weak but genuine cases are kept: a place named only in a hashtag stays, with its confidence capped and the review screen saying why. Two numbers bound the rest, and they are deliberately not the same number. CANDIDATE_CAP is twelve — twelve candidates are carried, and a reply of thirteen to twenty-four is truncated to the first twelve rather than refused, so a caption naming thirteen places does not lose all thirteen. FLOOD_GUARD_CANDIDATES is twenty-four, and that is the refusal: past two dozen the model has stopped reading the caption and started listing hashtags, so the reply fails validation instead of flooding the pipeline. Of what is carried, only the first eight are looked up; the rest are kept and marked unchecked.

3.4  Match each name to a real place

Each surviving name goes to Google Places, in a query built from the name, whatever city, country or address the caption gave, and any alternative spellings the model offered. That last part is how a Hebrew caption reaches a place listed under its English name.

The provider does not rank for us. domain/places/score.ts scores its results on how closely the names match, whether the categories agree, and how confident the dataset is. Each candidate then lands in one of three outcomes: a clear winner, pre-selected on the review screen; several plausible options, offered as a shortlist to pick from; or no match.

Two gates decide which, and both must pass: the best result has to clear an absolute score floor, and it has to beat the second best by a margin. The margin does the real work. A caption that names no place tends to match a great many rows equally well — each of them scoring respectably — and a floor alone would pre-select the first of them. The margin is what notices there was nothing to choose between.

When nothing matches we do not invent a coordinate, and we do not throw the candidate away. It is kept with the model’s own guess, marked approximate on its card, with a link out to a public map so the user can check. We skip a candidate only when the provider found nothing and the model offered no coordinate.

3.5  Caching

A model run is stored against the post, the model and the prompt version together, so pasting the same link again costs no model call. Provider answers are cached too. Saving money is the smaller reason: the model is not deterministic, so without the cache the same link returns different places on a second run. The cache is what makes an import repeatable.

3.6  Nothing calls a vendor directly

The pipeline never calls the model or the places provider itself. Each sits behind a small interface owned by the domain, with one adapter per vendor behind it, chosen in a single factory. No vendor type crosses that line. So tests replace the network with fakes, a second model is a second file, and changing places provider touches one place: the factory in integrations/places/, which also reports which provider it chose and why.

Section 04

The Map, and Where State Lives

There is no client state library. Each kind of state has one home, chosen by how long it has to survive.

4.1  State placement

Kind of stateWhere it livesWhy there
The user’s placesRead on the server, in app/map/page.tsxIt must survive a refresh, and the database already holds the rules about who can see it
Which view is openURL search parametersIt must survive a navigation and be shareable
Selection, search text, filtersLocal state in the component that owns itIt needs to survive neither

4.2  Reading and writing

The page reads the user’s saved places on the server and passes plain objects down. No component fetches its own data when it mounts. That query has no “where user = me” clause, deliberately: row-level security already scopes it, and writing the same rule twice is how two versions of it end up disagreeing.

Writes go through server actions, and each ends by revalidating the page it affected. The server stays the source of truth, and there is no client cache to keep in step.

4.3  One map for the whole session

A map is expensive to build: a style download, a round trip for tiles, and a camera back at the start. MapLibre also offers no way to hand a live map to a newly mounted component. So the map is created once, in the root layout — the only ancestor every map-bearing route shares — and rendered through a React portal into a container the layout owns. Each route borrows that container by appending it to its own anchor. Moving the node moves the canvas without disturbing it, so changing tabs no longer rebuilds the map.

4.4  One filter, three surfaces

Tag, visit state and search text are applied in one place, and the resulting list is handed to the mobile sheet, the desktop panel and the pins. There is no second code path that could filter one surface and not another, so the count in the list and the number of pins cannot disagree.

Section 05

Screens and the Main Flow

Eight surfaces. One of them — the map — is where a person spends their time; the others exist to put something on it or to get back to it.

5.1  The screens

ScreenWhereWhat a person does there
Landing/Reads what the product is, and signs in
Sign in/sign-in, /auth/reset, /auth/new-passwordEmail and password, and the two steps of a reset
Map/mapThe library: pins, the list, search, filters, and one place in detail
Adda sheet over whatever is on screenThe ＋ opens one sheet offering the two things a person can create: a place, or a collection
Import/import, or the same flow over the mapPaste a link and review what came back
Collections/map?view=collectionsThe index, and one open collection, in a drawer over the map
Join/collections/join/[token]Accepts a share link, having shown what is being joined
Profile and account/profile, /accountThe name on the account, signing out, and deleting your data

5.2  Pasting a link, screen by screen

Four screens, and one piece of state saying which is showing. Every move between them is caused by a real server response; nothing advances on a timer.

Paste is one field. The link is checked as it is typed, so an unsupported one becomes a clear offer to add the place by hand before any request goes out.

Waiting covers the model call, which is the slow part. As soon as the oEmbed fetch answers — about a second in — the screen shows the post itself: thumbnail, handle, caption. The three stages report themselves as they finish.

Review shows the caption plainly, and beneath it each candidate with what the caption said and what we matched it to. A clear winner is pre-selected and can be changed. An ambiguous one shows its shortlist rather than guessing. Nothing is written to places or saved_places until this screen is confirmed.

Then the flow hands the new places up and closes. The map moves to frame them and says what was saved.

5.3  The screen most people see most often

Most captions name no place, so “no places found” is the ordinary end of this flow rather than a failure of it. Its screen shows the post and the caption that was read, so the claim can be checked rather than believed, and offers two ways on: search for the place by name, or say in one sentence what the caption did not and let that be read instead. There is deliberately no retry button, because re-reading the same caption returns the same nothing.

Section 06

What Is Stored, and How It Is Organised

One Postgres database. Its shape follows from a single decision: a place in the world is not the same thing as one person’s decision to keep it.

6.1  Places are shared, saves are private

This is the one real modelling decision in the product. places is a shared, de-duplicated record of a real place — its name, category and coordinates. saved_places is one person’s entry pointing at it, holding their own name for it, their note, their tags and whether they have been.

So one place is one row, however many videos mention it. Three TikToks recommending the same bakery produce one place, one save, and three links back to the videos. It also settles where an edit lands: your note, your tags and your own category write to your own row and never the shared one, so nobody can change the map underneath anyone else. A uniqueness rule on (user_id, place_id) makes saving the same place twice impossible rather than merely unlikely.

6.2  The tables

TableWhat one row isHow it relates

Five supporting tables sit behind these, for seventeen in all. place_lookups caches provider answers. profile_names holds the name given at sign-up. poi_index and poi_regions are the local copy of open places data the second resolver adapter reads. And place_mentions is where a place we could not identify is meant to be kept honestly rather than discarded — its schema, its grants and its policies are written and tested, but nothing on a screen reads it yet, so it is the one table in this list that is not carrying the product.

6.3  The main operations

KindOperationHow it works
CreateSave places from a TikTokPOST /api/imports/confirm calls resolve_place() to find or create the shared place, then save_place() for the user’s own row (section 7.3)
CreateAdd a place by handA server action, through the same two functions, with no video attached
ReadThe map and the listOne query joining saves to places, run on the server
UpdateRe-categorise, note, tag, mark “Been there”A server action updating the user’s own row
DeleteRemove a save, or an accountDeleting a save removes that row and its links to videos; the shared place stays for everyone else. Deleting an account is a Supabase admin delete of the auth.users row, and everything else follows the foreign keys down from there — there is no application-level cleanup, deliberately, because a second definition of “the user’s data” would drift from the one Postgres actually obeys

Two rules are enforced by the database, not the application. Nothing is written to places until the user confirms; until then the candidates are JSON on extractions.candidates, which is the row the confirm route reads them back from, with a copy on imports.candidates kept for the audit trail. And a place is de-duplicated inside resolve_place() — on the provider’s id first, then on the same name within 75 metres — so two people importing the same bakery converge on one row.

Section 07

Routes, Actions and How Data Flows

Eight route handlers and seven server-action modules. Something becomes a route handler only when it needs a slow external call or elevated access; everything else is a server action or a plain read on the server.

7.1  The two paths through the system

Reading. The browser requests a page. The page is a server component, so it queries Postgres directly with a client carrying the signed-in user’s credentials, and the policies return only that user’s rows. The page renders and sends HTML with the data already in it. Nothing fetches on mount; there is no API in between.

Writing. The browser calls a server action, or posts to a route handler for the import steps. It validates its input, identifies the user, and writes through that user’s own database client, so the permission decision is made by Postgres rather than an if statement. It then revalidates the affected page, which pulls fresh data back down the read path. The server stays the only source of truth.

Signing in, which is neither. The auth screens — sign-up and sign-in at /sign-in, and the two steps of a reset at /auth/reset and /auth/new-password — are client components, and they call Supabase Auth from the browser with the public anon key. No password ever reaches our own server. Supabase then sends the user back to GET /auth/callback carrying a one-time code; that route handler is what calls exchangeCodeForSession and sets the session cookie, so a code that is one exchange away from a live account is never handed to React, never a prop, and never left in the address bar. From then on src/proxy.ts refreshes that cookie before every page, because a server component cannot write one for itself.

7.3  Server actions, and the one request worth tracing

Server actions cover every ordinary change to a user’s own rows: re-categorising, noting, tagging and marking a place “Been there”, deleting one, adding one by hand, collections, profile, account and sign-out. There is no REST layer over our own database: row-level security is already the authorisation layer, and a hand-written one would be a second place for the same rules to drift.

The request worth following all the way through is the confirm. Here it is with the values from a real run on 5 September 2026, so nothing below is illustrative.

On confirm, the browser does not send that place — it sends a pointer to the one the server already stored: { extractionId, items: [{ candidateIndex: 0, optionIndex: 0, note }] }. The server checks the extraction belongs to the caller and reads the name and the coordinates back from extractions.candidates, so a forged request cannot invent a place or move one that other users have saved. resolve_place(), the only function permitted to write to the shared places table, finds no existing row within 75 metres under that name and creates one — name Kohi בית קפה יפני, category cafe, lat 32.088286, lng 34.773303, country_code IL. Then save_place() writes the row that is actually yours: a saved_places record with your user_id, that place_id, origin 'import', visit_state 'want_to_go', and a saved_place_sources link back to the TikTok it came from. Paste the same link tomorrow and the unique key on (user_id, place_id) is what refuses the second save.

Section 08

Who Is Allowed to Do What

There is one kind of account. Anything that looks like a second role is a role inside one shared collection.

A visitor who is not signed in sees the landing page, the sign-in and password pages, and a preview of a collection someone shared a link to. That is all. A signed-in user owns a library that is private by default, plus any collections they made or were invited to. There is no administrator and no staff view: no screen shows one person another person’s library.

8.1  Where the check happens

src/proxy.ts runs before every page. It refreshes the session cookie, which a server component cannot do for itself, and redirects a signed-out visitor away from /map. Every other page that shows a user’s data calls getUser() itself and redirects if nobody is signed in — rather than relying on a list in middleware that someone will forget to add a new page to.

The real check is in the database. Row-level security is enabled and forced on all seventeen tables — forced matters, because without it the table’s own owner bypasses every policy — and the policies are written in terms of the signed-in user’s id. A whole policy looks like this:

create policy saved_places_select_own on public.saved_places
  for select to authenticated using (user_id = (select auth.uid()));

That is the authorisation layer, in full, for reading someone’s library. There are three more like it for insert, update and delete. Pages and server actions both query with a client carrying the user’s own credentials, so a query for another user’s rows returns nothing rather than being refused — which is why the application contains almost no permission logic. A build script fails if a migration ships a new table without the enable-and-force pair.

8.2  The one exception

A user cannot be allowed to write to the shared places table directly, so resolve_place() runs with the service role and is the only path that can. Seven modules hold that key: five route handlers — confirm, probe, source-preview, place-search and thumbnail — and two server actions, account deletion and manual add. All seven are server-only, and the key cannot reach a browser because the module holding it fails the build if client code ever imports it. Every one of them runs its ownership check on the user’s own client first, so the privileged step is reached only after the database has agreed the request belongs to the caller.

8.3  Roles inside a collection

A collection has exactly one owner, who can rename or delete it, invite people, change roles and remove members; editors can add and remove places; viewers can read. An invite is a link carrying a token that grants editor or viewer, and it can expire or be revoked.

Membership ends rather than being deleted, so a revoked invite cannot be replayed and a demotion cannot be undone by leaving and rejoining.

Section 09

Bad Input, and What Happens When Things Fail

Anything from outside is validated where it arrives, and every failure is one of a fixed set of error codes that carry no text from a vendor.

9.1  Validating the link

The pasted link is the only outside address a user can point our server at, so it is checked before we fetch it. The host must match an allow-list of six official TikTok domains exactly, not by suffix, so tiktok.com.evil.io fails. The check runs again on every redirect a shortened link follows, up to five hops, so the server can never be sent somewhere unsafe. The check in the browser is a convenience only.

9.2  Everything else that arrives from outside

InputHow it is handled
TikTok’s responseParsed leniently about extra fields, so TikTok adding one cannot break us, but strictly about the ones we need
The model’s replyChecked against the schema. A bad reply becomes a named error, not an exception thrown somewhere odd
Request bodiesValidated against a schema before anything else runs
Our own stored JSONRe-validated when read back, because the code that wrote it may be an older deployment
Form inputChecked by plain functions that return the message the form should show

9.3  A closed set of errors

Failures are represented by a fixed list of thirteen codes. What crosses to the browser is a code, one flag saying whether retrying could help, and the id of the import it belongs to — no message, no stack, no vendor string — so nothing internal leaks into a screen or a log by accident. Each code is produced by exactly one function, which fixes whether it is worth retrying, so no caller can claim otherwise. Adapters catch every vendor exception and turn it into one of these.

The HTTP status says whose fault it was: a caption-less video is a 422, an exhausted model quota a 503 because the quota is ours, and only one code may ever be a 500 — which is what keeps a 500 in the logs worth reading. The words a user sees are held in one place on the client, one entry per code, so adding a fourteenth code is a compile error rather than a screen that quietly says “something went wrong”. Every entry names at least one way forward, and a test enforces that, so no failure screen is a dead end.

9.4  Finding nothing is not a failure

“No places found” is not in that list of errors. It is a successful result with a screen of its own, because it is the usual result. Treating the commonest outcome as a failure would make every error log and every reliability number meaningless.
