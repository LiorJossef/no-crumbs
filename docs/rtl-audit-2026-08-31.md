## Headline finding

**Hebrew rendering here is not incidental — it's a deliberate, mostly-consistent system**, built on
two patterns applied file-by-file: `<bdi>` around a name that sits beside fixed chrome (so the
chrome doesn't move), and `dir="auto"` on a paragraph/input that is itself free text. `line-clamp-*`
is used instead of `truncate` everywhere a name can be Hebrew, specifically because `truncate`'s
ellipsis lands on the wrong side of RTL text — that reasoning is written into the code as comments,
not something I had to infer.

Against that backdrop I found **two real, screenshotted defects**, both a missing `dir="auto"` /
missing-isolation gap rather than anything structural, plus one thing that is correct today only by
a Unicode accident worth protecting, and one thing I first read as a bug and confirmed is actually
correct. Full detail below, ranked by how often a real user hits it.

## Findings, ranked by real-user frequency

### 1. The note field ignores direction entirely — both read and edit — real defect

**Every saved place has a note field, and it is the single most likely place for unassisted
free-form Hebrew prose in this product.** In `src/components/sheet/saved-place-edits.tsx`:

- The read display, line 534: `<p className="text-sm leading-relaxed whitespace-pre-wrap
  text-foreground">{note}</p>` — no `dir`, no `bdi`.
- The edit control, the `<textarea>` starting around line 570 — no `dir` either, unlike the sibling
  `Name` `<Input dir="auto" …>` twelve lines above it in the same file.

Confirmed two ways:
- **Computed style**, read directly from the live DOM after opening the edit form for the seeded
  Abu Hassan note: `{ dir: null, value: 'הכי טעים בעיר, חובה לחזור', computedDir: 'ltr' }`. A
  `<textarea>` holding nothing but Hebrew is computing `direction: ltr`.
- **Screenshot**, `desktop-02-abu-hassan.png` — the popover variant shows the whole card, including
  the "YOUR NOTE" block uncut. `הכי טעים בעיר, חובה לחזור` sits flush against the card's left edge,
  same x-coordinate as the English "CATEGORY" label above it, instead of hugging the right edge the
  way a native RTL sentence would.

**The proof this is avoidable, not structural: the sibling feature got it right.**
`src/components/collections/collection-place-detail.tsx` implements the *shared collection* note —
functionally the same field, a different table (`collection` note vs `saved_places.note`) — and both
its textarea (line 437) and its read paragraph (line 459) carry `dir="auto"`. Two implementations of
the same idea in the same codebase; one has the attribute, one doesn't.

**Mechanism:** a missing `dir="auto"` attribute, two call sites, in one file. Cheapest class of fix
there is — no restructuring, no new dependency.

### 2. The address row's icon changes sides depending on the place's language — real defect

`src/components/sheet/place-sheet.tsx:1671`:

```tsx
<p dir="auto" className="flex items-start gap-2 text-sm text-foreground">
  <MapPin className="mt-0.5 size-4 shrink-0 text-muted-foreground" aria-hidden />
  <span>{addressLine}</span>
</p>
```

`dir="auto"` sits on the **flex row itself**, not on an isolated span around just the text. When the
address's first strong character is Hebrew, the whole row — icon included — resolves to
`direction: rtl`, and CSS flexbox reverses visual order under `dir="rtl"`. The pin, which is DOM-first
and renders on the *left* for an English address, jumps to the *right* for a Hebrew one.

Screenshotted side by side, same component, same session:
- `01b-search-abu-390.png` — **Neve Tzedek Coffee House**, address "8 Shabazi St": pin icon on the
  left, text following it, flush left.
- `hires-abu-hassan.png` — **אבו חסן**, address "רחוב שיף 1": pin icon on the **right**, text to its
  left, the whole row flush **right**.

This is exactly the failure mode the file's own comment (line 1615, on the `<h2>` two blocks above)
says it chose `<bdi>` specifically to avoid: *"`<bdi>` rather than `dir="auto"` on the heading: a
Hebrew name would otherwise right-align the whole identity block… so a mixed library would have a
ragged edge."* The name heading follows that rule (isolates the text only; the rename pencil stays
put on the right regardless of language, confirmed in both `hires-abu-hassan.png` and
`hires-rothschild.png`). The address row three lines later does not — it's the one `dir="auto"` in
this file applied to a container with a fixed chrome child rather than to the text alone (verified by
grep across every `dir="auto"` in the file — this is the only icon-bearing one).

**Mechanism:** `dir="auto"` on the wrong element — the icon+text flex row instead of a `<bdi>`/`<span
dir="auto">` around just the text. One-line fix, same shape as the h2 above it already uses.

### 3. Curly quote marks around the caption are correctly positioned — correct today, by a Unicode accident worth protecting

`src/components/sheet/place-sheet.tsx:1687`:

```tsx
<blockquote dir="auto" className="text-sm leading-relaxed text-foreground">
  &ldquo;{shownQuote}&rdquo;
</blockquote>
```

Screenshotted in `hires-rothschild.png` / `desktop-03-rothschild.png` (quote: `המקום הכי שווה בתל
אביב`, "the best spot in Tel Aviv"): the opening-shaped quote glyph sits at the **visual right** (the
RTL reading start) and the closing-shaped glyph at the **visual left** (the RTL reading end) — the
typographically correct arrangement for a Hebrew quotation.

Nobody wrote RTL-aware quote logic for this. `&ldquo;`/`&rdquo;` (U+201C/U+201D) are both
Unicode-flagged `Bidi_Mirrored`, and browsers auto-swap a mirrored glyph's *rendered shape* — not its
logical position — inside an RTL-resolved run. The DOM order is always ldquo-then-text-then-rdquo;
`dir="auto"` resolving to RTL here reorders that run visually and mirrors both marks, and the two
effects happen to cancel out into the right answer. **This is correct by accident, not by design**,
and the thing protecting it is the specific choice of curly HTML entities over straight quotes.
Swap `&ldquo;`/`&rdquo;` for a plain `"` (U+0022, not mirrored) — a lint autofix, a design-system
token, a different templating helper — and the correct positioning silently disappears with no
visual signal in an LTR-only review. Worth a code comment pinning the reason, or a snapshot test
against a Hebrew fixture.

### 4. Mixed-script place names reorder — first read as a bug, confirmed correct

`קפה קיוסק Rothschild` (Hebrew phrase, Latin street brand appended) renders as **`Rothschild קפה
קיוסק`** — the Latin word visually leftmost, the Hebrew phrase visually rightmost (`hires-rothschild.png`,
`desktop-03-rothschild.png`). On first look this reads like the words got scrambled.

It didn't. The name is wrapped in `<bdi>` (`place-sheet.tsx:1624`), which — like `dir="auto"` —
detects its own base direction from the first strong character. Hebrew is first, so the isolate's
base direction is RTL; in an RTL context, "what comes next" in reading order sits visually to the
*left* of what came before. A native Hebrew reader typing "קפה קיוסק Rothschild" intends the Hebrew
phrase to lead (right) and the Latin brand name to trail it (left) — which is exactly what rendered.
**Confirmed correct, not a defect.** I'm calling this out explicitly because it is the single most
surprising-looking result in this whole audit for anyone who doesn't read Hebrew, and the obvious
"fix" (forcing LTR order) would make it wrong for the audience it's for.

The rest of the row stays anchored regardless: the pin icon, the "Café · Tel Aviv-Yafo" subtitle, the
`מומלץ` tag chip, and the rename pencil never move — `<bdi>` isolates the name's internal reordering
without dragging the row's layout with it, same as finding 2's fix target.

### 6. `authorLabel` renders without `<bdi>`/`dir="auto"` in two spots — low real-world risk

`place-sheet.tsx:1690–1692` and `:1789–1790` render `{authorLabel}` bare. `authorLabel` is `@handle`
when a TikTok handle exists (always ASCII — no bidi risk) and falls back to `source.authorName`
only when there's no handle. TikTok's `unique_id` is effectively always present in real data, so
this fallback is rarely exercised — but it's the one place in this file that doesn't follow the
file's own `<bdi>`/`dir="auto"` convention, and a Hebrew display name (I seeded `יעל כהן` for exactly
this path and it went unexercised because the handle was present) would hit it.

## What is correct and appears to be systematic, not incidental

- **`<bdi>` around every place/collection name that sits beside fixed chrome** (rename pencil, list
  icon, count) — `place-sheet.tsx`, `collection-content.tsx`, `collections-index-list.tsx`,
  `add-to-collection.tsx`, `candidate-card.tsx`, `review-screen.tsx`, `add-by-name.tsx`,
  `account-actions.tsx`. Each carries an explanatory comment about *why* `<bdi>` over `dir="auto"`
  in that spot. Confirmed live for both test names, at both viewports.
- **`dir="auto"` on every genuinely free-text input I found except the two gaps above**: the manual
  add-sheet search field, the collection-name field, the saved-place-name rename field, the address
  line, the extraction summary sentence, the tag chips, and the collection note (both read and
  edit).
- **`line-clamp-1`/`line-clamp-2` instead of `truncate` on every name/description field** —
  deliberately, per the comment at `collections-index-list.tsx:330`: *"`truncate`, because an
  ellipsis on an RTL string inside an LTR box clips the [wrong end]."* The only two `truncate`
  instances left on any name-adjacent text are the English-only "N places" / "Nothing collected yet"
  peek-row summary strings (`collections-index-list.tsx:93`, `collection-content.tsx:221`) — never
  user content. Grepped exhaustively; no counter-example found.
- **Hebrew tag chips render correctly**, mixed with English ones, in both the sheet
  (`hires-abu-hassan.png`: `חומוס`, `ותיק` beside the English category line) and the filter chip row
  (`בית קפה 2` beside `Coffee 4`, `Bakery 1`, screenshotted in the full-list view) — chips use
  `dir="auto"` per-chip, confirmed live.
- **Map marker and pill labels render Hebrew correctly**, right-to-left, no mirrored or reversed
  characters, confirmed for both `אבו חסן` and `קפה קיוסק Rothschild` under their pins in both
  `hires-abu-hassan.png` / `hires-rothschild.png` (mobile) and the desktop pair.
- **Mixed real production data already exists and already renders correctly**: `Kohi בית קפה יפני`
  in `places` (found before I inserted anything) is a genuine Latin-plus-Hebrew place name from a
  real resolution, not a fixture — I didn't need to fabricate this case, only confirm the seeded
  ones behaved the same way.
